Структура шапки и разделов повторяет [ADR 0001](0001-graph-rag-v1.md). Документ
проектный: код, миграции и зависимости им не меняются. Все значения ниже относятся к

ставке НДС больше 6,06% (0.116666 / 0.11 = 1.0606, у deep так же), то есть почти при

Деградация deep → fast, `failed` и `cancelled` могут стоить нам больше списанного
(§3.4, §8.2). Расчёт цен во внутреннем документе команды.

## 1. Контекст

Расход LLM считается, но ни с кого не списывается. Права в продукте целиком
выводятся из GitHub. Состояние `main`, на которое опирается ADR:

- `payments` и `credit_ledger` созданы миграцией 0001, код их не читает и не пишет
  ([models.py](../../app/modules/billing/infrastructure/models.py)). Суммы в USD,
  `Numeric(12, 6)`.
- `payments`: `provider`, `provider_checkout_id`, `provider_payment_id`,
  `amount_usd`, `status` (`pending | paid | failed | expired`), `paid_at`; уникальны
  пары `(provider, provider_checkout_id)` и `(provider, provider_payment_id)`.
- `credit_ledger`: виды `top_up | usage_debit | adjustment`; `usage_event_id` и
  `payment_id` уникальны (частичные индексы). CHECK: `top_up` только с
  `amount_usd > 0` и `payment_id`, `usage_debit` только с `amount_usd < 0` и
  `usage_event_id`.
- `usage_events.cost_usd` пишется после каждого вызова LLM своей короткой
  транзакцией и переживает откат прогона (AGENTS.md, исключение для
  `SqlAlchemyUsageLedger.record`). `run_id` NOT NULL.
- Лимит стоимости прогона: fast $0.50, deep $3 на все попытки, проверка до каждого
  вызова ([PIPELINE_SPEC §4.5](../PIPELINE_SPEC.md#45-лимиты-вызовов-и-стоимости)).
- `budget_paused`: Run `skipped` при claim, если остаток дневного бюджета меньше
  лимита fast. `workspaces.daily_budget_usd = 0` значит «лимит не задан»
  (`handle_review_run.py`, SD §11).
- Членство в workspace: `github_user_workspace_access`, пересчитывается из GitHub
  при каждом входе (`LinkGitHubInstallations`, `revoke_unlisted`). Ролей нет.
- Access JWT живёт 15 минут (`ACCESS_TOKEN_LIFETIME`), несёт список Workspace
  (SD §6.5).
- Payload вебхуков `installation` хранится в `webhook_events` 30 дней после
  завершения квитанции (SD §13).

## 2. Решение кратко

- Свой предоплаченный баланс в USD в `credit_ledger` остаётся источником правды.
  Stripe принимает платежи и ведёт подписки. Stripe Billing Credits не используем
  (§10.2).
- Клиент платит за ревью, а не за места. Вся команда workspace бесплатна.
- Цена ревью фиксирована по тарифу и движку. Расход LLM считаем внутри и не
  показываем клиенту.
- Тарифы: Pay as you go, Starter $19/мес, Pro $49/мес.
- Нулевой баланс блокирует новые прогоны с причиной `balance_exhausted`.
- Роли продукта Owner, Admin, Billing, Member поверх доступа GitHub. Роль не в JWT,
  проверяется в БД.
- Налоги: Stripe Tax, цены включают НДС и одинаковы для всех. Бизнес из другой
  страны ЕС с VAT ID платит ту же сумму с НДС 0 (reverse charge), бизнес из
  Германии платит с немецким НДС.

## 3. Деньги

| Показ клиенту | до цента; цена единицы тарифа до десятой доли цента ($0.136); хранимое значение в 6 знаках (§3.2) |

### 3.2. Цена за ревью (изменение D1)

D1 говорит «расход LLM × наценка». ADR меняет D1, изменение принято техлидом в
ревью этого PR: **клиент платит фиксированную цену за ревью** по своему тарифу и
движку (§4). Расход каждого прогона по `usage_events.cost_usd` и его доля в цене
считаются и логируются внутри, для сверки и пересчёта цен. Причина: клиент видит
цену до запуска, сумма не зависит от провайдера и курса EUR, а пороги расхода
(§8.2) ниже цены прогона с НДС на любом тарифе.

Цена прогона `P`:

```
P = цена_движка(тариф, движок) × множитель
цена_движка = цена_единицы(тариф) × единиц_движка   (fast 1, deep 5)
множитель = 1 + надбавка_большого_PR
```

Два термина: **цена единицы** это цена одного fast-ревью на тарифе, **цена
движка** это цена ревью выбранным движком с множителем 1 (fast: цена единицы,
deep: 5 цен единицы).

- `цена_единицы`: §4.1. Хранится как цена тарифа, делённая на число ревью в пакете,
  с округлением вниз до 6 знаков: PAYG $0.200000, Starter $0.135714 (19/140), Pro
  $0.116666 (49/420). Так 140 и 420 ревью целиком помещаются в грант $19 и $49
  (остаток $0.00004 и $0.00028 истекает с грантом). Клиенту показывается
  округлённая цена $0.136 и $0.117 (§3.1).
- Надбавка: +1 к множителю за каждые начатые 1000 строк сверх 1000 (§4.2).
- Тариф и цена движка фиксируются при первом claim. Множитель и признак
  summary-only известны только после загрузки и фильтрации diff (`vcs.fetch_diff`,
  PIPELINE_SPEC §2), поэтому `P` фиксируется там и дальше не меняется, кроме
  деградации (§3.3). Все три значения хранятся в строке удержания run (§5.2):
  `engine_price_usd` (цена движка), `multiplier`, `price_usd` (`P`); порог
  расхода, доля 25% и задача §10.6 читают их оттуда.

### 3.3. Момент и формула списания

- **Гейт 1, claim** (T4/T5): доступный для движка остаток (§5.2) не меньше цены
  движка (множитель 1). Тогда в той же транзакции claim пишется удержание на цену
  движка (§5.2). Иначе `skipped`, `balance_exhausted` (§8). Строк PR на этом шаге
  ещё нет.
- **Повторный claim** того же run (T9, T12 возвращают его в `queued`, T4 берёт
  снова, PIPELINE_SPEC §1): удержание уже есть, новое не пишется. Гейт 1 считается
  пройденным, своё удержание run из доступного остатка не вычитается. `P`, цена
  движка и множитель берутся из строки удержания. Если снимок diff сохранён и
  `vcs.fetch_diff` не идёт, гейт 2 не повторяется: удержание уже поднято до `P`.
- **Повторный claim после списаний**, если он заканчивается `skipped` или
  `cancelled`: итог считается по §3.4 для `cancelled` (уже списанное остаётся, доплаты нет),
  удержание снимается.
- **Гейт 2, после `vcs.fetch_diff`**, до первого вызова LLM: известны множитель и
  summary-only. Если по классификации diff (PIPELINE_SPEC §2) run не вызовет
  модель (summary-only, T19 `no_changes` / `all_changes_ignored`, backend none):
  `P = 0`, удержание снимается, гейт пройден, отказа по балансу или дню нет даже
  на большом PR. Иначе
  доступный остаток и остаток дня (§8.1) вместе с удержанием этого run не меньше
  `P`: удержание поднимается до `P`. Если не хватает, удержание снимается и
  `running → skipped` с 0 вызовов LLM, по образцу T19: `error_code =
  balance_exhausted` при нехватке баланса, `budget_paused` при нехватке остатка дня.
  Переход добавляется в PIPELINE_SPEC §1 вместе с #371.
- **После каждого вызова LLM** пишется списание, связанное с `usage_event_id`
  этого вызова: `max(0, min(P × 25%, P - уже_списано_по_run))`. Доля не зависит от расхода
  вызова, поэтому сумма не раскрывает расход. Распределение по грантам: §5.1.
  Строка с нулевой суммой не пишется: после четвёртого вызова и для доплаты, когда
  уже списано `P`, строк нет.
- **При успехе** (T14 `succeeded`) пишется доплата до `P` (`run_settlement`).
  Повторные попытки внутри run цену не увеличивают.
- **Run без вызовов LLM бесплатен.** Правило задаётся через вызовы, а не через
  итог: если у run нет ни одной строки `usage_events`, при итоге `P = 0`,
  `run_settlement` не пишется, удержание снимается. Это покрывает summary-only,
  backend none и `skipped` (§3.4).
- **Деградация deep → fast** (PIPELINE_SPEC §5.3): с момента деградации `P`
  пересчитывается по цене fast с тем же множителем, порог расхода тоже берётся для
  fast и считается только по расходу после деградации (§8.2): расход deep до неё
  первый fast-вызов не останавливает. Если по run уже списано больше нового `P`, новые списания за вызов
  дают 0 (формула выше ограничена нулём), а разница зависит от итога:
  - `succeeded`: разница возвращается строками `adjustment` с причиной
    `engine_fallback` в те же гранты, итог ровно новый `P`;
  - `cancelled` и `skipped` после списаний: так же, разница сверх нового `P`
    возвращается, клиент платит не больше цены fast;
  - `failed`: разница не пишется, сторно возвращает каждую строку списания (§3.4),
    итог 0.
  Клиент платит цену fast.
- **Второе узкое исключение** из правила «commit делает только use case», рядом с
  `SqlAlchemyUsageLedger.record`, одним текстом в `AGENTS.md`,
  `.agents/rules/backend.md` и BACKEND_ARCHITECTURE (§15): единственная точка
  записи модуля `billing` пишет состояние списаний run своей короткой транзакцией,
  без сетевых вызовов внутри. В неё входят строки run в `credit_ledger`
  (`usage_debit`, `run_settlement`, `adjustment` сторно и деградации, `expiry`
  возвращённой суммы) и изменение удержания run в `balance_holds` (§5.2). Запись
  идёт сразу после `usage_events`, после commit перехода run в конечное состояние
  или позже из задачи досписания §10.6, идемпотентно по ключам §10.4
  (`(usage_event_id, grant_id)`, `(run_id, grant_id)`, `reversal_of_id`,
  `balance_holds.run_id`), чтобы откат основного run её не терял, а повтор не
  дублировал. Истечение грантов, основное и отложенное до снятия удержания (ключ
  `(grant_id, hold_run_id)`), пишет часовая задача истечения §10.6 обычным use
  case, в исключение оно не входит.

### 3.4. Неудачный и отменённый прогон

| Итог run | Что списано |
|---|---|
| `succeeded` с хотя бы одним вызовом LLM | ровно `P` |
| любой `failed`, с любым `error_code` (ошибка LLM, таймаут, баг, verifier, `github_forbidden`, `pr_base_changed`, `llm_context_overflow` и другие) | 0: каждое списание run сторнируется строкой `adjustment` в тот же грант (§5.1) |
| `cancelled` (новый `head_sha`, PR закрыт, `POST /api/runs/{id}/cancel`) | уже списанное по §3.3, без доплаты; после деградации deep → fast не больше нового `P` |
| `skipped` без вызовов LLM (гейт 1, гейт 2, `budget_paused`) | 0 |
| `skipped` после вызовов LLM на прошлой попытке run | уже списанное, без доплаты, как `cancelled` |
| summary-only, любая из причин `diff_too_large` (в том числе PR больше 3000 строк, §4.2), `diff_inventory_incomplete`, `no_reviewable_files` (PIPELINE_SPEC §2) | 0 |
| `succeeded` без вызовов модели (backend none: 0 LLM, `findings=[]`, coverage none, PIPELINE_SPEC §2) | 0 |
| любой итог, если у run нет ни одной строки `usage_events` | 0 (§3.3) |

### 3.5. Что видит клиент

Клиент видит **списанную сумму** (`chargedUsd`) и остаток баланса, никогда не
`cost_usd`, лимиты расхода и токенов прогона. Поля `contracts/openapi.yaml` на
`main`, которые сейчас отдают клиенту расход, и решение по каждому (реализация
#310 и #371):

| Схема и поле | Где отдаётся | Решение |
|---|---|---|
| `RunUsage.costUsd` | прогон в списке и деталях | заменяется на `chargedUsd` из `credit_ledger` ([#310](https://github.com/larchanka-training/dmc-268-api-t6/issues/310)) |
| `RunBudget.costUsd`, `RunBudget.costLimitUsd`, `RunBudget.tokenLimit` | детали прогона | убираются из ответа клиенту; расход, порог и лимит токенов прогона видит только оператор |
| `MetricsTotals.costUsd` | `GET /api/metrics/summary` | заменяется на `chargedUsd` за период |
| `MetricsDay.costUsd` | `GET /api/metrics/summary`, по дням | заменяется на `chargedUsd` за день |
| шаги `llm.call` в трейсе: `usage.cost`, `usage.cost_currency` в ответе шага, `fx` в запросе шага | `GET /api/runs/{run_id}/actions`, `/actions/{index}/response` | вырезаются из ответа клиенту при отдаче шага; в БД и для оператора остаются. Токены в `usage` остаются |
| `WorkspaceDailyBudget.spentTodayUsd`, `dailyBudgetUsd` | `GET /api/metrics/summary` | считаются по списанному, а не по расходу: дневной лимит workspace ограничивает списания за день (§8.1) |

- Токены (`tokensIn`, `tokensOut`) остаются: это техническая метрика прогона, а не
  сумма в деньгах.
- `cost_usd` остаётся во внутренних метриках оператора (Prometheus, логи), не в
  API клиента.
- [ui#186](https://github.com/larchanka-training/dmc-268-ui-t6/issues/186): страницы
  «Аудит» и «Аналитика» показывают списанное, а не расход LLM.

## 4. Тарифы

### 4.1. Цены

| Тариф | Цена | Включено | Fast | Deep | Graph RAG | Репозитории |
|---|---|---|---|---|---|---|
| Pay as you go | только пополнения | - | $0.20 | $1.00 (5 единиц) | нет | без лимита |
| Starter | $19/мес | 140 ревью | $0.136 (хранится $0.135714) | 5 единиц | да | до 5 |
| Pro | $49/мес | 420 ревью | $0.117 (хранится $0.116666) | 5 единиц | да | без лимита |

- Названия тарифов финальные: Pay as you go, Starter, Pro. Enterprise вне эпика #369.
- Единица тарифа: одно fast-ревью. Deep стоит 5 единиц своего тарифа, как в PAYG
  ($1.00 = 5 × $0.20).
- Deep доступен во всех тарифах. Graph RAG только в подписке. Лимит
  репозиториев: Starter до 5, остальные без лимита.
- Сверх пакета ревью списываются с купленного баланса по цене единицы своего
  тарифа.
- Мест нет: число участников не ограничено.
- Скидка к PAYG: Starter 32%, Pro 42%.
- Отдельного тарифа для бизнеса нет: компании покупают Starter или Pro.
- Enterprise (SSO, договор, SLA): по запросу, вне эпика.

### 4.2. Надбавка за большой PR

- Строки PR: добавленные плюс удалённые строки diff после исключений политики.
- 1-1000 строк: множитель 1. Каждые начатые 1000 строк сверх 1000: +1. Пример для
  PAYG: fast на 1500 строк $0.40, deep на 2500 строк $3.00.
- Больше 3000 строк: ревью только summary без LLM, $0.

### 4.3. Подписка

- Подписка Stripe на месяц, автопродление. Смена тарифа и отмена через Customer
  Portal (§10.1).
- Включённые ревью начисляются грантом `subscription_grant` в USD ($19 и $49) по
  `invoice.paid` только для счетов с `billing_reason` = `subscription_create` или
  `subscription_cycle`. Ключ идемпотентности: id счёта
  (`payments.provider_invoice_id`, §10.4).
- Счета с другим `billing_reason` полного гранта не дают. Единственное исключение
  описано в §4.4: доплата за повышение даёт грант на оплаченную сумму. Счёт с нулевой
  суммой (`amount_paid = 0`) грант не даёт.
- Отмена действует в конце оплаченного периода; до него тариф работает.
- **Неоплата счёта подписки** (стандартный путь Stripe):
  - `invoice.payment_failed` по счёту `subscription_cycle`: подписка в статусе
    Stripe `past_due`, Stripe повторяет списание (Smart Retries). Тариф работает,
    гранта за этот счёт нет, баннер для Owner, Admin и Billing «Оплата подписки не
    прошла» с кнопкой в Customer Portal;
  - конец повторов: в настройках Stripe (Revenue recovery) задано «отменить
    подписку» и «пометить счёт как uncollectible». По `customer.subscription.deleted`
    тариф снимается, workspace переходит на PAYG и платит с баланса; остаток
    прошлого гранта живёт до своего срока (§5);
  - поздний `invoice.paid` по счёту, у которого подписка уже `canceled`: тариф не
    возвращается и `subscription_grant` не пишется; оплаченная сумма зачисляется
    грантом `top_up` (12 месяцев), чтобы деньги клиента не пропали. Вернуть тариф
    можно только новой подпиской (§4.4);
  - `invoice.paid` по счёту в `past_due` до конца повторов: обычный грант по
    `billing_reason`, подписка снова `active`.

### 4.4. Смена тарифа

| Переход | Когда действует | Деньги и гранты |
|---|---|---|
| PAYG → Starter или Pro | сразу, новая подписка | грант по `subscription_create` (§4.3) |
| Starter → Pro (повышение) | сразу | Stripe выставляет доплату за остаток периода (`proration_behavior=always_invoice`); по её `invoice.paid` (`billing_reason=subscription_update`) пишется `subscription_grant` на оплаченную сумму со сроком текущего гранта; цена единицы Pro действует с момента смены |
| Pro → Starter (понижение) | в конце оплаченного периода | до конца периода работает Pro; новый грант $19 по `subscription_cycle`; остаток гранта Pro живёт до своего срока |
| Подписка → PAYG (отмена) | в конце оплаченного периода | §4.3 |

- Customer Portal настраивается так: повышение сразу с доплатой, понижение и
  отмена в конце периода (`schedule_at_period_end`).
- **Starter при числе репозиториев больше 5.** Правило одно для любого пути в
  Starter: понижение Pro → Starter, переход PAYG → Starter и новая подписка Starter
  после отмены. До оплаты или смены страница тарифа предупреждает и даёт Owner или
  Admin выбрать 5 репозиториев. После начала Starter ревью идут только в выбранных
  5; если выбора нет, остаются 5 с последними прогонами. Остальные репозитории
  остаются подключёнными, их прогоны `skipped` с `error_code = plan_repo_limit`.
- **Коды отказа по лимитам тарифа.** Сервер проверяет каждый лимит сам:

| Код | Когда |
|---|---|
| `plan_repo_limit` | Starter: включение 6-го репозитория (ответ API) или прогон в репозитории сверх лимита (`skipped`) |
| `plan_graph_rag_unavailable` | PAYG: включение Graph RAG (ответ API). Если RAG уже включён, а тариф стал PAYG, ревью идёт без RAG, отметка в трейсе с этим кодом |
| `balance_exhausted` | остаток меньше цены (§3.3, §8.1) |

## 5. Кредиты: виды, порядок и сроки

| Источник | Вид в `credit_ledger` | Срок | На что |
|---|---|---|---|
| Подписка | `subscription_grant` (новый) | до конца периода счёта плюс 1 месяц (ниже) | fast и deep |
| Бонус | `promo` (новый) | 30 дней | только fast |
| Пополнение | `top_up` | 12 месяцев | fast и deep |

- **Порядок списания:** подписка, затем бонус, затем купленные. Внутри источника
  раньше истекающий грант первым.
- **Точка отсчёта срока.** `expires_at` гранта подписки = конец периода позиции
  подписки в счёте (`invoice.lines[].period.end`) плюс 1 месяц. Доплата за
  повышение (§4.4) получает `expires_at` текущего гранта подписки. Поздний
  `invoice.paid` по отменённой подписке даёт `top_up` со сроком 12 месяцев от
  оплаты (§4.3). `top_up` и `promo` считаются от момента начисления.
- **Перенос остатка подписки:** неиспользованный `subscription_grant` живёт ещё один
  месяц после своего цикла и складывается с грантом следующего цикла; по порядку
  выше первым списывается старый. Дальше не переносится: остаток сгорает строкой
  `expiry`. При отмене подписки и переходе на PAYG (§4.3) уже выданный грант
  доживает до своего срока: он оплачен.
- Истечение пишет строку `expiry` (новый вид) на свободный остаток гранта. Пишет
  её leader-задача истечения раз в час (§10.6) обычным use case, не запрос
  клиента и не исключение короткой транзакции (§3.3).
- **Возврат денег** (`charge.refunded`, в том числе частичный и отказ в 14 дней,
  §9) пишет строку `refund` (новый вид) на каждый объект возврата Stripe
  (`re_...`): ключ `provider_refund_id`, сумма возврата со знаком минус, в грант
  этого платежа (`top_up` или `subscription_grant`). Сумма всех `refund` по гранту
  не больше суммы гранта. Строка `refund` не заполняет `payment_id`, поэтому не
  конфликтует с грантом платежа (§10.4). Доплата при успехе пишет
  `run_settlement` (новый вид).
- **Спор по платежу** (chargeback): по `charge.dispute.created` пишется строка
  `adjustment` с причиной `dispute` на сумму спора, в грант этого платежа: `top_up`
  для пополнения и авто-пополнения, `subscription_grant` для счёта подписки, даже
  если остаток уйдёт в минус. Выигранный спор (`charge.dispute.closed`,
  `status=won`) пишет обратную строку `adjustment` с `reversal_of_id` на неё.
  Проигранный ничего не добавляет.
- **Возврат и спор на истёкшем гранте.** Строка `refund` или спора всегда пишется
  на полную сумму в грант платежа: так она сходится со Stripe (§10.5). Если по
  гранту уже есть `expiry`, в той же транзакции пишется `adjustment` с причиной
  `expired_offset` на `min(сумма строки, сумма expiry по гранту ещё без offset)`,
  со ссылкой `offset_of_id` на строку возврата или спора. Минус остаётся только на
  потраченную часть: сгоревшее уже не было у клиента. Выигранный спор пишет
  обратную строку и к самому спору, и к его `expired_offset` (`reversal_of_id`), и
  грант возвращается к прежнему остатку 0: второй `expiry` не нужен.
- **Долг** это отрицательный остаток гранта (§5.2). Он входит в доступный остаток
  для любого движка, даже если грант истёк, и гасится первым следующим грантом
  `top_up` или `subscription_grant`: обработчик гранта в той же транзакции пишет
  пару `adjustment` с причиной `debt_repayment`, минус на новый грант и плюс на
  грант с долгом, на `min(долг, сумма нового гранта)`. Бонус `promo` долг не
  гасит: он только для fast и не деньги клиента.
- DDL новых видов и ссылки на грант: #371 и #372.

### 5.1. Распределение списания по грантам

- Каждая строка списания ссылается на один грант (`grant_id`). Если сумма
  списания больше остатка текущего гранта, пишется несколько строк: по одной на
  каждый грант в порядке выше, до полной суммы.
- Уникальность: `(usage_event_id, grant_id)` для списаний за вызов и
  `(run_id, grant_id)` для `run_settlement`. Частичный уникальный индекс
  `uq_credit_ledger_usage_event` только по `usage_event_id` в #371 заменяется
  составным. Идемпотентность записи сохраняется: строки одного списания пишутся
  одной транзакцией, повтор находит их по `usage_event_id` (или `run_id`) и ничего
  не пишет.
- **Сторно** (неудачный run, деградация) пишет строку `adjustment` на каждую строку
  списания run, в тот же грант и на ту же сумму. Возврат сохраняет срок и движки
  исходного гранта: бонус возвращается бонусом, только для fast. Если грант уже
  истёк, сразу за сторно пишется `expiry` на возвращённую сумму.
- Остаток гранта: сумма гранта плюс все строки, которые на него ссылаются.

### 5.2. Удержание на время прогона

Параллельные прогоны не могут потратить один и тот же остаток: каждый run держит
удержание, и следующий claim видит уже уменьшенный остаток.

- Таблица `balance_holds` (новая, #371): `run_id` (уникален), `workspace_id`,
  `engine`, `amount_usd`, `engine_price_usd`, `multiplier`, `price_usd` (`P`, пусто до
  гейта 2), `status` (`active | released`), `created_at`, `released_at`. Одно
  удержание на run на все его попытки: повторный claim его не создаёт (§3.3).
- **Доступный остаток** для движка = долг workspace (отрицательные остатки
  грантов, §5) плюс сумма по грантам, которые подходят движку
  (§5) и чей срок ещё не наступил, остатка гранта минус его часть под активными
  удержаниями других run (распределение ниже). Вычитаются только удержания,
  которые распределение относит к этим грантам: fast-удержание на бонусе остаток
  для deep не уменьшает. Пример: бонус $5, `top_up` $1, fast-удержание $0.20 лежит
  на бонусе: для deep доступно $1.00. Удержание на гранте с наступившим сроком тоже
  не вычитается из других грантов. Грант с наступившим сроком не считается сразу,
  даже если строка `expiry` ещё не написана: окна до часового прохода нет. Гейты
  §3.3 смотрят именно на него; `budget_paused` смотрит на остаток дня (§8.1),
  который своё удержание run исключает так же.
- Claim пишет удержание в своей транзакции под блокировкой строки workspace
  (`SELECT ... FOR UPDATE`), поэтому два claim одного workspace проверяют остаток
  по очереди. Гейт 2 поднимает удержание до `P` так же.
- Каждое списание за вызов уменьшает удержание на ту же сумму в той же короткой
  транзакции: удержание всегда равно `P` минус уже списанное по run.
- Удержание снимается (`released`) в транзакции итогового списания или сторно
  run: `run_settlement` при `succeeded`, сторно при `failed`, конец списаний при
  `cancelled` и `skipped`. Повтор находит `released` и ничего не делает.
- Если воркер не дожил до итога (T13 `lease_expired` и другие переходы
  реконсилера), удержание снимает задача досписания §10.6.
- **Распределение удержаний по грантам** не хранится, а считается: активные
  удержания workspace по `created_at` распределяются по грантам в порядке §5
  (deep-удержание бонус не берёт), как распределялось бы их списание. Так
  определяется часть гранта «под удержаниями».
- Списания run с активным удержанием могут брать грант, срок которого наступил
  после записи удержания (`expires_at > balance_holds.created_at`): эта часть уже
  удержана для run.
- `expiry` (§5) списывает только свободную часть гранта: остаток минус часть под
  удержаниями. Часть под удержанием истекает после его снятия: её пишет та же
  задача истечения на следующем часовом проходе после `released`, отдельной
  строкой `expiry` на остаток этой части с ключом `(grant_id, hold_run_id)`
  (§10.4).
- **Блокировка.** Задача истечения пишет `expiry` под той же блокировкой строки
  workspace (`SELECT ... FOR UPDATE`), что claim и гейт 2, поэтому не может
  истечь сумму, которую параллельный claim уже удержал.
- **Овердрафт:** 0. Удержание покрывает полную цену run, сторно и деградация её
  только уменьшают, а истечение не трогает удержанную часть. Отрицательный остаток
  возможен только после возврата денег (`refund`) или спора (`adjustment` с
  причиной `dispute`, §5) на уже потраченную часть платежа: на истёкшем гранте
  сгоревшее в минус не идёт. Он гасится первым следующим грантом `top_up` или
  `subscription_grant` (§5).

## 6. Пополнение и авто-пополнение

### 6.1. Пополнение

- Любая сумма от $10 до $500 в целых долларах, Stripe Checkout `mode=payment`.
- Грант `top_up` пишется по `checkout.session.completed` со статусом оплаты `paid`.
  Налог и счёт: §9. В `metadata` сессии и её PaymentIntent
  (`payment_intent_data.metadata`) пишутся `workspace_id` и `source=checkout`.
- Карту можно сохранить двумя путями, оба уже в первой версии:
  - **кнопка «Привязать карту»** на экране «Баланс и тариф»: Checkout `mode=setup`
    (SetupIntent `usage=off_session`), без списания. Событие `setup_intent.succeeded`.
    В `setup_intent_data.metadata` сессии пишутся `workspace_id`, `github_user_id`
    (кто нажал кнопку) и `source=link_card`. Только этот путь даёт бонус (§7);
  - **при пополнении**, если клиент отметил «Сохранить карту» на нашей странице до
    Checkout (§9, п. 4): `payment_intent_data.setup_future_usage=off_session`. Карта
    сохраняется вместе с оплатой; событие `checkout.session.completed`, карта берётся
    из `payment_method` его PaymentIntent. Бонуса этот путь не даёт.
- Сохранённая карта нужна авто-пополнению (§6.2), чтобы не вводить её повторно.
- **Карта авто-пополнения одна** на workspace: её выбирают на экране включения
  (§9, п. 3), id хранится в настройках авто-пополнения. Другие сохранённые карты
  авто-пополнение не списывает.

### 6.2. Авто-пополнение

| Параметр | Значение |
|---|---|
| По умолчанию | выключено |
| Кто включает | Owner, Admin или Billing; порог и сумму задаёт пользователь |
| Порог | от $5 до $100 и строго меньше суммы пополнения: после платежа остаток всегда выше порога; настройки с порогом не меньше суммы не сохраняются |
| Когда срабатывает | по уровню: доступный остаток для fast (§5.2: все действующие гранты, включая подписку и бонус, минус удержания; тот же, что в баннере низкого баланса §8.1) ниже порога, авто-пополнение включено, нет попытки в `pending` и остаток потолка месяца не меньше суммы. Проверка идёт после commit каждого списания (вызов Stripe вне транзакции, §6.2 шаги), после `refund` и спора, при `skipped` с `balance_exhausted`, при включении (в том числе повторном после отказа карты) и на каждом проходе задачи §10.6 (раз в 5 минут, в том числе в начале месяца UTC), поэтому сбой после commit списания проверку не теряет. Защита от серии ниже |
| Сумма | от $10 до $500, как обычное пополнение, и не больше месячного потолка: настройки с суммой больше потолка не сохраняются |
| Месячный потолок | по умолчанию $200 за календарный месяц UTC; пользователь меняет в пределах $10-$500 |
| Платёж | разовый счёт Stripe Invoicing: позиция на сумму с `tax_behavior=inclusive` (одна брутто-цена, §9), `automatic_tax[enabled]=true`, `collection_method=charge_automatically`, карта авто-пополнения как `default_payment_method`, `metadata.source=auto_recharge`, `metadata.payment_id`; шаги и ключи ниже |
| Карта | одна карта авто-пополнения (§6.1). Сменить её можно только на нашем экране включения, с новым согласием (§9, п. 3). Смена карты по умолчанию в Customer Portal её не меняет; удаление этой карты (`payment_method.detached`) выключает авто-пополнение до нового согласия |
| Отказ карты | авто-пополнение выключается; баннер в ui (ниже) |
| Требуется 3-D Secure | то же: выключается, баннер; клиент платит вручную через Checkout |
| Потолок достигнут | попытка не идёт, если сумма больше остатка потолка месяца; до конца месяца не срабатывает, отметка в ui; в начале месяца проверка по уровню запускает его снова |

- **Шаги платежа.** Счёт, созданный через API, стоит в `draft`, а
  автоматическое проведение Stripe ждёт час, поэтому все шаги явные:
  1. В короткой транзакции БД пишется строка `payments` (`source=auto_recharge`,
     `status=pending`, сумма); её id и есть id попытки.
  2. Вне транзакции: счёт (`auto_advance=false`), позиция счёта на него, затем
     `POST /v1/invoices/{id}/finalize`, затем `POST /v1/invoices/{id}/pay` с
     `off_session=true`. У каждого вызова свой `Idempotency-Key` из id попытки и
     имени шага: `ar-<payment_id>-invoice`, `-item`, `-finalize`, `-pay`. Повтор
     шага с тем же ключом и теми же параметрами Stripe отвечает прежним объектом.
  3. В строку `payments` пишутся `provider_invoice_id` (`in_...`) и
     `provider_payment_id` PaymentIntent счёта.
  4. Деньги только по вебхуку: `invoice.paid` даёт `payments.status=paid` и грант
     `top_up` с этим `payment_id`; `invoice.payment_failed` и
     `invoice.payment_action_required` дают `status=failed`, выключают
     авто-пополнение, и счёт аннулируется (`POST /v1/invoices/{id}/void`, ключ
     `ar-<payment_id>-void`): оплатить его позже нельзя. Если `invoice.paid` всё же
     пришёл на строку `failed` (гонка с `void`), деньги зачисляются: строка
     становится `paid`, пишется грант `top_up`, авто-пополнение остаётся
     выключенным.
- **Попытка без счёта.** Если процесс упал после шага 1 и `provider_invoice_id` не
  записан, строка `pending` держит индекс одной попытки. Её подхватывает задача
  досписания §10.6 (раз в 5 минут, строки старше 5 минут): повторяет шаги 2-3 с
  теми же ключами, Stripe вернёт уже созданные объекты. Ключи живут у Stripe
  24 часа; если попытка не завершилась за 23 часа, задача аннулирует счёт, если он
  есть, ставит `failed` с причиной `stale_attempt`, и на следующем проходе
  проверка по уровню создаёт новую попытку. Строка `pending` со счётом старше
  часа сверяется с Stripe той же задачей.
- **Нет адреса для налога.** Если `finalize` отвечает HTTP 400
  `customer_tax_location_invalid` (у Customer нет действительного адреса, например
  карта привязана до того, как Checkout стал собирать адрес), черновик счёта
  удаляется, строка `payments` становится `failed` с этой причиной,
  авто-пополнение выключается, баннер «Укажите адрес для счёта: пополните вручную»
  (ручное пополнение через Checkout соберёт адрес); включить снова можно новым
  согласием.
- **Защита от серии.** Если после оплаченной попытки остаток всё ещё ниже порога
  (например, долг после возврата больше суммы пополнения), авто-пополнение
  ставится на паузу с баннером «Сумма авто-пополнения меньше долга, пополните
  вручную»; пауза снимается ручным пополнением или новым согласием. Спор по
  платежу авто-пополнение выключает (§10.3).
- **Одна попытка на workspace:** частичный уникальный индекс `payments
  (workspace_id) WHERE source = 'auto_recharge' AND status = 'pending'`. Пока
  попытка не закончилась, новая не создаётся.
- Месячный потолок считается по строкам `payments` с `source=auto_recharge` в
  статусах `pending` и `paid` за календарный месяц UTC.
- **Как клиент узнаёт об отказе.** Писем мы не шлём: своей рассылки в эпике нет
  (#369), а email пользователей у нас нет (вход через GitHub App). Вместо письма:
  - баннер на всех страницах workspace для Owner, Admin и Billing: «Авто-пополнение
    выключено: карта отклонена» (или «нужно подтверждение банка») и кнопка
    «Пополнить»; баннер скрывается после успешного пополнения или повторного
    включения;

    причина и дата последнего отказа, остаток месячного потолка.
- Пополнения баланса по порогу в Stripe Billing в документации не найдено, поэтому
  порог проверяем мы.
- Реализация отдельной задачей позже, вне #371: [#513](https://github.com/larchanka-training/dmc-268-api-t6/issues/513). Карта сохраняется уже в
  первой версии (§6.1).

## 7. Бонус новым

- **Фича-флаг** `billing_signup_bonus`, по умолчанию выключен. Пока флаг выключен,
  бонус не начисляется и не обещается в ui. Включает команда.
- **Когда начисляется:** $5 только после привязки карты кнопкой «Привязать карту»
  (Checkout `mode=setup`, §6.1), по `setup_intent.succeeded`. Получателя и
  workspace обработчик берёт из `metadata` SetupIntent; без `source=link_card`,
  `workspace_id` и `github_user_id` бонуса нет, даже если флаг включён: другой
  SetupIntent того же Customer бонус не даёт. На этом пути карта не
  списывается. Карта, сохранённая при пополнении, бонуса не даёт: так у бонуса одно
  событие и одно место в ui.
- **Кому:** GitHub-пользователю, который нажал кнопку (роль Owner, Admin или
  Billing, §11.1). Не на установку и не на организацию: организаций можно создать
  сколько угодно, а id установки меняется при переустановке.
- **Ограничения:**
  - один бонус на GitHub user id: повторная установка бонус не даёт;
  - один бонус на workspace: второй участник со своей картой бонус не получает;
  - один бонус на карту: по `card.fingerprint` из Stripe, та же карта на другом
    аккаунте бонус не даёт;
  - аккаунту GitHub больше 30 дней (`created_at` из GitHub API).
- Только fast, срок 30 дней. Пишется грантом `promo` на этот workspace. Факт
  выдачи хранится по GitHub user id, workspace и fingerprint карты.
- Реализация в #371.

## 8. Нулевой баланс и лимиты прогона

### 8.1. Нулевой баланс

- **Флаг оплаты.** Всё ниже действует, только когда включён `billing_enforcement`;
  пока он выключен, ревью бесплатны, как на `main` (§16).
- **Новые прогоны:** два гейта §3.3. При claim доступный остаток для движка (§5.2)
  меньше цены движка: Run `skipped`, `error_code = balance_exhausted`; проверка
  идёт после `budget_paused`. После `vcs.fetch_diff` остаток вместе с удержанием
  run меньше `P`: `running → skipped` с тем же кодом.
- **Deep при балансе только на fast.** Deep-Run при claim, если доступный остаток
  для deep меньше цены движка deep, но остаток для fast не меньше цены единицы
  (например, остался только бонус, он только для fast, §5): Run идёт как fast по
  цене fast, как деградация по дневному бюджету ниже. В summary PR: «На deep не
  хватило баланса, выполнено fast-ревью» и ссылка на пополнение. Если не хватает и
  на fast: `balance_exhausted`. До фазы 3 API принимает только fast
  (PIPELINE_SPEC §5.3), правило нужно для #371 заранее.
- **Что видит клиент** (GitHub): check-run `completed/skipped` с текстом «Баланс
  исчерпан, ревью не запущено» и ссылкой на пополнение; комментарий в PR с той же
  ссылкой не чаще раза в сутки на PR; причина в ui. Время последнего такого
  комментария хранится в `code_changes.balance_notice_at` (новое поле, #371).
  Для GitLab и Bitbucket в ADR пока только причина в ui; их поверхность (§19)
  решается до #371.
- **Баннер низкого баланса** для Owner, Admin и Billing на всех страницах
  workspace: доступный остаток (§5.2) меньше 10 цен единицы тарифа (PAYG $2.00);
  при остатке меньше цены единицы текст «Баланс исчерпан». Кнопка «Пополнить».
  Скрывается, когда остаток снова не меньше порога.
- **Начатые прогоны** доделываются: их цена уже удержана (§5.2). Параллельные
  прогоны не уводят остаток в минус, овердрафт 0.
- **`daily_budget_usd`** остаётся отдельным дневным лимитом workspace, 0 значит
  «лимита нет». С #371 он считается по списанному за день, а не по расходу LLM
  (§3.5): клиент задаёт лимит в тех же деньгах, которые платит. Нулевой баланс и
  `budget_paused` не смешиваются: разные проверки, разные коды.
- **С чем сравнивается остаток дня.** Лимиты fast $0.50 и deep $3 больше не
  участвуют (§8.2). Оба правила ниже действуют только при `daily_budget_usd > 0`,
  как условие `snapshot.daily_budget_usd > 0` на `main`
  (`handle_review_run.py`); при 0 остаток дня не считается и `budget_paused` не
  ставится. **Остаток дня** = `daily_budget_usd` минус списанное за день минус
  активные удержания workspace, кроме удержания этого же run (как доступный
  остаток, §5.2). Это единственное определение; повторный claim уже оплаченного
  run своё удержание не видит и `budget_paused` из-за него не получает. При claim:
  - остаток дня меньше цены единицы тарифа: `skipped`, `budget_paused`;
  - deep-Run и остаток дня меньше цены движка deep (5 единиц), но не меньше цены
    единицы: Run идёт как fast (деградация PIPELINE_SPEC §5.3), цена и
    порог fast (§3.3, §8.2).
  Пример: PAYG, остаток дня $0.40: fast за $0.20 запускается, deep за $1.00
  деградирует в fast.
- **Гейт 2 сверяет и остаток дня** (тоже только при `daily_budget_usd > 0`). После
  `vcs.fetch_diff`, когда удержание поднимается до `P`, остаток дня вместе с
  удержанием этого run должен быть не меньше `P`. Иначе удержание снимается и
  `running → skipped` с `budget_paused`, 0 вызовов LLM. Пример: PAYG fast, остаток
  дня $0.20, PR на 2500 строк (`P` = $0.60): claim проходит, гейт 2 даёт
  `budget_paused`. Дневной лимит не превышается ни на один прогон.

### 8.2. Пороги расхода прогона

Пороги заменяют лимиты PIPELINE_SPEC §4.5 и SD §13 (fast $0.50, deep $3) при
реализации #371. Порог одинаков на всех тарифах, чтобы скидка подписки не
меняла качество ревью, и ниже самой низкой цены ревью с НДС (Pro по хранимой
цене движка: fast $0.116666, deep $0.583330). Порог сравнивается с брутто-ценой,
а не с выручкой:

| Движок | Порог расхода на прогон |
|---|---|
| fast | $0.11 × множитель |
| deep | $0.55 × множитель |

- Множитель тот же, что в цене (§3.2): большой PR получает порог больше в той же
  пропорции, что и цену.
- Порог передаётся в существующую проверку шлюза перед каждым вызовом
  (`run_cost_limit_usd`, PIPELINE_SPEC §4.5) как лимит этого прогона, а не как
  константа движка. До гейта 2 (§3.3) вызовов LLM нет, поэтому множитель к первому
  вызову уже известен.
- При деградации deep → fast с этого момента действует порог fast, и против него
  считается только расход после деградации: лимит прогона в шлюзе становится
  `расход до деградации + $0.11 × множитель`. Шлюз сейчас считает `spent` по всему
  run и сравнивает с лимитом текущего движка (`gateway.py`, PIPELINE_SPEC §4.5),
  поэтому без этой поправки первый fast-вызов после дорогого deep дал бы
  `BUDGET_EXCEEDED` и `failed` с итогом 0. Расход deep до деградации может
  превысить цену fast; этот редкий случай сбоя deep мы берём на себя, клиент
  платит цену fast (§3.3).
- Без деградации расход прогона на пороге остаётся меньше его цены с НДС на любом
  тарифе. **Выручка без НДС может быть ниже порога.** У Pro это так при любой ставке
  НДС больше 6,06% (0.116666 / 0.11 = 1.0606 и 0.583330 / 0.55 = 1.0606), то есть
  почти при любой ставке ЕС: при 19% выручка fast $0.098 и deep $0.490 против
  порогов $0.11 и $0.55. Starter уходит ниже порога при ставке от 23,4% (0.135714 /
  0.11 = 1.2338), PAYG ни при какой ставке ЕС. При reverse charge выручка равна
  цене. Этот случай техлид принял решением от 2026-11-06: пороги и цены не меняются,
  доля таких прогонов проверяется на сверке цен через 30 дней (ниже).
- Расход считается по цене фактического провайдера вызова, а не самого дешёвого.
- Модель и провайдер выбираются по eval
  [#512](https://github.com/larchanka-training/dmc-268-api-t6/issues/512) в пределах
  этих порогов. Если ни одна пригодная модель не укладывается, цены пересчитываются
  новым ADR, пороги не поднимаются молча.
- Через 30 дней после запуска на staging цены сверяются по фактическим
  `usage_events`.

## 9. Клиенты B2B и B2C, налоги и согласия

| Что | Решение |
|---|---|
| Охват | в эпике оба типа: бизнес с VAT ID и потребитель (D6), на одних тарифах |
| Тип клиента | бизнес: в Checkout введён VAT ID (`tax_id_collection[enabled]=true`); иначе потребитель |
| Расчёт налога | Stripe Tax (`automatic_tax[enabled]=true`), регистрации моковой GmbH в sandbox. Checkout считает налог сам; авто-пополнение идёт разовым счётом Invoicing с тем же `automatic_tax`, поэтому налог и reverse charge те же (§6.2) |
| Счёт клиенту | пополнение через Checkout: `invoice_creation[enabled]=true`, Stripe выставляет счёт с НДС; авто-пополнение: тот же счёт Invoicing. Счета видны в Customer Portal, Stripe отправляет их на email Customer, введённый в Checkout |
| Цены | `tax_behavior=inclusive`, одна брутто-цена для всех (решение техлида от 2026-11-06): потребитель платит указанную цену с НДС; бизнес платит ту же сумму |
| Reverse charge | только трансграничный B2B в ЕС: VAT ID страны ЕС, отличной от Германии (страна моковой GmbH, §12). Сумма та же, НДС 0, в счёте пометка reverse charge |
| Немецкий VAT ID | продажа внутри страны: Stripe Tax начисляет немецкий НДС, reverse charge не применяется; сумма та же, НДС внутри неё, VAT ID печатается в счёте |
| Вне ЕС | налог по правилам Stripe Tax для страны клиента, сумма та же |
| Проверка VAT ID | Stripe проверяет формат сразу и асинхронно по базе ЕС (`customer.tax_id.updated`); reverse charge Stripe Tax применяет по формату номера и стране |
| Страница цен | до Checkout тип клиента неизвестен, поэтому показывается одна цена с пометкой «включая НДС» и сноска: «Компании из других стран ЕС с действительным VAT ID платят ту же сумму, НДС не начисляется (reverse charge)». Отдельной нетто-цены нет |
| Право отказа 14 дней | только потребителям; при немедленном начале услуги право теряется на потраченную часть |
| Отказ в 14 дней | возвращаем неиспользованный остаток пополнения; по подписке оплату минус ревью, уже сделанные по цене единицы тарифа |

**Согласия перед оплатой.** Checkout умеет один обязательный чекбокс
(`consent_collection[terms_of_service]=required`) с текстом до 1200 символов, а
`custom_fields` бывают только text, numeric и dropdown. Поэтому:

1. На нашей странице до перехода в Checkout: цена, НДС, период, автопродление,
   способ отмены и чекбокс «Прошу начать услугу сразу и понимаю, что теряю право
   отказа на использованную часть». Без чекбокса кнопка оплаты не активна. Время и
   версия текста сохраняются в нашей БД.
2. В Checkout: чекбокс условий (`terms_of_service=required`) с
   `custom_text.terms_of_service_acceptance`, ссылками на Terms и Refund Policy.
3. **Включение авто-пополнения** (настройки, Checkout там нет): отдельный экран с
   условиями: порог, сумма, месячный потолок, карта (последние 4 цифры), что
   списание идёт без участия клиента, и как отключить (переключатель на экране
   «Баланс и тариф» в любой момент). Чекбокс «Разрешаю списывать эту сумму с карты,
   когда баланс ниже порога, не больше потолка в месяц». Рядом пояснение: баланс
   здесь это все доступные кредиты, включая ревью подписки и бонус (§6.2), поэтому
   у подписчика авто-пополнение срабатывает только после пакета. Без чекбокса включить
   нельзя. Сохраняются GitHub user id, параметры, карта, версия текста и время.
   Изменение порога, суммы, потолка или карты требует нового согласия: смена карты
   авто-пополнения идёт только на этом экране, а её удаление в Customer Portal
   выключает авто-пополнение (§10.3).
   Согласие держится на человеке: если давший его пользователь теряет право
   включать авто-пополнение (снята роль Admin или Billing, удалён из workspace,
   снята роль Owner, §11.2), авто-пополнение выключается в той же транзакции,
   что и смена роли, и баннер «Авто-пополнение выключено: у включившего больше
   нет прав» показывается Owner, Admin и Billing. Включить снова может только
   пользователь с правом, новым согласием.
4. **Сохранение карты при пополнении** (§6.1): на нашей странице до Checkout
   необязательный чекбокс «Сохранить карту для следующих пополнений». Текст рядом:
   карта хранится в Stripe, без действия клиента она списывается только при
   включённом авто-пополнении (п. 3). Без чекбокса карта не сохраняется. Время и
   версия текста сохраняются. Кнопка «Привязать карту» показывает тот же текст без
   чекбокса: нажатие кнопки и есть согласие, оно сохраняется так же.
5. Для подписки (ЕС и США): раскрытие условий до оплаты (п. 1), явное согласие
   (пп. 1-2), отмена онлайн в Customer Portal и ссылкой из ui. Квитанции и счета
   шлёт Stripe.

**Где хранятся согласия.** Таблица `billing_consents` (новая): `id`, `workspace_id`,
`github_user_id`, `kind` (`immediate_start | auto_recharge | save_card`),
`text_version`, `params` (JSON: цена и период для `immediate_start`; порог, сумма,
потолок и карта для `auto_recharge`), `created_at`. Строки только добавляются;
действующее согласие авто-пополнения последнее по `created_at`. Пишут #371 (п. 1, 4),
#372 (п. 1 для подписки) и #513 (п. 3).

Тексты пишет legal ([ui#211](https://github.com/larchanka-training/dmc-268-ui-t6/issues/211)),
юридическая проверка вне эпика (§18).

## 10. Stripe

### 10.1. Объекты

| Объект | Использование |
|---|---|
| Customer | один на workspace; `metadata.workspace_id`; создаётся нами до первого Checkout любого вида (`mode=payment`, `subscription` или `setup`) и передаётся в сессию как `customer` |
| Checkout Session | пополнение (`mode=payment`), подписка (`mode=subscription`), сохранение карты (`mode=setup`); в каждой сессии `billing_address_collection=required` и `customer_update[address]=auto`: адрес сохраняется в Customer, по нему Stripe Tax считает налог и в Checkout, и в счёте авто-пополнения (§6.2) |
| Product, Price | Starter и Pro: фиксированная месячная цена (licensed), `tax_behavior=inclusive`; пополнение: `price_data` на выбранную сумму с `tax_behavior=inclusive` |
| Subscription | один активный тариф на workspace |
| SetupIntent | сохранение карты `off_session` |
| Invoice (разовый) | авто-пополнение (§6.2); счёт пополнения через Checkout `invoice_creation` |
| Customer Portal | карта, счета, VAT ID, смена Starter/Pro по §4.4, отмена в конце периода |
| Stripe Tax | расчёт и reverse charge |
| Billing Credits, Meters | не используем (§10.2) |

### 10.2. Почему не Billing Credits

- Кредиты применяются только к счёту подписки при его финализации, а не в момент
  прогона: проверку баланса перед прогоном на них не построить.
- Применяются только к позициям с metered-ценами через Meters; к разовым счетам
  (пополнение) и к licensed-ценам не применяются.
- Правила Stripe запрещают выдавать их как stored value, то есть как кошелёк вне
  конкретных услуг.
- Лимит: не больше 100 неиспользованных грантов на клиента.
- Customer Portal не меняет подписки с usage-based ценами, только отменяет их.

Свой журнал даёт проверку до прогона, списание после каждого вызова и порядок
источников §5.

### 10.3. Вебхуки

| Событие | Действие |
|---|---|
| `checkout.session.completed` | `mode=payment`: `payments.status=paid`, грант `top_up`, карта сохранена, если был `setup_future_usage` (§6.1); `mode=setup`: карта сохранена, бонус по `setup_intent.succeeded` |
| `checkout.session.expired` | `payments.status=expired` |
| `checkout.session.async_payment_succeeded`, `..._failed` | в v1 только карты; событие логируется |
| `payment_intent.succeeded`, `payment_intent.payment_failed` | только лог: деньги пополнения по `checkout.session.completed`, авто-пополнения и подписки по событиям счёта |
| `payment_method.detached` | если это карта авто-пополнения: авто-пополнение выключается, баннер «Карта изменена, включите авто-пополнение заново» (§6.2, §9 п. 3) |
| `setup_intent.succeeded` | `metadata.source=link_card`: карта сохранена; бонус §7 получателю из `metadata.github_user_id`, если флаг включён и условия выполнены. Без этой метки только лог |
| `invoice.paid` | `metadata.source=auto_recharge`: грант `top_up` (§6.2). Счёт подписки, подписка `canceled`: грант `top_up` на оплаченную сумму, тариф не возвращается (§4.3). Иначе грант `subscription_grant`: полный для `billing_reason` = `subscription_create` или `subscription_cycle`, на оплаченную сумму для доплаты за повышение (§4.3, §4.4); иначе без гранта |
| `invoice.payment_failed`, `invoice.payment_action_required` | `metadata.source=auto_recharge`: авто-пополнение выключается, баннер (§6.2). Подписка: статус `past_due`, тариф работает, баннер «Оплата подписки не прошла» (§4.3), письмо шлёт Stripe |
| `customer.subscription.created`, `.updated` | тариф workspace, лимит репозиториев, статус подписки (`active`, `past_due`) |
| `customer.subscription.deleted` | тариф снимается, workspace на PAYG (§4.3) |
| `customer.tax_id.created`, `.updated` | статус проверки VAT ID |
| `charge.refunded` | по строке `refund` на каждый объект возврата из `charge.refunds`, которого ещё нет (ключ `provider_refund_id`, §5) |
| `charge.dispute.created` | строка `adjustment` с причиной `dispute` на сумму спора в грант платежа (§5); авто-пополнение выключается; отметка для оператора |
| `charge.dispute.closed` | `status=won`: обратная строка `adjustment` с `reversal_of_id`; иначе только лог |

### 10.4. Идемпотентность

- Входящие: id события Stripe (`evt_...`) уникален в своей таблице квитанций;
  повтор отвечает 200 без действий. Порядок событий не гарантирован: обработчик
  читает актуальный объект из Stripe.
- **Строка `payments` на каждый оплачиваемый объект Stripe.** Новые поля (#371):
  `source` (`checkout | auto_recharge | subscription`) и `provider_invoice_id`
  (уникальна пара `(provider, provider_invoice_id)`); `workspace_id` уже есть
  (`app/modules/billing/infrastructure/models.py`). Checkout
  пишет строку при создании сессии (`provider_checkout_id`, счёт `invoice_creation`
  дописывается в `provider_invoice_id`); авто-пополнение при создании попытки
  (§6.2); счёт подписки при первом событии по нему (`invoice.paid` или
  `invoice.payment_failed`). Статусы те же: `pending | paid | failed | expired`.
  Грант `top_up` и `subscription_grant` ссылаются на строку через `payment_id`;
  ключ гранта подписки «id счёта» это `provider_invoice_id` этой строки.
- Бизнес-ключи: уникальные `payments (provider, provider_checkout_id)`,
  `(provider, provider_invoice_id)` и
  `(provider, provider_payment_id)`, `credit_ledger.payment_id`,
  строки списания по `(usage_event_id, grant_id)`, `run_settlement` по
  `(run_id, grant_id)` (§5.1), грант подписки по id счёта, бонус по GitHub user id,
  workspace и fingerprint карты.
- Строки гранта платежа: частичный уникальный индекс `uq_credit_ledger_payment`
  по `payment_id` в #371 сужается до видов `top_up` и `subscription_grant`; строка
  `refund` уникальна по `provider_refund_id` (новое поле), повторное
  `charge.refunded` с тем же возвратом ничего не пишет.
- Сторно и возвраты: строка `adjustment` сторно уникальна по `reversal_of_id` (id
  строки, которую она возвращает, в том числе строки спора); строка спора уникальна
  по id спора Stripe (`dp_...`); возврат при деградации по
  `(run_id, grant_id)` с причиной `engine_fallback`. Истечение: `expiry` уникален по
  `grant_id` для основного истечения, по `(grant_id, hold_run_id)` для отложенной
  части после снятия удержания (§5.2) и по `reversal_of_id` для истечения
  возвращённой суммы (§5.1). `expired_offset` уникален по `offset_of_id` (строка
  возврата или спора), `debt_repayment` по паре (id нового гранта,
  `repaid_grant_id`). Удержание по `run_id` (§5.2).
- Исходящие вызовы Stripe идут с `Idempotency-Key` из нашего id (платёж, попытка
  авто-пополнения), вне транзакции БД (BACKEND_ARCHITECTURE).

### 10.5. Сверка

- Leader-задача раз в сутки читает из Stripe Checkout Sessions, PaymentIntents,
  счета, возвраты и споры (`disputes`) за 72 часа и сравнивает с `payments`,
  грантами, строками `refund` и строками спора. Пропущенное применяется тем же
  идемпотентным обработчиком. Расхождение сумм даёт алерт. Зависшие попытки
  авто-пополнения в `pending` разбирает задача §10.6, а не суточная (§6.2).
- Инвариант баланса: остаток равен сумме `credit_ledger.amount_usd` по workspace;
  отдельного поля баланса нет либо оно проверяется по сумме.

### 10.6. Досписание после сбоя

Строки списания и итог run пишутся разными транзакциями (§3.3). Если процесс упал
между ними, пропуск находит leader-задача, а не повтор воркера.

- Раз в 5 минут задача сверяет итоги, а не ищет строку на каждый вызов (строки с
  нулевой суммой не пишутся, §3.3). Для run в конечном состоянии, в том числе
  переведённых реконсилером в `failed` без воркера (T13 `lease_expired`), ожидаемый
  итог такой:

  | Итог run | Ожидается |
  |---|---|
  | `succeeded` с вызовами LLM | сумма списаний run равна `P` |
  | `failed` | у каждой строки списания run есть сторно, сумма 0 |
  | `cancelled`, `skipped` | удержание снято; списанное не меняется, после деградации не больше нового `P` (§3.3) |
  | любой, без `usage_events` | строк списания нет, удержание снято |

  Для run в работе ожидаемая сумма списаний `min(число вызовов × P × 25%, P)`;
  меньшая сумма значит пропуск.
- Найденное расхождение применяется тем же идемпотентным обработчиком, что и в
  воркере: недостающее списание за вызов, итог по §3.4, снятие удержания. Повтор
  ничего не дублирует (§10.4).
- **Попытки авто-пополнения в `pending`** старше 5 минут: та же задача повторяет
  шаги с прежними ключами, сверяет счёт со Stripe или после 23 часов ставит
  `failed` с `stale_attempt` (§6.2).
- **Проверка авто-пополнения по уровню** (§6.2): на каждом проходе та же
  leader-задача проверяет workspace, где авто-пополнение включено, остаток ниже
  порога и нет попытки в `pending`. Так проверка не теряется, если процесс упал
  между commit списания и вызовом Stripe, или остаток опустили `refund` и спор без
  списания. В начале месяца UTC эта же проверка снова запускает авто-пополнение,
  остановленное потолком.
- **Истечение грантов** выполняет отдельная leader-задача раз в час: для каждого
  гранта с истёкшим сроком под блокировкой строки workspace пишет `expiry` на
  свободный остаток, а для части под активным удержанием ждёт `released` и пишет
  отложенную строку (§5.2). Запись идёт обычным use case (§3.3). Пропуск
  истечения старше суток даёт алерт.
- Задача смотрит записи старше 2 минут, чтобы не гоняться с живым воркером.
  Найденный пропуск увеличивает метрику и пишется в лог; пропуск старше часа даёт
  алерт.
- Для списания за вызов нужен id события: `SqlAlchemyUsageLedger.record` сейчас
  возвращает `None` (`usage_ledger.py`), в #371 он возвращает id `usage_events`.

## 11. Роли и команда

### 11.1. Матрица

| Действие | Owner | Admin | Billing | Member |
|---|---|---|---|---|
| Смотреть списания, баланс, тариф | да | да | да | да |
| Смотреть прогоны и находки | при доступе GitHub к репозиторию | при доступе GitHub | при доступе GitHub | при доступе GitHub |
| Запускать и перезапускать ревью | да | да | нет | да |
| Пополнять баланс, менять карту | да | да | да | нет |
| Менять тариф, авто-пополнение, счета, VAT ID | да | да | да | нет |
| Настройки репозиториев (вкл., движок, правила, RAG) | да | да | нет | нет |
| Приглашать, менять роли, удалять участников | да | да (кроме Owner) | нет | нет |
| Назначать и снимать Owner | да, кроме последнего Owner (§11.2) | нет | нет | нет |

- Прогоны и находки содержат код, поэтому их видимость не зависит от роли: только
  при доступе GitHub к репозиторию (D4). Billing без доступа GitHub видит оплату,
  баланс и сводку списаний, но не прогоны, находки и код.
- Billing нужен бизнесу: бухгалтер платит, но не трогает настройки.
- Удаление workspace вне scope, см.
  [#545](https://github.com/larchanka-training/dmc-268-api-t6/issues/545).

### 11.2. Членство поверх GitHub

- Роли хранятся отдельно от `github_user_workspace_access`: строка роли
  `(workspace_id, github_user_id, role, source)`, `source` = `install` (первый
  Owner, ниже), `invite` (приглашение или назначение в продукте) или `claim`
  (восстановление Owner, ниже). `LinkGitHubInstallations` строки ролей не меняет.
- Роль пользователя определяется по шагам, первое совпадение решает:
  1. **Запись об исключении** (`workspace_member_exclusions`: `workspace_id`,
     `github_user_id`, кто и когда удалил): доступа к workspace в продукте нет, даже
     при доступе GitHub.
  2. **Строка роли:** Owner, Admin, Billing, Member.
  3. **Доступ GitHub без строки роли:** Member.
  4. Иначе доступа нет.
- **Первый Owner это установщик App**, как в похожих GitHub App сервисах:
  - установка на организацию: ставит App владелец организации в GitHub или тот,
    кому он это разрешил (менеджер GitHub App); участник может лишь запросить
    установку, а одобряет её владелец. Поэтому `sender` события
    `installation.created` и есть первый Owner; право `members: read` для этого
    не нужно;
  - установка на личный аккаунт: владелец этого аккаунта.
  Workspace и установку на `main` создаёт OAuth-вход (`LinkGitHubInstallations`),
  а доставка для ещё не связанной установки ждёт связывания (SD §6.5). Поэтому
  первого Owner пишет проекция после связывания, а не обработчик вебхука: когда
  установка связана с workspace, проекция берёт `sender.id` и `account.type` из
  сохранённой доставки `installation.created` этой установки, пишет в
  `provider_metadata` установки `installer_github_user_id` и `account_type`
  (`Organization | User`) и, **только если у workspace ещё нет ни одного Owner**, в
  той же транзакции строку роли `owner` с `source = install`. Исходы:
  - переустановка на тот же аккаунт (новая установка получает прежний workspace,
    `github_repository_rebinding.py`): метаданные новой установки пишутся, Owner
    не добавляется, роли и баланс workspace не меняются;
  - доставка `installation.created` истекла до связывания (payload живёт 30 дней,
    §1) или не пришла: установщика нет, workspace начинает в режиме без Owner до
    восстановления (ниже);
  - установки, созданные до #373: сейчас в `provider_metadata` только
    `account_login`, поэтому установщика нет, тот же режим без Owner.
- **Дальше Owner живёт только в нашей БД.** Назначает и снимает Owner только Owner
  в продукте: делает Owner другого участника или приглашает с ролью Owner. Смена роли
  в организации GitHub наши роли не меняет: проверок роли GitHub при входе, перед
  денежными действиями и по вебхукам `organization` и `membership` нет.
- **Принятый риск: роль живёт до снятия в продукте.** Owner, Admin и Billing (любой
  `source`) держат workspace в токене и свои права, пока их роль не снимут в
  продукте, даже если человек ушёл из организации GitHub: денежные действия и смена
  карты и ролей ему доступны всё это время. Согласие на авто-пополнение такого
  человека тоже действует, списания ограничены месячным потолком (§6.2). Снимают
  роль Owner (любую) и Admin (кроме Owner) удалением участника ниже; если ушли все
  Owner, сначала заявка «Стать Owner». Чтобы риск был виден, экран «Команда»
  показывает у Owner, Admin и Billing дату последнего входа через GitHub и, если
  право `members: read` принято, членство в организации на момент открытия экрана.
  Срока жизни роли нет; риск выносится на подтверждение техлида (§19).
- **Минимум один Owner.** Последнего Owner нельзя понизить или удалить: API
  отвечает отказом, ui прячет действие. Ui рекомендует держать двух Owner, чтобы
  уход одного человека не оставил workspace без владельца.
- **Восстановление Owner.** Условие проверяется в момент заявки, а не по строкам
  `github_user_workspace_access`: они не пересчитываются по workspace и живут, пока
  человек сам не войдёт (SD §6.5).
  - организация: админ организации в GitHub может нажать «Стать Owner». При заявке
    мы проверяем через GitHub API (`GET /orgs/{org}/memberships/{username}`) его
    роль (`admin`, `state = active`) и каждого текущего Owner. Заявка проходит, если
    ни один текущий Owner не активный участник организации (ушёл, удалён или
    приглашён в продукт без членства в организации) или Owner нет совсем (старая
    установка без сохранённого установщика). «Без доступа» значит именно это: не
    активный участник организации по ответу API на момент заявки. Для проверок App
    нужно право организации `members: read` (сейчас прав организации нет, SD §8.2;
    добавление в #373), его принимает админ организации в GitHub. Пока право не
    принято, восстановление недоступно, и ui так и пишет: «Попросите админа
    организации принять новые права приложения в GitHub» со ссылкой на страницу
    установки;
  - личный аккаунт: владелец аккаунта установки (проверка по id аккаунта) может
    стать Owner, если он ещё не Owner: установка принадлежит ему, другого
    владельца у неё нет.
  - Заявка пишет строку `owner` с `source = claim` и строку журнала
    `workspace_owner_claims` (новая, #373): `workspace_id`, `github_user_id`, время,
    id прежних Owner и их статус в организации по ответу API, снята ли запись об
    исключении. Если у заявителя есть запись об исключении (шаг 1), заявка снимает
    её в той же транзакции и отмечает это в журнале: админ организации и так
    управляет установкой в GitHub. Прежние Owner не снимаются сами, в том числе
    приглашённые без членства в организации; снять их может новый Owner обычным
    удалением.
- **Режим без Owner.** Пока у workspace нет ни одного Owner (старая установка до
  восстановления):
  - ревью идут как обычно и списываются с имеющегося баланса и бонуса; на нуле
    `balance_exhausted` (§8.1);
  - Admin и Billing по приглашению (`source = invite`) действуют по матрице §11.1:
    бизнес может платить через своего Billing;
  - если нет и Admin, и Billing, закрыты пополнение, карта, тариф, авто-пополнение
    и роли: делать это некому;
  - пока нет ни Owner, ни Admin, настройки репозиториев открыты всем с доступом
    GitHub, как на `main` сейчас, чтобы роли не отняли их у существующих
    организаций;
  - ui показывает кнопку «Стать Owner» для админа организации или владельца
    аккаунта, а если право `members: read` не принято, текст выше.
  Режим заканчивается с первым Owner: дальше действует матрица §11.1. Ни
  оператор, ни порядок входа Owner не назначают.
- **GitLab и Bitbucket.** Workspace рождается только при входе через GitHub
  (`LinkGitHubInstallations`), а подключение GitLab или Bitbucket требует уже
  существующего workspace (`app/modules/integrations/gitlab/application/manage_connection.py`).
  Поэтому Owner у такого workspace по правилам выше: первый Owner от установки
  GitHub App, восстановление админом организации GitHub. Роли группы GitLab и
  workspace Bitbucket на наши роли не влияют. Подключать и отключать интеграции
  могут Owner и Admin (настройки, §11.1). Workspace без GitHub в эпике нет; если он
  появится, правило первого Owner для него решается отдельно.
- **Удалить участника** (Owner или Admin; Admin не удаляет Owner, последнего Owner
  удалить нельзя) значит снять строку роли и записать исключение (шаг 1). Если его
  согласие держит включённое авто-пополнение, оно выключается (§9, п. 3); так же
  при снятии роли, в том числе роли Owner. Повторный вход через GitHub доступ не
  возвращает. Исключение снимается только принятием нового приглашения для этого
  GitHub user id или заявкой «Стать Owner» этого пользователя (с записью в
  журнале). Доступ GitHub к репозиториям мы не трогаем; полностью закрыть доступ
  можно только в GitHub.
- **Приглашение без email:** ссылка с одноразовым кодом, срок 7 дней, роль задана
  заранее, принять её можно только после входа через GitHub. Приглашение с ролью
  Owner, Admin или Billing обязательно привязано к GitHub login: его принимает
  только этот логин (сверка по GitHub user id, который мы находим по логину при
  создании приглашения), иначе отказ, код не тратится. Так утёкшая ссылка не даёт
  чужому человеку карту, баланс и роли. Приглашение Member можно без привязки.
  Ссылку передают любым каналом.

### 11.3. Роль и JWT

**Членство в workspace** сейчас читается из `github_user_workspace_access` в
нескольких местах (SD §6.5):

| Место | Что читает |
|---|---|
| `app/modules/auth/infrastructure/sessions.py` | список Workspace в токене |
| `app/modules/auth/infrastructure/current_user.py` | `GET /api/auth/me`, список workspace для ui |
| `app/modules/reviews/infrastructure/metrics_summary.py` | сводка расхода и списаний |
| `app/modules/integrations/bitbucket/infrastructure/connection_store.py` | выбор workspace для подключения Bitbucket |
| `app/modules/workspaces/infrastructure/repository_access.py` | доступ к репозиториям, прогонам и находкам |

С #373 первые четыре места читают одно определение членства: строки
`github_user_workspace_access` плюс строки роли любого `source` (`install`,
`invite`, `claim`; Owner, Admin, Billing, Member) минус записи об исключении
(§11.2). Определение живёт в одном запросе модуля `workspaces`, места выше его
вызывают. `repository_access.py` остаётся на доступе GitHub: прогоны, находки и
код видны только при доступе GitHub к репозиторию (§11.1). Так Billing без доступа
GitHub после принятия приглашения видит workspace в ui, баланс и сводку списаний и
может платить; прогоны и находки ему по-прежнему не видны.

Роль не кладётся в JWT. На каждом важном действии (оплата, тариф, авто-пополнение,
настройки, команда) роль читается из БД. Запись об исключении (§11.2, шаг 1)
проверяется на каждом запросе к workspace, в том числе на чтении: список Workspace
из JWT сверяется с `workspace_member_exclusions`. Смена роли и удаление действуют
сразу везде, а не через 15 минут жизни access-токена.

## 13. Рассмотренные модели оплаты

| Модель | Плюсы | Минусы |
|---|---|---|
| За место в месяц | привычно, предсказуемо | платят за людей, а не за ревью; маленькие команды переплачивают |
| Расход × наценка | честно к расходу | цена неизвестна до прогона, зависит от провайдера и курса |
| Кредиты Stripe Billing | готовый журнал у Stripe | только при счёте подписки, нет проверки до прогона (§10.2) |
| **Фиксированная цена за ревью + свой баланс** | цена видна заранее, команда бесплатна | свой журнал, сверка и пороги расхода на нас |

Выбрана последняя.

## 14. Последствия

Плюсы:

- клиент знает цену ревью до запуска, команда растёт без доплаты;
- баланс проверяется до прогона, а не после счёта;
- смена модели или провайдера не меняет цену для клиента.

Цена:

- свой журнал, гранты, сроки, сверка со Stripe и идемпотентность вебхуков;
- пороги расхода ограничивают выбор модели (§8.2);
- согласия потребителя частично вне Checkout, на нашей странице;
- роли продукта живут рядом с членством из GitHub.

режим, журнал не меняется.
