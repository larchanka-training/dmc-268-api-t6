## 1. Контекст

Расход LLM считается, но ни с кого не списывается. Права в продукте целиком
выводятся из GitHub. Состояние `main`, на которое опирается ADR:

- `payments` и `credit_ledger` созданы миграцией 0001, код их не читает и не пишет
  ([models.py](../../app/modules/billing/infrastructure/models.py)). Суммы в USD,
  `Numeric(12, 6)`.
- `payments`: `provider`, `provider_checkout_id`, `provider_payment_id`,
  `amount_usd`, `status` (`pending | paid | failed | expired`), `paid_at`; уникальны
  пары `(provider, provider_checkout_id)` и `(provider, provider_payment_id)`.
- `credit_ledger`: виды `top_up | usage_debit | adjustment`; `usage_event_id` и
  `payment_id` уникальны (частичные индексы). CHECK: `top_up` только с
  `amount_usd > 0` и `payment_id`, `usage_debit` только с `amount_usd < 0` и
  `usage_event_id`.
- `usage_events.cost_usd` пишется после каждого вызова LLM своей короткой
  транзакцией и переживает откат прогона (AGENTS.md, исключение для
  `SqlAlchemyUsageLedger.record`). `run_id` NOT NULL.
- Лимит стоимости прогона: fast $0.50, deep $3 на все попытки, проверка до каждого
  вызова ([PIPELINE_SPEC §4.5](../PIPELINE_SPEC.md#45-лимиты-вызовов-и-стоимости)).
- `budget_paused`: Run `skipped` при claim, если остаток дневного бюджета меньше
  лимита fast. `workspaces.daily_budget_usd = 0` значит «лимит не задан»
  (`handle_review_run.py`, SD §11).
- Членство в workspace: `github_user_workspace_access`, пересчитывается из GitHub
  при каждом входе (`LinkGitHubInstallations`, `revoke_unlisted`). Ролей нет.
- Access JWT живёт 15 минут (`ACCESS_TOKEN_LIFETIME`), несёт список Workspace
  (SD §6.5).
- Payload вебхуков `installation` хранится в `webhook_events` 30 дней после
  завершения квитанции (SD §13).

## 2. Решение кратко

- Свой предоплаченный баланс в USD в `credit_ledger` остаётся источником правды.
  Stripe принимает платежи и ведёт подписки. Stripe Billing Credits не используем
  (§10.2).
- Клиент платит за ревью, а не за места. Вся команда workspace бесплатна.
- Цена ревью фиксирована по тарифу и движку. Расход LLM считаем внутри и не
  показываем клиенту.
- Тарифы: Pay as you go, Starter $19/мес, Pro $49/мес.
- Нулевой баланс блокирует новые прогоны с причиной `balance_exhausted`.
- Роли продукта Owner, Admin, Billing, Member поверх доступа GitHub. Роль не в JWT,
  проверяется в БД.
- Налоги: Stripe Tax, цены включают НДС и одинаковы для всех. Бизнес из другой
  страны ЕС с VAT ID платит ту же сумму с НДС 0 (reverse charge), бизнес из
  Германии платит с немецким НДС.

## 3. Деньги

### 3.1. Валюта и точность

| Что | Решение |
|---|---|
| Валюта | USD везде: баланс, цены, Stripe Prices |
| Хранение | `Numeric(12, 6)`, как `credit_ledger` и `usage_events` |
| Stripe | целые центы; пополнение в целых долларах |
| Показ клиенту | до цента; цена единицы тарифа до десятой доли цента ($0.136); хранимое значение в 6 знаках (§3.2) |
| Округление | списание считается в 6 знаках и не округляется до центов |

### 3.2. Цена за ревью (изменение D1)

D1 говорит «расход LLM × наценка». ADR меняет D1, изменение принято техлидом в
ревью этого PR: **клиент платит фиксированную цену за ревью** по своему тарифу и
движку (§4). Расход каждого прогона по `usage_events.cost_usd` и его доля в цене
считаются и логируются внутри, для сверки и пересчёта цен. Причина: клиент видит
цену до запуска, сумма не зависит от провайдера и курса EUR, а пороги расхода
(§8.2) ниже цены прогона на любом тарифе.

Цена прогона `P`:

```
P = цена_единицы(тариф, движок) × множитель
множитель = 1 + надбавка_большого_PR
```

- `цена_единицы`: §4.1. Хранится как цена тарифа, делённая на число ревью в пакете,
  с округлением вниз до 6 знаков: PAYG $0.200000, Starter $0.135714 (19/140), Pro
  $0.116666 (49/420). Так 140 и 420 ревью целиком помещаются в грант $19 и $49
  (остаток $0.00004 и $0.00028 истекает с грантом). Клиенту показывается
  округлённая цена $0.136 и $0.117 (§3.1).
- Надбавка: +1 к множителю за каждые начатые 1000 строк сверх 1000 (§4.2).
- Тариф и цена единицы фиксируются при claim. Множитель и признак summary-only
  известны только после загрузки и фильтрации diff (`vcs.fetch_diff`, PIPELINE_SPEC
  §2), поэтому `P` фиксируется там и дальше не меняется, кроме деградации (§3.3).

### 3.3. Момент и формула списания

- **Гейт 1, claim** (T4/T5): доступный для движка остаток (§5.2) не меньше цены
  единицы (множитель 1). Тогда в той же транзакции claim пишется удержание на цену
  единицы (§5.2). Иначе `skipped`, `balance_exhausted` (§8). Строк PR на этом шаге
  ещё нет.
- **Гейт 2, после `vcs.fetch_diff`**, до первого вызова LLM: известны множитель и
  summary-only. Summary-only: `P = 0`, удержание снимается, гейт пройден. Иначе
  доступный остаток вместе с удержанием этого run не меньше `P`: удержание
  поднимается до `P`. Если не хватает, удержание снимается и `running → skipped` с
  `error_code = balance_exhausted` и 0 вызовов LLM, по образцу T19. Переход
  добавляется в PIPELINE_SPEC §1 вместе с #371.
- **После каждого вызова LLM** пишется списание, связанное с `usage_event_id`
  этого вызова: `min(P × 25%, P - уже_списано_по_run)`. Доля не зависит от расхода
  вызова, поэтому сумма не раскрывает расход. Распределение по грантам: §5.1.
- **При успехе** (T14 `succeeded`) пишется доплата до `P` (`run_settlement`).
  Повторные попытки внутри run цену не увеличивают.
- **Run без вызовов LLM бесплатен.** Правило задаётся через вызовы, а не через
  итог: если у run нет ни одной строки `usage_events`, при итоге `P = 0`,
  `run_settlement` не пишется, удержание снимается. Это покрывает summary-only,
  backend none и `skipped` (§3.4).
- **Деградация deep → fast** (PIPELINE_SPEC §5.3): с момента деградации `P`
  пересчитывается по цене fast с тем же множителем, порог расхода тоже берётся для
  fast (§8.2). Если по run уже списано больше нового `P`, разница возвращается
  строками `adjustment` в те же гранты при завершении run. Клиент платит цену fast.
- Строки списания пишутся своей короткой транзакцией сразу после `usage_events`,
  без сетевых вызовов внутри. Это второе узкое исключение из правила «commit
  делает только use case», рядом с `SqlAlchemyUsageLedger.record`; оно записано в
  `AGENTS.md`, `.agents/rules/backend.md` и BACKEND_ARCHITECTURE (§15). Доплата
  `run_settlement` и возвраты пишутся так же: отдельной короткой транзакцией после
  commit перехода run в конечное состояние, идемпотентно по `run_id` (§10.4), чтобы
  откат основного run их не терял, а повтор не дублировал. Пропуск после сбоя
  дописывает задача §10.6.

### 3.4. Неудачный и отменённый прогон

| Итог run | Что списано |
|---|---|
| `succeeded` с хотя бы одним вызовом LLM | ровно `P` |
| `failed` (наша сторона: ошибка LLM, таймаут, баг, verifier) | 0: каждое списание run сторнируется строкой `adjustment` в тот же грант (§5.1) |
| `cancelled` (новый `head_sha`, PR закрыт, `POST /api/runs/{id}/cancel`) | уже списанное по §3.3, без доплаты |
| `skipped` (вызовов LLM не было, в том числе гейт 2) | 0 |
| summary-only, любая из причин `diff_too_large` (в том числе PR больше 3000 строк, §4.2), `diff_inventory_incomplete`, `no_reviewable_files` (PIPELINE_SPEC §2) | 0 |
| `succeeded` без вызовов модели (backend none: 0 LLM, `findings=[]`, coverage none, PIPELINE_SPEC §2) | 0 |
| любой итог, если у run нет ни одной строки `usage_events` | 0 (§3.3) |

### 3.5. Что видит клиент

Клиент видит **списанную сумму** (`chargedUsd`) и остаток баланса, никогда не
`cost_usd`, лимиты расхода и токенов прогона. Поля `contracts/openapi.yaml` на
`main`, которые сейчас отдают клиенту расход, и решение по каждому (реализация
#310 и #371):

| Схема и поле | Где отдаётся | Решение |
|---|---|---|
| `RunUsage.costUsd` | прогон в списке и деталях | заменяется на `chargedUsd` из `credit_ledger` ([#310](https://github.com/larchanka-training/dmc-268-api-t6/issues/310)) |
| `RunBudget.costUsd`, `RunBudget.costLimitUsd` | детали прогона | убираются из ответа клиенту; расход и порог прогона видит только оператор |
| `MetricsTotals.costUsd` | `GET /api/metrics/summary` | заменяется на `chargedUsd` за период |
| `MetricsDay.costUsd` | `GET /api/metrics/summary`, по дням | заменяется на `chargedUsd` за день |
| `WorkspaceDailyBudget.spentTodayUsd`, `dailyBudgetUsd` | `GET /api/metrics/summary` | считаются по списанному, а не по расходу: дневной лимит workspace ограничивает списания за день (§8.1) |

- Токены (`tokensIn`, `tokensOut`) остаются: это техническая метрика прогона, а не
  сумма в деньгах.
- `cost_usd` остаётся во внутренних метриках оператора (Prometheus, логи), не в
  API клиента.
- [ui#186](https://github.com/larchanka-training/dmc-268-ui-t6/issues/186): страницы
  «Аудит» и «Аналитика» показывают списанное, а не расход LLM.

## 4. Тарифы

### 4.1. Цены

| Тариф | Цена | Включено | Fast | Deep | Graph RAG | Репозитории |
|---|---|---|---|---|---|---|
| Pay as you go | только пополнения | - | $0.20 | $1.00 (5 единиц) | нет | без лимита |
| Starter | $19/мес | 140 ревью | $0.136 (хранится $0.135714) | 5 единиц | да | до 5 |
| Pro | $49/мес | 420 ревью | $0.117 (хранится $0.116666) | 5 единиц | да | без лимита |

- Единица тарифа: одно fast-ревью. Deep стоит 5 единиц своего тарифа, как в PAYG
  ($1.00 = 5 × $0.20).
- Deep доступен во всех тарифах. Graph RAG только в подписке. Лимит
  репозиториев: Starter до 5, остальные без лимита.
- Сверх пакета ревью списываются с купленного баланса по цене единицы своего
  тарифа.
- Мест нет: число участников не ограничено.
- Скидка к PAYG: Starter 32%, Pro 42%.
- Отдельного тарифа для бизнеса нет: компании покупают Starter или Pro.
- Enterprise (SSO, договор, SLA): по запросу, вне эпика.

### 4.2. Надбавка за большой PR

- Строки PR: добавленные плюс удалённые строки diff после исключений политики.
- 1-1000 строк: множитель 1. Каждые начатые 1000 строк сверх 1000: +1. Пример для
  PAYG: fast на 1500 строк $0.40, deep на 2500 строк $3.00.
- Больше 3000 строк: ревью только summary без LLM, $0.

### 4.3. Подписка

- Подписка Stripe на месяц, автопродление. Смена тарифа и отмена через Customer
  Portal (§10.1).
- Включённые ревью начисляются грантом `subscription_grant` в USD ($19 и $49) по
  `invoice.paid` только для счетов с `billing_reason` = `subscription_create` или
  `subscription_cycle`. Ключ идемпотентности: id счёта.
- Счета с другим `billing_reason` полного гранта не дают. Единственное исключение
  описано в §4.4: доплата за повышение даёт грант на оплаченную сумму. Счёт с нулевой
  суммой (`amount_paid = 0`) грант не даёт.
- Отмена действует в конце оплаченного периода; до него тариф работает.
- Счёт не оплачен после повторов Stripe: тариф снимается, workspace переходит на
  PAYG, остаток гранта живёт до своего срока.

### 4.4. Смена тарифа

| Переход | Когда действует | Деньги и гранты |
|---|---|---|
| PAYG → Starter или Pro | сразу, новая подписка | грант по `subscription_create` (§4.3) |
| Starter → Pro (повышение) | сразу | Stripe выставляет доплату за остаток периода (`proration_behavior=always_invoice`); по её `invoice.paid` (`billing_reason=subscription_update`) пишется `subscription_grant` на оплаченную сумму со сроком текущего гранта; цена единицы Pro действует с момента смены |
| Pro → Starter (понижение) | в конце оплаченного периода | до конца периода работает Pro; новый грант $19 по `subscription_cycle`; остаток гранта Pro живёт до своего срока |
| Подписка → PAYG (отмена) | в конце оплаченного периода | §4.3 |

- Customer Portal настраивается так: повышение сразу с доплатой, понижение и
  отмена в конце периода (`schedule_at_period_end`).
- **Понижение при числе репозиториев больше 5.** До смены страница тарифа
  предупреждает и даёт Owner или Admin выбрать 5 репозиториев. После смены ревью
  идут только в выбранных 5; если выбора нет, остаются 5 с последними прогонами.
  Остальные репозитории остаются подключёнными, их прогоны `skipped` с
  `error_code = plan_repo_limit`.
- **Коды отказа по лимитам тарифа.** Сервер проверяет каждый лимит сам:

| Код | Когда |
|---|---|
| `plan_repo_limit` | Starter: включение 6-го репозитория (ответ API) или прогон в репозитории сверх лимита (`skipped`) |
| `plan_graph_rag_unavailable` | PAYG: включение Graph RAG (ответ API). Если RAG уже включён, а тариф стал PAYG, ревью идёт без RAG, отметка в трейсе с этим кодом |
| `balance_exhausted` | остаток меньше цены (§3.3, §8.1) |

## 5. Кредиты: виды, порядок и сроки

| Источник | Вид в `credit_ledger` | Срок | На что |
|---|---|---|---|
| Подписка | `subscription_grant` (новый) | 1 цикл + 1 месяц | fast и deep |
| Бонус | `promo` (новый) | 30 дней | только fast |
| Пополнение | `top_up` | 12 месяцев | fast и deep |

- **Порядок списания:** подписка, затем бонус, затем купленные. Внутри источника
  раньше истекающий грант первым.
- Истечение пишет строку `expiry` (новый вид) на остаток гранта.
- Возврат денег пишет `refund` (новый вид). Доплата при успехе пишет
  `run_settlement` (новый вид).
- Отрицательный остаток (§5.2) гасится первым следующим начислением любого вида.
- DDL новых видов и ссылки на грант: #371 и #372.

### 5.1. Распределение списания по грантам

- Каждая строка списания ссылается на один грант (`grant_id`). Если сумма
  списания больше остатка текущего гранта, пишется несколько строк: по одной на
  каждый грант в порядке выше, до полной суммы.
- Уникальность: `(usage_event_id, grant_id)` для списаний за вызов и
  `(run_id, grant_id)` для `run_settlement`. Частичный уникальный индекс
  `uq_credit_ledger_usage_event` только по `usage_event_id` в #371 заменяется
  составным. Идемпотентность записи сохраняется: строки одного списания пишутся
  одной транзакцией, повтор находит их по `usage_event_id` (или `run_id`) и ничего
  не пишет.
- **Сторно** (неудачный run, деградация) пишет строку `adjustment` на каждую строку
  списания run, в тот же грант и на ту же сумму. Возврат сохраняет срок и движки
  исходного гранта: бонус возвращается бонусом, только для fast. Если грант уже
  истёк, сразу за сторно пишется `expiry` на возвращённую сумму.
- Остаток гранта: сумма гранта плюс все строки, которые на него ссылаются.

### 5.2. Удержание на время прогона

Параллельные прогоны не могут потратить один и тот же остаток: каждый run держит
удержание, и следующий claim видит уже уменьшенный остаток.

- Таблица `balance_holds` (новая, #371): `run_id` (уникален), `workspace_id`,
  `engine`, `amount_usd`, `status` (`active | released`), `created_at`,
  `released_at`. Одно удержание на run.
- **Доступный остаток** для движка = остаток грантов, которые подходят движку
  (§5), минус активные удержания workspace. Гейты §3.3 и `budget_paused` (§8.1)
  смотрят именно на него.
- Claim пишет удержание в своей транзакции под блокировкой строки workspace
  (`SELECT ... FOR UPDATE`), поэтому два claim одного workspace проверяют остаток
  по очереди. Гейт 2 поднимает удержание до `P` так же.
- Каждое списание за вызов уменьшает удержание на ту же сумму в той же короткой
  транзакции: удержание всегда равно `P` минус уже списанное по run.
- Удержание снимается (`released`) в транзакции итогового списания или сторно
  run: `run_settlement` при `succeeded`, сторно при `failed`, конец списаний при
  `cancelled` и `skipped`. Повтор находит `released` и ничего не делает.
- Если воркер не дожил до итога (T13 `lease_expired` и другие переходы
  реконсилера), удержание снимает задача досписания §10.6.
- `expiry` (§5) списывает только свободную часть гранта: часть, которая по порядку
  §5 приходится на активные удержания, истекает после снятия удержания.
- **Овердрафт:** 0. Удержание покрывает полную цену run, сторно и деградация её
  только уменьшают, а истечение не трогает удержанную часть. Отрицательный остаток
  возможен только после возврата денег (`refund`, `charge.dispute.created`) на уже
  потраченное пополнение; он гасится первым следующим начислением (§5).

## 6. Пополнение и авто-пополнение

### 6.1. Пополнение

- Любая сумма от $10 до $500 в целых долларах, Stripe Checkout `mode=payment`.
- Грант `top_up` пишется по `checkout.session.completed` со статусом оплаты `paid`.
- Карту можно сохранить двумя путями, оба уже в первой версии:
  - **кнопка «Привязать карту»** на экране «Баланс и тариф»: Checkout `mode=setup`
    (SetupIntent `usage=off_session`), без списания. Событие `setup_intent.succeeded`.
    Только этот путь даёт бонус (§7);
  - **при пополнении**, если клиент отметил «Сохранить карту» на нашей странице до
    Checkout (§9, п. 4): `payment_intent_data.setup_future_usage=off_session`. Карта
    сохраняется вместе с оплатой; событие `checkout.session.completed`, карта берётся
    из `payment_method` его PaymentIntent. Бонуса этот путь не даёт.
- Сохранённая карта нужна авто-пополнению (§6.2), чтобы не вводить её повторно.

### 6.2. Авто-пополнение

| Параметр | Значение |
|---|---|
| По умолчанию | выключено |
| Кто включает | Owner, Admin или Billing; порог и сумму задаёт пользователь |
| Порог | от $5, когда купленный и бонусный остаток падает ниже порога |
| Сумма | от $10 до $500, как обычное пополнение |
| Месячный потолок | по умолчанию $200 за календарный месяц UTC; пользователь меняет в пределах $10-$500 |
| Платёж | PaymentIntent `off_session` с сохранённой картой, ключ идемпотентности на попытку |
| Отказ карты | авто-пополнение выключается, письмо Owner и Billing, отметка в ui |
| Требуется 3-D Secure | то же: выключается, клиент платит вручную через Checkout |
| Потолок достигнут | до конца месяца не срабатывает, отметка в ui |

- Не больше одной попытки на workspace одновременно.
- Пополнения баланса по порогу в Stripe Billing в документации не найдено, поэтому
  порог проверяем мы.
- Реализация отдельной задачей позже, вне #371: [#513](https://github.com/larchanka-training/dmc-268-api-t6/issues/513). Карта сохраняется уже в
  первой версии (§6.1).

## 7. Бонус новым

- **Фича-флаг** `billing_signup_bonus`, по умолчанию выключен. Пока флаг выключен,
  бонус не начисляется и не обещается в ui. Включает команда.
- **Когда начисляется:** $5 только после привязки карты кнопкой «Привязать карту»
  (Checkout `mode=setup`, §6.1), по `setup_intent.succeeded`. На этом пути карта не
  списывается. Карта, сохранённая при пополнении, бонуса не даёт: так у бонуса одно
  событие и одно место в ui.
- **Кому:** GitHub-пользователю, который нажал кнопку (роль Owner, Admin или
  Billing, §11.1). Не на установку и не на организацию: организаций можно создать
  сколько угодно, а id установки меняется при переустановке.
- **Ограничения:**
  - один бонус на GitHub user id: повторная установка бонус не даёт;
  - один бонус на workspace: второй участник со своей картой бонус не получает;
  - один бонус на карту: по `card.fingerprint` из Stripe, та же карта на другом
    аккаунте бонус не даёт;
  - аккаунту GitHub больше 30 дней (`created_at` из GitHub API).
- Только fast, срок 30 дней. Пишется грантом `promo` на этот workspace. Факт
  выдачи хранится по GitHub user id, workspace и fingerprint карты.
- Реализация в #371.

## 8. Нулевой баланс и лимиты прогона

### 8.1. Нулевой баланс

- **Новые прогоны:** два гейта §3.3. При claim доступный остаток для движка (§5.2)
  меньше цены единицы: Run `skipped`, `error_code = balance_exhausted`; проверка
  идёт после `budget_paused`. После `vcs.fetch_diff` остаток вместе с удержанием
  run меньше `P`: `running → skipped` с тем же кодом.
- **Что видит клиент:** check-run `completed/skipped` с текстом «Баланс исчерпан,
  ревью не запущено» и ссылкой на пополнение; комментарий в PR с той же ссылкой не
  чаще раза в сутки на PR; причина в ui.
- **Начатые прогоны** доделываются: их цена уже удержана (§5.2). Параллельные
  прогоны не уводят остаток в минус, овердрафт 0.
- **`daily_budget_usd`** остаётся отдельным дневным лимитом workspace, 0 значит
  «лимита нет». С #371 он считается по списанному за день, а не по расходу LLM
  (§3.5): клиент задаёт лимит в тех же деньгах, которые платит. Нулевой баланс и
  `budget_paused` не смешиваются: разные проверки, разные коды.

### 8.2. Пороги расхода прогона

Пороги заменяют лимиты PIPELINE_SPEC §4.5 и SD §13 (fast $0.50, deep $3) при
реализации #371. Порог одинаков на всех тарифах, чтобы скидка подписки не
меняла качество ревью, и ниже самой низкой цены ревью (Pro по хранимой цене
единицы: fast $0.116666, deep $0.583330):

| Движок | Порог расхода на прогон |
|---|---|
| fast | $0.11 × множитель |
| deep | $0.55 × множитель |

- Множитель тот же, что в цене (§3.2): большой PR получает порог больше в той же
  пропорции, что и цену.
- Порог передаётся в существующую проверку шлюза перед каждым вызовом
  (`run_cost_limit_usd`, PIPELINE_SPEC §4.5) как лимит этого прогона, а не как
  константа движка. До гейта 2 (§3.3) вызовов LLM нет, поэтому множитель к первому
  вызову уже известен.
- При деградации deep → fast с этого момента действует порог fast. Расход deep
  до деградации может превысить цену fast; этот редкий случай сбоя deep мы берём
  на себя, клиент платит цену fast (§3.3).
- Без деградации расход прогона на пороге остаётся меньше его цены на любом тарифе.
- Расход считается по цене фактического провайдера вызова, а не самого дешёвого.
- Модель и провайдер выбираются по eval
  [#512](https://github.com/larchanka-training/dmc-268-api-t6/issues/512) в пределах
  этих порогов. Если ни одна пригодная модель не укладывается, цены пересчитываются
  новым ADR, пороги не поднимаются молча.
- Через 30 дней после запуска на staging цены сверяются по фактическим
  `usage_events`.

## 9. Клиенты B2B и B2C, налоги и согласия

| Что | Решение |
|---|---|
| Охват | в эпике оба типа: бизнес с VAT ID и потребитель (D6), на одних тарифах |
| Тип клиента | бизнес: в Checkout введён VAT ID (`tax_id_collection[enabled]=true`); иначе потребитель |
| Расчёт налога | Stripe Tax (`automatic_tax[enabled]=true`), регистрации моковой GmbH в sandbox |
| Цены | `tax_behavior=inclusive`, одна брутто-цена для всех (решение техлида от 2026-11-06): потребитель платит указанную цену с НДС; бизнес платит ту же сумму |
| Reverse charge | только трансграничный B2B в ЕС: VAT ID страны ЕС, отличной от Германии (страна моковой GmbH, §12). Сумма та же, НДС 0, в счёте пометка reverse charge |
| Немецкий VAT ID | продажа внутри страны: Stripe Tax начисляет немецкий НДС, reverse charge не применяется; сумма та же, НДС внутри неё, VAT ID печатается в счёте |
| Вне ЕС | налог по правилам Stripe Tax для страны клиента, сумма та же |
| Проверка VAT ID | Stripe проверяет формат сразу и асинхронно по базе ЕС (`customer.tax_id.updated`); reverse charge Stripe Tax применяет по формату номера и стране |
| Страница цен | до Checkout тип клиента неизвестен, поэтому показывается одна цена с пометкой «включая НДС» и сноска: «Компании из других стран ЕС с действительным VAT ID платят ту же сумму, НДС не начисляется (reverse charge)». Отдельной нетто-цены нет |
| Право отказа 14 дней | только потребителям; при немедленном начале услуги право теряется на потраченную часть |
| Отказ в 14 дней | возвращаем неиспользованный остаток пополнения; по подписке оплату минус ревью, уже сделанные по цене единицы тарифа |

**Согласия перед оплатой.** Checkout умеет один обязательный чекбокс
(`consent_collection[terms_of_service]=required`) с текстом до 1200 символов, а
`custom_fields` бывают только text, numeric и dropdown. Поэтому:

1. На нашей странице до перехода в Checkout: цена, НДС, период, автопродление,
   способ отмены и чекбокс «Прошу начать услугу сразу и понимаю, что теряю право
   отказа на использованную часть». Без чекбокса кнопка оплаты не активна. Время и
   версия текста сохраняются в нашей БД.
2. В Checkout: чекбокс условий (`terms_of_service=required`) с
   `custom_text.terms_of_service_acceptance`, ссылками на Terms и Refund Policy.
3. Для подписки и авто-пополнения (ЕС и США): раскрытие условий до оплаты (п. 1),
   явное согласие (пп. 1-2), отмена онлайн в Customer Portal и ссылкой из ui.
   Квитанции и счета шлёт Stripe.

Тексты пишет legal ([ui#211](https://github.com/larchanka-training/dmc-268-ui-t6/issues/211)),
юридическая проверка вне эпика (§18).

## 10. Stripe

### 10.1. Объекты

| Объект | Использование |
|---|---|
| Customer | один на workspace; `metadata.workspace_id`; создаётся при первой оплате |
| Checkout Session | пополнение (`mode=payment`), подписка (`mode=subscription`), сохранение карты (`mode=setup`) |
| Product, Price | Starter и Pro: фиксированная месячная цена (licensed), `tax_behavior=inclusive`; пополнение: `price_data` на выбранную сумму |
| Subscription | один активный тариф на workspace |
| SetupIntent, PaymentIntent | сохранение карты `off_session`; авто-пополнение |
| Customer Portal | карта, счета, VAT ID, смена Starter/Pro по §4.4, отмена в конце периода |
| Stripe Tax | расчёт и reverse charge |
| Billing Credits, Meters | не используем (§10.2) |

### 10.2. Почему не Billing Credits

- Кредиты применяются только к счёту подписки при его финализации, а не в момент
  прогона: проверку баланса перед прогоном на них не построить.
- Применяются только к позициям с metered-ценами через Meters; к разовым счетам
  (пополнение) и к licensed-ценам не применяются.
- Правила Stripe запрещают выдавать их как stored value, то есть как кошелёк вне
  конкретных услуг.
- Лимит: не больше 100 неиспользованных грантов на клиента.
- Customer Portal не меняет подписки с usage-based ценами, только отменяет их.

Свой журнал даёт проверку до прогона, списание после каждого вызова и порядок
источников §5.

### 10.3. Вебхуки

| Событие | Действие |
|---|---|
| `checkout.session.completed` | `mode=payment`: `payments.status=paid`, грант `top_up`, карта сохранена, если был `setup_future_usage` (§6.1); `mode=setup`: карта сохранена, бонус по `setup_intent.succeeded` |
| `checkout.session.expired` | `payments.status=expired` |
| `checkout.session.async_payment_succeeded`, `..._failed` | в v1 только карты; событие логируется |
| `payment_intent.succeeded`, `payment_intent.payment_failed` | по `metadata.source` нашего PaymentIntent: `auto_recharge`: грант `top_up` или выключение (§6.2); `checkout`: только лог, деньги по `checkout.session.completed`; без нашего `metadata` (PaymentIntent счёта подписки): только лог, гранты по `invoice.paid` |
| `setup_intent.succeeded` | путь «Привязать карту»: карта сохранена; бонус §7, если флаг включён и условия выполнены |
| `invoice.paid` | грант `subscription_grant`: полный для `billing_reason` = `subscription_create` или `subscription_cycle`, на оплаченную сумму для доплаты за повышение (§4.3, §4.4); иначе без гранта |
| `invoice.payment_failed` | отметка в ui, письмо шлёт Stripe |
| `customer.subscription.created`, `.updated`, `.deleted` | тариф workspace, лимит репозиториев |
| `customer.tax_id.created`, `.updated` | статус проверки VAT ID |
| `charge.refunded` | строка `refund` |
| `charge.dispute.created` | авто-пополнение выключается, отметка для оператора |

### 10.4. Идемпотентность

- Входящие: id события Stripe (`evt_...`) уникален в своей таблице квитанций;
  повтор отвечает 200 без действий. Порядок событий не гарантирован: обработчик
  читает актуальный объект из Stripe.
- Бизнес-ключи: уникальные `payments (provider, provider_checkout_id)` и
  `(provider, provider_payment_id)`, `credit_ledger.payment_id`,
  строки списания по `(usage_event_id, grant_id)`, `run_settlement` по
  `(run_id, grant_id)` (§5.1), грант подписки по id счёта, бонус по GitHub user id,
  workspace и fingerprint карты.
- Сторно и возвраты: строка `adjustment` сторно уникальна по `reversal_of_id` (id
  строки списания, которую она возвращает); возврат при деградации по
  `(run_id, grant_id)` с причиной `engine_fallback`. Истечение: `expiry` уникален по
  `grant_id` для основного истечения и по `reversal_of_id` для истечения
  возвращённой суммы (§5.1). Удержание по `run_id` (§5.2).
- Исходящие вызовы Stripe идут с `Idempotency-Key` из нашего id (платёж, попытка
  авто-пополнения), вне транзакции БД (BACKEND_ARCHITECTURE).

### 10.5. Сверка

- Leader-задача раз в сутки читает из Stripe Checkout Sessions, PaymentIntents,
  счета и возвраты за 72 часа и сравнивает с `payments` и грантами. Пропущенное
  применяется тем же идемпотентным обработчиком. Расхождение сумм даёт алерт.
- Инвариант баланса: остаток равен сумме `credit_ledger.amount_usd` по workspace;
  отдельного поля баланса нет либо оно проверяется по сумме.

### 10.6. Досписание после сбоя

Строки списания и итог run пишутся разными транзакциями (§3.3). Если процесс упал
между ними, пропуск находит leader-задача, а не повтор воркера.

- Раз в 5 минут задача ищет:
  - `usage_events` прогонов с `P > 0` без строк списания;
  - run в конечном состоянии (`succeeded`, `failed`, `cancelled`, `skipped`) без
    `run_settlement`, без сторно или с активным удержанием (§5.2), в том числе
    run, которые реконсилер перевёл в `failed` без воркера (T13 `lease_expired`).
- Найденное применяется тем же идемпотентным обработчиком, что и в воркере:
  списание за вызов, итог по §3.4, снятие удержания. Повтор ничего не дублирует
  (§10.4).
- Задача смотрит записи старше 2 минут, чтобы не гоняться с живым воркером.
  Найденный пропуск увеличивает метрику и пишется в лог; пропуск старше часа даёт
  алерт.
- Для списания за вызов нужен id события: `SqlAlchemyUsageLedger.record` сейчас
  возвращает `None` (`usage_ledger.py`), в #371 он возвращает id `usage_events`.

### 11.2. Членство поверх GitHub

- Роли хранятся отдельно от `github_user_workspace_access`: строка роли
  `(workspace_id, github_user_id, role)`. `LinkGitHubInstallations` её не меняет.
- Роль пользователя определяется по шагам, первое совпадение решает:
  1. **Owner из GitHub** (правило ниже). Админ организации управляет ею в GitHub,
     поэтому исключение в продукте его не закрывает.
  2. **Запись об исключении** (`workspace_member_exclusions`: `workspace_id`,
     `github_user_id`, кто и когда удалил): доступа к workspace в продукте нет, даже
     при доступе GitHub.
  3. **Строка роли** по приглашению или назначению: Admin, Billing, Member.
  4. **Доступ GitHub без строки роли:** Member.
  5. Иначе доступа нет.
- **Owner** не назначается в продукте, он выводится из GitHub, как права на
  репозитории (Р-7):
  - установка на организацию: пользователь, который установил App (`sender`
    `installation.created`), пока у него есть доступ GitHub к установке, и каждый
    админ организации в GitHub (роль `admin` в
    `GET /orgs/{org}/memberships/{username}`);
  - установка на личный аккаунт: владелец этого аккаунта.
- Роль админа проверяется через GitHub API при каждом входе и при пересчёте
  членства (`LinkGitHubInstallations`). Пользователь, который перестал быть
  админом организации, теряет Owner при следующей проверке и получает роль по шагам
  2-5. Для этой проверки App нужно право организации `members: read` (сейчас прав
  организации нет, SD §8.2); его добавление в #373.
- Пока никто из Owner ещё не входил (например, payload `installation.created` уже
  удалён по сроку хранения, а админ организации не входил), настройки оплаты,
  тарифа и ролей закрыты, все работают как Member. Первый вход админа организации
  открывает их. Ни оператор, ни порядок входа Owner не назначают.
- Owner может быть несколько. Удалить Owner из workspace в продукте нельзя: его
  права снимаются только в GitHub.
- **Удалить участника** (Owner или Admin; Admin не удаляет Owner) значит снять строку
  роли и записать исключение (шаг 2). Повторный вход через GitHub доступ не
  возвращает. Исключение снимается только принятием нового приглашения для этого
  GitHub user id. Доступ GitHub к репозиториям мы не трогаем; полностью закрыть
  доступ можно только в GitHub.
- **Приглашение без email:** ссылка с одноразовым кодом, срок 7 дней, роль задана
  заранее. Ссылку можно привязать к GitHub login; принять её можно только после
  входа через GitHub, при привязке логин должен совпасть. Ссылку передают любым
  каналом.

### 11.3. Роль и JWT

Роль не кладётся в JWT. На каждом важном действии (оплата, тариф, авто-пополнение,
настройки, команда) роль читается из БД. Смена роли и удаление действуют сразу, а
не через 15 минут жизни access-токена.

## 13. Рассмотренные модели оплаты

| Модель | Плюсы | Минусы |
|---|---|---|
| За место в месяц | привычно, предсказуемо | платят за людей, а не за ревью; маленькие команды переплачивают |
| Расход × наценка | честно к расходу | цена неизвестна до прогона, зависит от провайдера и курса |
| Кредиты Stripe Billing | готовый журнал у Stripe | только при счёте подписки, нет проверки до прогона (§10.2) |
| **Фиксированная цена за ревью + свой баланс** | цена видна заранее, команда бесплатна | свой журнал, сверка и пороги расхода на нас |

Выбрана последняя.

## 14. Последствия

Плюсы:

- клиент знает цену ревью до запуска, команда растёт без доплаты;
- баланс проверяется до прогона, а не после счёта;
- смена модели или провайдера не меняет цену для клиента.

Цена:

- свой журнал, гранты, сроки, сверка со Stripe и идемпотентность вебхуков;
- пороги расхода ограничивают выбор модели (§8.2);
- согласия потребителя частично вне Checkout, на нашей странице;
- роли продукта живут рядом с членством из GitHub.
