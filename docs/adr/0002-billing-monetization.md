## 1. Контекст

Расход LLM считается, но ни с кого не списывается. Права в продукте целиком
выводятся из GitHub. Состояние `main`, на которое опирается ADR:

- `payments` (`provider`, id сессии и платежа, `amount_usd`, `status` `pending |
  paid | failed | expired`) и `credit_ledger` (виды `top_up | usage_debit |
  adjustment`) созданы миграцией 0001, код их не читает и не пишет
  ([models.py](../../app/modules/billing/infrastructure/models.py)). Суммы в USD,
  `Numeric(12, 6)`.
- `usage_events.cost_usd` пишется после каждого вызова LLM своей короткой
  транзакцией и переживает откат прогона (AGENTS.md, исключение для
  `SqlAlchemyUsageLedger.record`). `run_id` NOT NULL.
- Лимит стоимости прогона: fast $0.50, deep $3 на все попытки, проверка до каждого
  вызова ([PIPELINE_SPEC §4.5](../PIPELINE_SPEC.md#45-лимиты-вызовов-и-стоимости)).
- `budget_paused`: Run `skipped` при claim, если остаток дневного бюджета меньше
  лимита fast. `workspaces.daily_budget_usd = 0` значит «лимит не задан»
  (`handle_review_run.py`, SD §11).
- Членство в workspace: `github_user_workspace_access`, пересчитывается из GitHub
  при каждом входе (`LinkGitHubInstallations`, `revoke_unlisted`). Ролей нет.
- Access JWT живёт 15 минут (`ACCESS_TOKEN_LIFETIME`), несёт список Workspace
  (SD §6.5).
- Payload вебхуков `installation` хранится в `webhook_events` 30 дней после
  завершения квитанции (SD §13).

## 2. Решение кратко

- Свой предоплаченный баланс в USD в `credit_ledger` остаётся источником правды.
  Stripe принимает платежи и ведёт подписки. Stripe Billing Credits не используем
  (§10.2).
- Клиент платит за ревью, а не за места. Вся команда workspace бесплатна.
- Цена ревью фиксирована по тарифу и движку. Расход LLM считаем внутри и не
  показываем клиенту.
- Тарифы: Pay as you go, Starter $19/мес, Pro $49/мес.
- Нулевой баланс блокирует новые прогоны с причиной `balance_exhausted`.
- Роли продукта Owner, Admin, Billing, Member поверх доступа GitHub. Роль не в JWT,
  проверяется в БД.
- Налоги: Stripe Tax, цены включают НДС и одинаковы для всех. Бизнес из другой
  страны ЕС с VAT ID платит ту же сумму с НДС 0 (reverse charge), бизнес из
  Германии платит с немецким НДС.

## 3. Деньги

### 3.1. Валюта и точность

| Что | Решение |

| Stripe | целые центы; пополнение в целых долларах |
| Показ клиенту | до цента; цена единицы тарифа до десятой доли цента ($0.136); хранимое значение в 6 знаках (§3.2) |

### 3.2. Цена за ревью (изменение D1)

D1 говорит «расход LLM × наценка». ADR меняет D1, изменение принято техлидом в
ревью этого PR: **клиент платит фиксированную цену за ревью** по своему тарифу и
движку (§4). Расход каждого прогона по `usage_events.cost_usd` и его доля в цене
считаются и логируются внутри, для сверки и пересчёта цен. Причина: клиент видит
цену до запуска, сумма не зависит от провайдера и курса EUR, а пороги расхода
(§8.2) ниже цены прогона с НДС на любом тарифе.

Цена прогона `P`:

```
P = цена_движка(тариф, движок) × множитель
цена_движка = цена_единицы(тариф) × единиц_движка   (fast 1, deep 5)
множитель = 1 + надбавка_большого_PR
```

Два термина: **цена единицы** это цена одного fast-ревью на тарифе, **цена
движка** это цена ревью выбранным движком с множителем 1 (fast: цена единицы,
deep: 5 цен единицы).

- `цена_единицы`: §4.1. Хранится как цена тарифа, делённая на число ревью в пакете,
  с округлением вниз до 6 знаков: PAYG $0.200000, Starter $0.135714 (19/140), Pro
  $0.116666 (49/420). Так 140 и 420 ревью целиком помещаются в грант $19 и $49
  (остаток $0.00004 и $0.00028 истекает с грантом). Клиенту показывается
  округлённая цена $0.136 и $0.117 (§3.1).
- Надбавка: +1 к множителю за каждые начатые 1000 строк сверх 1000 (§4.2).
- Тариф и цена движка фиксируются при первом claim. Множитель и признак
  summary-only известны только после загрузки и фильтрации diff (`vcs.fetch_diff`,
  PIPELINE_SPEC §2), поэтому `P` фиксируется там и дальше не меняется, кроме
  деградации (§3.3). Все три значения хранятся с удержанием run (§5.2), порог
  расхода, доля 25% и задача §10.6 читают их оттуда.

### 3.3. Момент и формула списания

Гейты, удержания и списания ниже действуют только при включённом
`billing_enforcement` (§16).

- **Гейт 1, claim** (T4/T5): доступный для движка остаток (§5.2) не меньше цены
  движка (множитель 1). Тогда claim в той же транзакции удерживает цену движка
  (§5.2). Иначе `skipped`, `balance_exhausted` (§8); исключение: deep-run, которому
  хватает на цену fast, идёт как fast (§8.1). Строк PR на этом шаге ещё нет.
- **Повторный claim** того же run (T9, T12 возвращают его в `queued`) нового
  удержания не пишет и гейты по уже зафиксированной `P` не повторяет; если он
  заканчивается `skipped` или `cancelled`, итог как у `cancelled` (§3.4). Механика:
  #371.
- **Гейт 2, после `vcs.fetch_diff`**, до первого вызова LLM: известны множитель и
  summary-only. `P = 0` только для маршрута, на котором модель не вызывается:
  summary-only, T19 `no_changes` / `all_changes_ignored` и backend none snapshot
  path (v4, v5). Тогда удержание снимается, отказа по балансу или дню нет даже на
  большом PR. Legacy (≤ v3) с none вызывает модель (`too_large`,
  `unsupported_change`, PIPELINE_SPEC §2) и считает обычную `P`. Иначе доступный
  остаток и остаток дня (§8.1) вместе с удержанием этого run не меньше `P`:
  удержание поднимается до `P`. Если не хватает, удержание снимается и
  `running → skipped` с 0 вызовов LLM, по образцу T19: `balance_exhausted` при
  нехватке баланса, `budget_paused` при нехватке остатка дня. Deep, которому не
  хватает на `P` deep, но хватает на `P` fast с тем же множителем, идёт как fast
  (деградация PIPELINE_SPEC §5.3) до первого вызова LLM, с удержанием `P` fast и
  текстом summary из §8.1. Пример: PAYG deep, доступно $2.50, PR на 2500 строк: `P`
  deep $3.00 не помещается, `P` fast $0.60 помещается, ревью fast. Переход
  добавляется в PIPELINE_SPEC §1 вместе с #371.
- **После каждого вызова LLM** пишется списание, связанное с `usage_event_id`
  этого вызова: `max(0, min(P × 25%, P - уже_списано_по_run))`. Доля не зависит от
  расхода вызова, поэтому сумма не раскрывает расход. Строка с нулевой суммой не
  пишется.
- **При успехе** (T14 `succeeded`) пишется доплата до `P` (`run_settlement`).
  Повторные попытки внутри run цену не увеличивают.
- **Run без вызовов LLM бесплатен.** Правило задаётся через вызовы, а не через
  итог: если у run нет ни одной строки `usage_events`, при итоге `P = 0`,
  `run_settlement` не пишется, удержание снимается (§3.4).
- **Деградация deep → fast** (PIPELINE_SPEC §5.3): с момента деградации `P`
  пересчитывается по цене fast с тем же множителем, порог расхода тоже fast и
  считается только по расходу после деградации (§8.2). Клиент платит не больше
  цены fast: при `succeeded`, `cancelled` и `skipped` списанное сверх нового `P`
  возвращается (`adjustment` с причиной `engine_fallback`), при `failed` итог 0
  (§3.4).
- **Инварианты журнала.** Механику (распределение по грантам, блокировки, ключи
  идемпотентности, удержания и их снятие, повторный claim, досписание, истечение,
  DDL) задаёт и ревьюит #371; эти правила она не нарушает:
  - овердрафт 0: прогон тратит только удержанное, отрицательный остаток бывает
    лишь после возврата денег или спора (§5);
  - каждое списание, сторно, возврат и истечение идемпотентны: повтор ничего не
    дублирует;
  - сетевых вызовов (LLM, GitHub, Stripe) внутри транзакции БД нет;
  - одна точка записи: **второе узкое исключение** из правила «commit делает
    только use case», рядом с `SqlAlchemyUsageLedger.record`, одним текстом в
    `AGENTS.md`, `.agents/rules/backend.md` и BACKEND_ARCHITECTURE (§15):
    единственная точка записи модуля `billing` пишет только строки списаний run
    (`credit_ledger`) и снятие его удержания при итоге run, своей короткой транзакцией
    сразу после `usage_events`, после commit конечного состояния run или позже из
    leader-задачи досписания, идемпотентно; строки, ключи и механика удержаний в #371.
    Удержание, которое пишется при claim (гейт 1), поднимается или снимается на гейте 2
    и снимается при выключении `billing_enforcement`, пишет обычный use case (claim,
    гейт 2, выключение флага) в собственной транзакции этого use case через порт модуля
    `billing`; истечение грантов тоже пишет обычный use case. В исключение они не
    входят. Исключения не распространяются на обычные repositories и не разрешают
    сетевых вызовов внутри транзакции БД.

### 3.4. Неудачный и отменённый прогон

| Итог run | Что списано |
|---|---|
| `succeeded` с хотя бы одним вызовом LLM | ровно `P` |
| любой `failed`, с любым `error_code` (ошибка LLM, таймаут, баг, verifier, `github_forbidden`, `pr_base_changed`, `llm_context_overflow` и другие) | 0: каждое списание run сторнируется строкой `adjustment` в тот же грант (§5.1) |
| `cancelled` (новый `head_sha`, PR закрыт, `POST /api/runs/{id}/cancel`) | уже списанное по §3.3, без доплаты; после деградации deep → fast не больше нового `P` |
| `skipped` без вызовов LLM (гейт 1, гейт 2, `budget_paused`) | 0 |
| `skipped` после вызовов LLM на прошлой попытке run | уже списанное, без доплаты, как `cancelled` |
| summary-only, любая из причин `diff_too_large` (в том числе PR больше 3000 строк, §4.2), `diff_inventory_incomplete`, `no_reviewable_files` (PIPELINE_SPEC §2) | 0 |
| `succeeded` без вызовов модели (backend none snapshot path v4, v5: 0 LLM, `findings=[]`, coverage none, PIPELINE_SPEC §2); legacy (≤ v3) с none вызывает модель и платит `P` (§3.3) | 0 |
| любой итог, если у run нет ни одной строки `usage_events` | 0 (§3.3) |

### 3.5. Что видит клиент

Клиент видит **списанную сумму** (`chargedUsd`) и остаток баланса, никогда не
`cost_usd`, лимиты расхода и токенов прогона. Поля `contracts/openapi.yaml` на
`main`, которые сейчас отдают клиенту расход, и решение по каждому (реализация
#310 и #371):

| Схема и поле | Где отдаётся | Решение |
|---|---|---|
| `RunUsage.costUsd` | прогон в списке и деталях | заменяется на `chargedUsd` из `credit_ledger` ([#310](https://github.com/larchanka-training/dmc-268-api-t6/issues/310)) |
| `RunBudget.costUsd`, `RunBudget.costLimitUsd`, `RunBudget.tokenLimit` | детали прогона | убираются из ответа клиенту; расход, порог и лимит токенов прогона видит только оператор |
| `MetricsTotals.costUsd` | `GET /api/metrics/summary` | заменяется на `chargedUsd` за период |
| `MetricsDay.costUsd` | `GET /api/metrics/summary`, по дням | заменяется на `chargedUsd` за день |
| шаги `llm.call` в трейсе: `usage.cost`, `usage.cost_currency` в ответе шага, `fx` в запросе шага | `GET /api/runs/{run_id}/actions`, `/actions/{index}/response` | вырезаются из ответа клиенту при отдаче шага; в БД и для оператора остаются. Токены в `usage` остаются |
| `WorkspaceDailyBudget.spentTodayUsd`, `dailyBudgetUsd` | `GET /api/metrics/summary` | считаются по списанному, а не по расходу: дневной лимит workspace ограничивает списания за день (§8.1) |

- Токены (`tokensIn`, `tokensOut`) остаются: это техническая метрика прогона, а не
  сумма в деньгах.
- `cost_usd` остаётся во внутренних метриках оператора (Prometheus, логи), не в
  API клиента.
- [ui#186](https://github.com/larchanka-training/dmc-268-ui-t6/issues/186): страницы
  «Аудит» и «Аналитика» показывают списанное, а не расход LLM.

## 4. Тарифы

### 4.1. Цены

| Тариф | Цена | Включено | Fast | Deep | Graph RAG | Репозитории |
|---|---|---|---|---|---|---|
| Pay as you go | только пополнения | - | $0.20 | $1.00 (5 единиц) | нет | без лимита |
| Starter | $19/мес | 140 ревью | $0.136 (хранится $0.135714) | 5 единиц | да | до 5 |
| Pro | $49/мес | 420 ревью | $0.117 (хранится $0.116666) | 5 единиц | да | без лимита |

- Названия тарифов финальные: Pay as you go, Starter, Pro. Enterprise вне эпика #369.
- Единица тарифа: одно fast-ревью. Deep стоит 5 единиц своего тарифа, как в PAYG
  ($1.00 = 5 × $0.20).
- Deep доступен во всех тарифах. Graph RAG только в подписке. Лимит
  репозиториев: Starter до 5, остальные без лимита.
- Сверх пакета ревью списываются с купленного баланса по цене единицы своего
  тарифа.
- Мест нет: число участников не ограничено.
- Скидка к PAYG: Starter 32%, Pro 42%.
- Отдельного тарифа для бизнеса нет: компании покупают Starter или Pro.
- Enterprise (SSO, договор, SLA): по запросу, вне эпика.

### 4.2. Надбавка за большой PR

- Строки PR: добавленные плюс удалённые строки diff после исключений политики.
- 1-1000 строк: множитель 1. Каждые начатые 1000 строк сверх 1000: +1. Пример для
  PAYG: fast на 1500 строк $0.40, deep на 2500 строк $3.00.
- Больше 3000 строк: ревью только summary без LLM, $0.

### 4.3. Подписка

- Подписка Stripe на месяц, автопродление. Повышение с нашего экрана, понижение и
  отмена через Customer Portal (§4.4, §10.1).
- Включённые ревью начисляются грантом `subscription_grant` в USD ($19 и $49) по
  `invoice.paid` только для счетов с `billing_reason` = `subscription_create` или
  `subscription_cycle`, один грант на счёт (§10.4).
- Счета с другим `billing_reason` полного гранта не дают. Единственное исключение
  описано в §4.4: доплата за повышение даёт грант на оплаченную сумму. Счёт с нулевой
  суммой (`amount_paid = 0`) грант не даёт.
- Отмена действует в конце оплаченного периода; до него тариф работает.
- **Неоплата счёта подписки** (стандартный путь Stripe):
  - `invoice.payment_failed` по счёту `subscription_cycle`: подписка в статусе
    Stripe `past_due`, Stripe повторяет списание (Smart Retries). Тариф работает,
    гранта за этот счёт нет, баннер для Owner, Admin и Billing «Оплата подписки не
    прошла» с кнопкой в Customer Portal;
  - конец повторов: в настройках Stripe (Revenue recovery) задано «отменить
    подписку» и «пометить счёт как uncollectible». По `customer.subscription.deleted`
    тариф снимается, workspace переходит на PAYG и платит с баланса; остаток
    прошлого гранта живёт до своего срока (§5);
  - поздний `invoice.paid` по счёту, у которого подписка уже `canceled`: тариф не
    возвращается и `subscription_grant` не пишется; оплаченная сумма зачисляется
    грантом `top_up` (12 месяцев), чтобы деньги клиента не пропали. Вернуть тариф
    можно только новой подпиской (§4.4);
  - первый счёт (`subscription_create`) не оплачен: подписка `incomplete`, тариф
    не начинается и гранта нет; Stripe закрывает её как `incomplete_expired`,
    workspace остаётся на прежнем тарифе;
  - `invoice.paid` по счёту в `past_due` до конца повторов: обычный грант по
    `billing_reason`, подписка снова `active`.

### 4.4. Смена тарифа

| Переход | Когда действует | Деньги и гранты |
|---|---|---|
| PAYG → Starter или Pro | сразу, новая подписка | грант по `subscription_create` (§4.3) |
| Starter → Pro (повышение) | после оплаты доплаты | наш экран тарифа вызывает `subscriptions.update` с `payment_behavior=pending_if_incomplete` и `proration_behavior=always_invoice`: Stripe выставляет доплату за остаток периода и меняет тариф только после её оплаты. По `invoice.paid` (`billing_reason=subscription_update`) пишется `subscription_grant` на оплаченную сумму со сроком текущего гранта; цена единицы и лимиты Pro действуют с `customer.subscription.pending_update_applied`. Доплата не прошла: Stripe держит изменение до 23 часов, потом аннулирует счёт (`customer.subscription.pending_update_expired`); workspace остаётся на Starter, баннер «Повышение не оплачено» для Owner, Admin и Billing |
| Pro → Starter (понижение) | в конце оплаченного периода | до конца периода работает Pro; новый грант $19 по `subscription_cycle`; остаток гранта Pro живёт до своего срока |
| Подписка → PAYG (отмена) | в конце оплаченного периода | §4.3 |

- Customer Portal настраивается так: повышение в Portal выключено (оно идёт только
  с нашего экрана, чтобы было `pending_if_incomplete`), понижение и отмена в конце
  периода (`schedule_at_period_end`). Можно ли в Portal включить понижение без повышения,
  исполнитель #372 проверяет по документации Stripe до реализации; если нельзя,
  понижение тоже идёт с нашего экрана.
- **Starter при числе репозиториев больше 5.** Правило одно для любого пути в
  Starter: понижение Pro → Starter, переход PAYG → Starter и новая подписка Starter
  после отмены. До оплаты или смены страница тарифа предупреждает и даёт Owner или
  Admin выбрать 5 репозиториев. После начала Starter ревью идут только в выбранных
  5; если выбора нет, остаются 5 с последними прогонами. Остальные репозитории
  остаются подключёнными, их прогоны `skipped` с `error_code = plan_repo_limit`.
- **Коды отказа по лимитам тарифа.** Сервер проверяет каждый лимит сам:

| Код | Когда |
|---|---|
| `plan_repo_limit` | Starter: включение 6-го репозитория (ответ API) или прогон в репозитории сверх лимита (`skipped`) |
| `plan_graph_rag_unavailable` | PAYG: включение Graph RAG (ответ API). Если RAG уже включён, а тариф стал PAYG, ревью идёт без RAG, отметка в трейсе с этим кодом |
| `balance_exhausted` | остаток меньше цены (§3.3, §8.1) |

## 5. Кредиты: виды, порядок и сроки

| Источник | Вид в `credit_ledger` | Срок | На что |
|---|---|---|---|
| Подписка | `subscription_grant` (новый) | до конца периода счёта плюс 1 месяц (ниже) | fast и deep |
| Бонус | `promo` (новый) | 30 дней | только fast |
| Пополнение | `top_up` | 12 месяцев | fast и deep |

- **Порядок списания:** подписка, затем бонус, затем купленные. Внутри источника
  раньше истекающий грант первым.
- **Точка отсчёта срока.** `expires_at` гранта подписки = конец периода позиции
  подписки в счёте (`invoice.lines[].period.end`) плюс 1 месяц. Доплата за
  повышение (§4.4) получает `expires_at` текущего гранта подписки. Поздний
  `invoice.paid` по отменённой подписке даёт `top_up` со сроком 12 месяцев от
  оплаты (§4.3). `top_up` и `promo` считаются от момента начисления.
- **Перенос остатка подписки:** неиспользованный `subscription_grant` живёт ещё один
  месяц после своего цикла и складывается с грантом следующего цикла; по порядку
  выше первым списывается старый. Дальше не переносится: остаток сгорает строкой
  `expiry` (новый вид). При отмене подписки и переходе на PAYG (§4.3) уже выданный
  грант доживает до своего срока: он оплачен.
- **Истечение** списывает только свободный остаток гранта; удержанная часть
  истекает после снятия удержания. Пишет его leader-задача раз в час (§10.6)
  обычным use case.
- **Возврат денег** (`charge.refunded`, в том числе частичный и отказ в 14 дней,
  §9) пишет строку `refund` (новый вид) на каждый объект возврата Stripe, со знаком
  минус, в грант этого платежа (`top_up` или `subscription_grant`). Сумма возвратов
  и спора по гранту не больше суммы гранта. Доплата при успехе пишет
  `run_settlement` (новый вид).
- **Спор по платежу** (chargeback): по `charge.dispute.created` в грант этого
  платежа пишется `adjustment` с причиной `dispute` на сумму спора, даже если
  остаток уйдёт в минус. Выигранный спор (`charge.dispute.closed`, `status=won`)
  его сторнирует, проигранный ничего не добавляет.
- **Возврат и спор на истёкшем гранте** пишутся на полную сумму (так они сходятся
  со Stripe, §10.5), но минус остаётся только на потраченную часть: сгоревшее уже
  не было у клиента.
- **Долг** это отрицательный остаток гранта после возврата или спора. Он входит в
  доступный остаток для любого движка, даже если грант истёк, и гасится первым
  следующим грантом `top_up` или `subscription_grant`. Бонус `promo` долг не гасит:
  он только для fast и не деньги клиента. Отказ в 14 дней долга не создаёт (§9).
- Строки, ключи и DDL новых видов: #371 (журнал), #372 (подписка).

### 5.1. Распределение списания по грантам

- Каждая строка списания ссылается на один грант; списание больше остатка гранта
  делится на строки по порядку §5.
- Сторно (неудачный run, деградация) возвращает каждую строку в тот же грант:
  возврат сохраняет срок и движки исходного гранта, бонус возвращается бонусом.
  Возвращённое в истёкший грант сразу истекает.
- Остаток гранта: сумма гранта плюс все строки, которые на него ссылаются.
- Ключи и порядок записи: #371.

### 5.2. Удержание на время прогона

Параллельные прогоны не могут потратить один и тот же остаток: каждый run держит
удержание (таблица `balance_holds`, #371), и следующий claim видит уже
уменьшенный остаток.

- Одно удержание на run на все его попытки. Оно равно `P` минус уже списанное по
  run и снимается при итоге run; если воркер не дожил до итога, его снимает задача
  досписания §10.6.
- **Доступный остаток** для движка = долг workspace (отрицательные остатки
  грантов, §5) плюс остатки действующих грантов, подходящих движку, минус их
  часть под активными удержаниями других run. Грант с наступившим сроком не
  считается сразу, даже если `expiry` ещё не написан. Гейты §3.3 смотрят на
  доступный остаток, `budget_paused` на остаток дня (§8.1); свой run удержание
  не вычитает ни там, ни там.
- **Овердрафт:** 0. Удержание покрывает полную цену run, сторно и деградация её
  только уменьшают, истечение не трогает удержанную часть, а claim, гейт 2 и
  истечение одного workspace идут по очереди. Отрицательный остаток возможен
  только после возврата денег или спора на уже потраченную часть платежа (§5).
- Распределение удержаний по грантам, блокировки, повторный claim и ключи: #371.

## 6. Пополнение и авто-пополнение

### 6.1. Пополнение

- Любая сумма от $10 до $500 в целых долларах, Stripe Checkout `mode=payment`.
- В v1 только карты: каждая сессия Checkout (пополнение, подписка, сохранение
  карты) создаётся с `payment_method_types=[card]` (§10.1), поэтому отложенных
  способов оплаты нет и деньги приходят в `checkout.session.completed`.
- Грант `top_up` пишется по `checkout.session.completed` со статусом оплаты `paid`.
  Налог и счёт: §9. В `metadata` сессии и её PaymentIntent
  (`payment_intent_data.metadata`) пишутся `workspace_id` и `source=checkout`.
- Карту можно сохранить двумя путями, оба уже в первой версии:
  - **кнопка «Привязать карту»** на экране «Баланс и тариф»: Checkout `mode=setup`
    (SetupIntent `usage=off_session`), без списания. Событие `setup_intent.succeeded`.
    В `setup_intent_data.metadata` сессии пишутся `workspace_id`, `github_user_id`
    (кто нажал кнопку) и `source=link_card`. Только этот путь даёт бонус (§7);
  - **при пополнении**, если клиент отметил «Сохранить карту» на нашей странице до
    Checkout (§9, п. 4): `payment_intent_data.setup_future_usage=off_session`. Карта
    сохраняется вместе с оплатой; событие `checkout.session.completed`, карта берётся
    из `payment_method` его PaymentIntent. Бонуса этот путь не даёт.
- Сохранённая карта нужна авто-пополнению (§6.2), чтобы не вводить её повторно.
- **Карта авто-пополнения одна** на workspace: её выбирают на экране включения
  (§9, п. 3), id хранится в настройках авто-пополнения. Другие сохранённые карты
  авто-пополнение не списывает.

### 6.2. Авто-пополнение

| Параметр | Значение |
|---|---|
| По умолчанию | выключено |
| Кто включает | Owner, Admin или Billing; порог и сумму задаёт пользователь |
| Порог | от $5 до $100 и строго меньше суммы пополнения: без долга (§5) остаток после платежа выше порога; настройки с порогом не меньше суммы не сохраняются |
| Когда срабатывает | по уровню: общий доступный остаток для fast (§5.2: все действующие гранты, включая подписку и бонус, минус удержания; тот же, что в баннере низкого баланса §8.1) ниже порога, авто-пополнение включено, нет попытки в процессе и остаток потолка месяца не меньше суммы. Проверка идёт после commit каждого списания (вызов Stripe вне транзакции), после возврата денег, при `skipped` с `balance_exhausted`, при включении и на каждом проходе задачи §10.6 (раз в 5 минут, в том числе в начале месяца UTC). Возврат по отказу в 14 дней и спор проверку не запускают: они выключают авто-пополнение (ниже). Только при включённом `billing_enforcement` (§16) |
| Сумма | от $10 до $500, как обычное пополнение, и не больше месячного потолка: настройки с суммой больше потолка не сохраняются |
| Месячный потолок | по умолчанию $200 за календарный месяц UTC; пользователь меняет в пределах $10-$500 |
| Платёж | разовый счёт Stripe Invoicing без Checkout: позиция на сумму с `tax_behavior=inclusive` (одна брутто-цена, §9), `automatic_tax[enabled]=true`, `collection_method=charge_automatically`, карта авто-пополнения как `default_payment_method`, `metadata.source=auto_recharge` |
| Карта | одна карта авто-пополнения (§6.1). Сменить её можно только на нашем экране включения, с новым согласием (§9, п. 3). Смена карты по умолчанию в Customer Portal её не меняет; удаление этой карты (`payment_method.detached`) выключает авто-пополнение до нового согласия |
| Отказ карты | авто-пополнение выключается; баннер в ui (ниже). Включить снова с теми же параметрами и той же картой можно без нового согласия (оно на эти параметры уже есть, §9 п. 3); с новыми параметрами или картой нужно новое |
| Требуется 3-D Secure | то же: выключается, баннер; клиент платит вручную через Checkout |
| Нет адреса для налога | у Customer нет адреса для Stripe Tax (карта привязана до сбора адреса в Checkout): попытка не проходит, авто-пополнение выключается, баннер «Укажите адрес для счёта: пополните вручную» (ручное пополнение через Checkout соберёт адрес); включить снова можно новым согласием |
| Потолок достигнут | попытка не идёт, если сумма больше остатка потолка месяца; до конца месяца не срабатывает, отметка в ui; в начале месяца проверка по уровню запускает его снова |
| Спор или отказ в 14 дней | спор по платежу или отказ от пополнения или авто-пополнения (§9) выключает авто-пополнение до нового согласия |

Правила платежа (шаги счёта, ключи каждого вызова Stripe, аннулирование, исход
каждого отказа и зависшей попытки задаёт и ревьюит
[#513](https://github.com/larchanka-training/dmc-268-api-t6/issues/513)):

- Попытка сначала пишется строкой `payments` (`source=auto_recharge`,
  `status=pending`) в короткой транзакции, вызовы Stripe идут после неё, вне
  транзакции, каждый со своим `Idempotency-Key` от id попытки.
- **Одна попытка на workspace:** пока попытка не закончилась, новая не создаётся
  (индекс в БД).
- Деньги только по вебхуку: `invoice.paid` даёт грант `top_up`. Отказ оплаты
  выключает авто-пополнение, неоплаченный счёт аннулируется, чтобы его нельзя было
  оплатить позже; если оплата всё же пришла, деньги зачисляются.
- Зависшую попытку доводит или закрывает задача §10.6, так что она не держит
  workspace дольше суток.
- **Защита от серии.** Если после оплаченной попытки остаток всё ещё ниже порога
  (например, долг после возврата больше суммы пополнения), авто-пополнение
  ставится на паузу с баннером «Сумма авто-пополнения меньше долга, пополните
  вручную»; пауза снимается ручным пополнением или новым согласием.
- Месячный потолок считается по попыткам в процессе и оплаченным за календарный
  месяц UTC.
- **Как клиент узнаёт об отказе.** Писем мы не шлём: своей рассылки в эпике нет
  (#369), а email пользователей у нас нет (вход через GitHub App). Вместо письма:
  - баннер на всех страницах workspace для Owner, Admin и Billing: «Авто-пополнение
    выключено: карта отклонена» (или «нужно подтверждение банка») и кнопка
    «Пополнить»; баннер скрывается после успешного пополнения или повторного
    включения;
  - на экране «Баланс и тариф» состояние авто-пополнения: включено или выключено,
    причина и дата последнего отказа, остаток месячного потолка.
- Пополнения баланса по порогу в Stripe Billing в документации не найдено, поэтому
  порог проверяем мы.
- Реализация отдельной задачей позже, вне #371: #513. Карта сохраняется уже в
  первой версии (§6.1).

## 7. Бонус новым

- **Фича-флаг** `billing_signup_bonus`, по умолчанию выключен. Пока флаг выключен,
  бонус не начисляется и не обещается в ui. Включает команда.
- **Когда начисляется:** $5 только после привязки карты кнопкой «Привязать карту»
  (Checkout `mode=setup`, §6.1), по `setup_intent.succeeded`. Получателя и
  workspace обработчик берёт из `metadata` SetupIntent; без `source=link_card`,
  `workspace_id` и `github_user_id` бонуса нет, даже если флаг включён: другой
  SetupIntent того же Customer бонус не даёт. На этом пути карта не
  списывается. Карта, сохранённая при пополнении, бонуса не даёт: так у бонуса одно
  событие и одно место в ui.
- **Кому:** GitHub-пользователю, который нажал кнопку (роль Owner, Admin или
  Billing, §11.1). Не на установку и не на организацию: организаций можно создать
  сколько угодно, а id установки меняется при переустановке.
- **Ограничения:**
  - один бонус на GitHub user id: повторная установка бонус не даёт;
  - один бонус на workspace: второй участник со своей картой бонус не получает;
  - один бонус на карту: по `card.fingerprint` из Stripe, та же карта на другом
    аккаунте бонус не даёт;
  - аккаунту GitHub больше 30 дней (`created_at` из GitHub API).
- Только fast, срок 30 дней. Пишется грантом `promo` на этот workspace. Факт
  выдачи хранится по GitHub user id, workspace и fingerprint карты.
- Реализация в #371.

## 8. Нулевой баланс и лимиты прогона

### 8.1. Нулевой баланс

- **Флаг оплаты.** Всё ниже действует, только когда включён `billing_enforcement`;
  пока он выключен, ревью бесплатны, как на `main` (§16).
- **Новые прогоны:** два гейта §3.3. При claim доступный остаток для движка (§5.2)
  меньше цены движка: Run `skipped`, `error_code = balance_exhausted`; проверка
  идёт после `budget_paused`. После `vcs.fetch_diff` остаток вместе с удержанием
  run меньше `P`: `running → skipped` с тем же кодом.
- **Deep при балансе только на fast** (при claim и на гейте 2, §3.3): если
  доступного остатка для deep меньше цены движка deep, а для fast хватает
  (например, остался только бонус, §5), Run идёт как fast по цене fast. В summary
  PR: «На deep не хватило баланса, выполнено fast-ревью» и ссылка на пополнение.
  Если не хватает и на fast: `balance_exhausted`. До фазы 3 API принимает только
  fast (PIPELINE_SPEC §5.3), правило нужно для #371 заранее.
- **Что видит клиент** (GitHub): check-run `completed/skipped` с текстом «Баланс
  исчерпан, ревью не запущено» и ссылкой на пополнение; комментарий в PR с той же
  ссылкой не чаще раза в сутки на PR (`code_changes.balance_notice_at`, #371);
  причина в ui. Для GitLab и Bitbucket пока только причина в ui (§19).
- **Баннер низкого баланса** для Owner, Admin и Billing на всех страницах
  workspace: доступный остаток для fast (§5.2) меньше 10 цен единицы тарифа (PAYG
  $2.00); при остатке меньше цены единицы текст «Баланс исчерпан». Кнопка
  «Пополнить». Скрывается, когда остаток снова не меньше порога.
- **Начатые прогоны** доделываются: их цена уже удержана (§5.2), овердрафт 0.
- **`daily_budget_usd`** остаётся отдельным дневным лимитом workspace, 0 значит
  «лимита нет». Он считается по списанному за день, а не по расходу LLM (§3.5):
  клиент задаёт лимит в тех же деньгах, которые платит. Лимиты fast $0.50 и deep
  $3 в нём больше не участвуют (§8.2). Правила ниже действуют только при
  `daily_budget_usd > 0`, как на `main` (`handle_review_run.py`).
  **Остаток дня** = `daily_budget_usd` минус списанное за день минус активные
  удержания workspace, кроме удержания этого же run (§5.2).
  - При claim: остаток дня меньше цены единицы тарифа: `skipped`,
    `budget_paused`; deep-Run при остатке дня меньше цены движка deep, но не меньше
    цены единицы, идёт как fast (PIPELINE_SPEC §5.3). Пример: PAYG, остаток дня
    $0.40: fast за $0.20 запускается, deep за $1.00 деградирует в fast.
  - На гейте 2 остаток дня вместе с удержанием этого run не меньше `P`, иначе
    `running → skipped` с `budget_paused` (deep сначала пробует `P` fast, §3.3).
    Пример: PAYG fast, остаток дня $0.20, PR на 2500 строк (`P` = $0.60): claim
    проходит, гейт 2 даёт `budget_paused`. Дневной лимит не превышается ни на
    один прогон.

### 8.2. Пороги расхода прогона

Пороги заменяют лимиты PIPELINE_SPEC §4.5 и SD §13 (fast $0.50, deep $3) при
включённом `billing_enforcement` (§16). Порог одинаков на всех тарифах, чтобы скидка подписки не
меняла качество ревью, и ниже самой низкой цены ревью с НДС (Pro по хранимой
цене движка: fast $0.116666, deep $0.583330). Порог сравнивается с брутто-ценой,
а не с выручкой:

| Движок | Порог расхода на прогон |
|---|---|
| fast | $0.11 × множитель |
| deep | $0.55 × множитель |

- Множитель тот же, что в цене (§3.2): большой PR получает порог больше в той же
  пропорции, что и цену.
- Порог передаётся в существующую проверку шлюза перед каждым вызовом
  (`run_cost_limit_usd`, PIPELINE_SPEC §4.5) как лимит этого прогона, а не как
  константа движка. До гейта 2 (§3.3) вызовов LLM нет, поэтому множитель к первому
  вызову уже известен.
- При деградации deep → fast с этого момента действует порог fast, и против него
  считается только расход после деградации: лимит прогона в шлюзе становится
  `расход до деградации + $0.11 × множитель`. Шлюз сейчас считает `spent` по всему
  run и сравнивает с лимитом текущего движка (`gateway.py`, PIPELINE_SPEC §4.5),
  поэтому без этой поправки первый fast-вызов после дорогого deep дал бы
  `BUDGET_EXCEEDED` и `failed` с итогом 0. Расход deep до деградации может
  превысить цену fast; этот редкий случай сбоя deep мы берём на себя, клиент
  платит цену fast (§3.3).
- Без деградации расход прогона на пороге остаётся меньше его цены с НДС на любом
  тарифе. **Выручка без НДС может быть ниже порога.** У Pro это так при любой ставке
  НДС больше 6,06% (0.116666 / 0.11 = 1.0606 и 0.583330 / 0.55 = 1.0606), то есть
  почти при любой ставке ЕС: при 19% выручка fast $0.098 и deep $0.490 против
  порогов $0.11 и $0.55. Starter уходит ниже порога при ставке от 23,4% (0.135714 /
  0.11 = 1.2338), PAYG ни при какой ставке ЕС. При reverse charge выручка равна
  цене. Этот случай техлид принял решением от 2026-11-06: пороги и цены не меняются,
  доля таких прогонов проверяется на сверке цен через 30 дней (ниже).
- Расход считается по цене фактического провайдера вызова, а не самого дешёвого.
- Модель и провайдер выбираются по eval
  [#512](https://github.com/larchanka-training/dmc-268-api-t6/issues/512) в пределах
  этих порогов. Если ни одна пригодная модель не укладывается, цены пересчитываются
  новым ADR, пороги не поднимаются молча.
- Через 30 дней после запуска на staging цены сверяются по фактическим
  `usage_events`.

## 9. Клиенты B2B и B2C, налоги и согласия

| Что | Решение |
|---|---|
| Охват | в эпике оба типа: бизнес с VAT ID и потребитель (D6), на одних тарифах |
| Тип клиента | бизнес: в Checkout введён VAT ID (`tax_id_collection[enabled]=true`) и его проверка не дала `unverified` или `invalid`; иначе потребитель: НДС начисляется, право отказа есть (ниже) |
| Расчёт налога | Stripe Tax (`automatic_tax[enabled]=true`), регистрации моковой GmbH в sandbox. Checkout считает налог сам; авто-пополнение идёт разовым счётом Invoicing с тем же `automatic_tax`, поэтому налог и reverse charge те же (§6.2) |
| Счёт клиенту | пополнение через Checkout: `invoice_creation[enabled]=true`, Stripe выставляет счёт с НДС; авто-пополнение: тот же счёт Invoicing. Счета видны в Customer Portal, Stripe отправляет их на email Customer, введённый в Checkout. В sandbox Stripe клиентам автоматически не шлёт квитанции и счета (support.stripe.com, перед стендом проверить), поэтому там клиент узнаёт о платежах и отказах только из ui (§18) |
| Цены | `tax_behavior=inclusive`, одна брутто-цена для всех (решение техлида от 2026-11-06): потребитель платит указанную цену с НДС; бизнес платит ту же сумму |
| Reverse charge | только трансграничный B2B в ЕС: VAT ID страны ЕС, отличной от Германии (страна моковой GmbH, §12). Сумма та же, НДС 0, в счёте пометка reverse charge |
| Немецкий VAT ID | продажа внутри страны: Stripe Tax начисляет немецкий НДС, reverse charge не применяется; сумма та же, НДС внутри неё, VAT ID печатается в счёте |
| Вне ЕС | налог по правилам Stripe Tax для страны клиента, сумма та же |
| Проверка VAT ID | Stripe проверяет формат сразу и асинхронно по базе ЕС (`customer.tax_id.updated`); reverse charge Stripe Tax применяет по формату номера и стране. Номер со статусом `unverified` или `invalid` клиента бизнесом не делает: он потребитель, `withdrawal_eligible` платежей с этим номером пересчитывается по событию, а номер убирается из Customer, чтобы следующие счета шли с НДС (механика в #372) |
| Страница цен | до Checkout тип клиента неизвестен, поэтому показывается одна цена с пометкой «включая НДС» и сноска: «Компании из других стран ЕС с действительным VAT ID платят ту же сумму, НДС не начисляется (reverse charge)». Отдельной нетто-цены нет |
| Право отказа 14 дней | потребитель (без проверенного VAT ID, «Тип клиента») со страной адреса оплаты в ЕС или ЕЭЗ; только ему показывается чекбокс п. 1 ниже. Бизнес и клиенты вне ЕС и ЕЭЗ права отказа у нас не получают |
| Отказ в 14 дней | правило ниже, «Отказ от договора» |

**Отказ от договора** (14 дней, только клиент с правом отказа; изменение D6, ниже):

- На что действует: на заключение договора, то есть на первую оплату подписки
  (`subscription_create`), на каждое пополнение с нашего экрана и на каждое
  авто-пополнение (его согласие, п. 3, содержит тот же текст о немедленном
  начале). Продление и доплата за повышение новым договором не считаются: подписку
  отменяют в Portal в конце периода. Срок 14 дней от оплаты этого платежа.
- Кто: Owner, Admin или Billing (§11.1), кнопкой «Отказаться от покупки» на экране
  «Баланс и тариф» у каждого такого платежа, 14 дней. Пока по платежу открыт спор,
  кнопки нет: Stripe не возвращает оспоренный платёж. Отказ письмом в поддержку
  оформляет оператор тем же действием по явному запросу клиента.
- **Удерживаем использованное, возвращаем неистраченный остаток.** Использованное
  это списанное из гранта этого платежа за ревью, с deep и надбавкой (§3.2);
  возврат = неистраченный остаток гранта на момент отказа. Правило одно для
  подписки, пополнения и авто-пополнения, расчёта «по дням» нет. Подписка
  заканчивается сразу, workspace переходит на PAYG.
- Если при оплате согласия на немедленное начало не было (ниже, «Что хранится»):
  возврат 100%.
- Возврат не больше суммы платежа минус уже возвращённое и сумма открытого или
  проигранного спора по нему (§5).
- **Долга отказ не создаёт.** Остаток гранта после отказа не тратится, удержания
  начатых run доживают до итога, итог по гранту равен использованному. Если
  возврат 100% больше неистраченного остатка, минус гранта списывается, а не
  становится долгом. Строки `credit_ledger` для этого задаёт #371.
- Отказ от пополнения или авто-пополнения выключает авто-пополнение до нового
  согласия, как спор (§6.2); возврат по отказу проверку по уровню не запускает.
- Попытка отказа пишется с зафиксированными суммами до вызовов Stripe (отмена
  подписки сразу без перерасчёта, возврат), итог по вебхукам
  `customer.subscription.deleted` и `charge.refunded`, зависшую доводит задача
  §10.6. Шаги и ключи: #371 (пополнение), #513 (авто-пополнение), #372 (подписка).
- **Что хранится в `payments` на момент оплаты:** `withdrawal_eligible`
  (потребитель, «Тип клиента», со страной адреса оплаты в ЕС или ЕЭЗ; страна и VAT
  ID из Checkout для пополнения и первой оплаты подписки, из Customer на момент
  платежа для `source=auto_recharge`), `immediate_start_consent_id` и
  `withdrawn_at`. Немедленное начало доказывает: для пополнения и первой оплаты
  подписки согласие `immediate_start` с нашей страницы (п. 1), для
  авто-пополнения действующее на момент платежа согласие `auto_recharge` с фразой
  п. 1 (п. 3). Чем связать согласие подписки со строкой её первого счёта, решает
  #372 (§16). Смена VAT ID позже право отказа не меняет, меняет только итог
  проверки номера этого платежа (таблица выше).
- Правило «удерживаем использованное» ждёт подтверждения legal
  ([ui#211](https://github.com/larchanka-training/dmc-268-ui-t6/issues/211), §19).
  Тексты Terms и Refund Policy перед live проверяет юрист (§18).

**Согласия перед оплатой.** Checkout умеет один обязательный чекбокс
(`consent_collection[terms_of_service]=required`) с текстом до 1200 символов, а
`custom_fields` бывают только text, numeric и dropdown. Поэтому:

1. **Немедленное начало** (`immediate_start`), на нашей странице до Checkout: цена,
   НДС, период, автопродление, способ отмены и, для клиента с правом отказа,
   чекбокс «Прошу начать услугу сразу и понимаю, что при отказе в 14 дней заплачу
   за оказанное, а после полного оказания теряю право отказа». Без чекбокса кнопка
   оплаты не активна. Страна и VAT ID берутся из формы и сверяются с Checkout;
   если Checkout дал страну ЕС или ЕЭЗ без VAT ID, а чекбокса не было, платёж
   проходит и при отказе возвращается полностью.
2. В Checkout: чекбокс условий (`terms_of_service=required`) с
   `custom_text.terms_of_service_acceptance`, ссылками на Terms и Refund Policy.
3. **Включение авто-пополнения** (`auto_recharge`; Checkout там нет): экран с
   порогом, суммой, месячным потолком, картой (последние 4 цифры), тем, что
   списание идёт без участия клиента, и как отключить (переключатель на экране
   «Баланс и тариф»). Чекбокс «Разрешаю списывать эту сумму с карты, когда баланс
   ниже порога, не больше потолка в месяц». Клиенту с правом отказа в текст входит
   фраза п. 1: каждое авто-пополнение начинает услугу сразу, при отказе
   удерживается потраченное. Пояснение рядом: баланс здесь это все доступные
   кредиты, включая ревью подписки и бонус (§6.2), поэтому у подписчика
   авто-пополнение срабатывает, когда общий остаток вместе с пакетом ниже порога.
   Без чекбокса включить нельзя. Изменение порога, суммы, потолка или карты
   требует нового согласия. Согласие держится на человеке: если давший его теряет
   право включать авто-пополнение (снята роль, удалён из workspace, §11.2),
   авто-пополнение выключается в той же транзакции, баннер «Авто-пополнение
   выключено: у включившего больше нет прав» для Owner, Admin и Billing.
4. **Сохранение карты при пополнении** (`save_card`, §6.1): необязательный чекбокс
   «Сохранить карту для следующих пополнений» с текстом: карта хранится в Stripe и
   без действия клиента списывается только при включённом авто-пополнении (п. 3).
   Кнопка «Привязать карту» показывает тот же текст без чекбокса: нажатие и есть
   согласие.
5. **Автопродление подписки** (`subscription_renewal`, все подписчики): на нашей
   странице до Checkout подписки обязательный чекбокс «Подписка продлевается
   автоматически, отменить можно в любой момент» с ценой, периодом и способом
   отмены. Отмена онлайн в Customer Portal и ссылкой из ui. Квитанции и счета в
   live шлёт Stripe (в sandbox писем нет, §18).

**Где хранятся согласия.** Таблица `billing_consents` (новая): `workspace_id`,
`github_user_id`, `kind` (`immediate_start | subscription_renewal | auto_recharge |
save_card`), версия текста, параметры (цена и период; порог, сумма, потолок и
карта), время. Строки только добавляются; действующее согласие авто-пополнения
последнее. Пишут #371 (п. 1, 4), #372 (пп. 1 и 5 для подписки) и #513 (п. 3).

Тексты пишет legal ([ui#211](https://github.com/larchanka-training/dmc-268-ui-t6/issues/211)),
юридическая проверка вне эпика (§18).

## 10. Stripe

### 10.1. Объекты

| Объект | Использование |
|---|---|
| Customer | один на workspace; `metadata.workspace_id`; создаётся нами до первого Checkout любого вида (`mode=payment`, `subscription` или `setup`) и передаётся в сессию как `customer` |
| Checkout Session | пополнение (`mode=payment`), подписка (`mode=subscription`), сохранение карты (`mode=setup`); в каждой сессии `payment_method_types=[card]` (§6.1), `billing_address_collection=required`, `customer_update[address]=auto` и, раз включён `tax_id_collection` при существующем Customer, `customer_update[name]=auto` (имя компании и VAT ID сохраняются в Customer, docs.stripe.com/tax/checkout/tax-ids): адрес сохраняется в Customer, по нему Stripe Tax считает налог и в Checkout, и в счёте авто-пополнения (§6.2) |
| Product, Price | Starter и Pro: фиксированная месячная цена (licensed), `tax_behavior=inclusive`; пополнение: `price_data` на выбранную сумму с `tax_behavior=inclusive` |
| Subscription | один активный тариф на workspace |
| SetupIntent | сохранение карты `off_session` |
| Invoice (разовый) | авто-пополнение (§6.2); счёт пополнения через Checkout `invoice_creation` |
| Customer Portal | карта, счета, VAT ID, понижение Pro → Starter и отмена в конце периода (§4.4); повышение только с нашего экрана |
| Stripe Tax | расчёт и reverse charge |
| Billing Credits, Meters | не используем (§10.2) |

### 10.2. Почему не Billing Credits

- Кредиты применяются только к счёту подписки при его финализации, а не в момент
  прогона: проверку баланса перед прогоном на них не построить.
- Применяются только к позициям с metered-ценами через Meters; к разовым счетам
  (пополнение) и к licensed-ценам не применяются.
- Правила Stripe запрещают выдавать их как stored value, то есть как кошелёк вне
  конкретных услуг.
- Лимит: не больше 100 неиспользованных грантов на клиента.
- Customer Portal не меняет подписки с usage-based ценами, только отменяет их.

Свой журнал даёт проверку до прогона, списание после каждого вызова и порядок
источников §5.

### 10.3. Вебхуки

| Событие | Действие |
|---|---|
| `checkout.session.completed` | `mode=payment`: `payments.status=paid`, грант `top_up`, карта сохранена, если был `setup_future_usage` (§6.1); `mode=setup`: карта сохранена, бонус по `setup_intent.succeeded` |
| `checkout.session.expired` | `payments.status=expired` |
| `checkout.session.async_payment_succeeded`, `..._failed` | не ожидаются: Checkout принимает только карты (`payment_method_types=[card]`, §6.1, §10.1); если придут, логируются, а оплату подхватывает суточная сверка (§10.5) |
| `payment_intent.succeeded`, `payment_intent.payment_failed` | только лог: деньги пополнения по `checkout.session.completed`, авто-пополнения и подписки по событиям счёта |
| `payment_method.detached` | если это карта авто-пополнения: авто-пополнение выключается, баннер «Карта изменена, включите авто-пополнение заново» (§6.2, §9 п. 3) |
| `setup_intent.succeeded` | `metadata.source=link_card`: карта сохранена; бонус §7 получателю из `metadata.github_user_id`, если флаг включён и условия выполнены. Без этой метки только лог |
| `invoice.paid` | `metadata.source=checkout`: только дописать `provider_invoice_id` строки Checkout, без гранта (§10.4). `metadata.source=auto_recharge`: грант `top_up` (§6.2). Счёт подписки, подписка `canceled`: грант `top_up` на оплаченную сумму, тариф не возвращается (§4.3). Иначе грант `subscription_grant`: полный для `billing_reason` = `subscription_create` или `subscription_cycle`, на оплаченную сумму для доплаты за повышение (§4.3, §4.4); иначе без гранта |
| `invoice.payment_failed`, `invoice.payment_action_required` | `metadata.source=auto_recharge`: авто-пополнение выключается, баннер (§6.2). Счёт подписки по `billing_reason`: `subscription_cycle`: статус `past_due`, тариф работает, баннер «Оплата подписки не прошла» (§4.3), в live письмо шлёт Stripe (в sandbox писем нет, §18); `subscription_update` (доплата за повышение): тариф и статус не меняются, остаётся Starter, баннер «Повышение не оплачено» по `pending_update_expired` (§4.4); `subscription_create`: тариф не начинается, гранта нет, workspace остаётся на прежнем тарифе (§4.3); иначе только лог |
| `customer.subscription.created`, `.updated` | тариф workspace, лимит репозиториев, статус подписки. Тариф действует при статусах `active` и `past_due` (на время повторов); при `incomplete`, `incomplete_expired`, `unpaid`, `paused` и `canceled` тарифа нет, workspace на PAYG (§4.3) |
| `customer.subscription.deleted` | тариф снимается, workspace на PAYG (§4.3) |
| `customer.subscription.pending_update_applied` | повышение оплачено: тариф Pro, цена единицы и лимиты Pro (§4.4) |
| `customer.subscription.pending_update_expired` | повышение не оплачено: тариф остаётся Starter, баннер «Повышение не оплачено» (§4.4) |
| `customer.tax_id.created`, `.updated` | статус проверки VAT ID: при `unverified` или `invalid` клиент считается потребителем (§9) |
| `charge.refunded` | по строке `refund` на каждый объект возврата из `charge.refunds`, которого ещё нет (§5). Возврат по отказу в 14 дней: авто-пополнение уже выключено отказом, проверка по уровню не запускается (§9); иной возврат запускает её (§6.2) |
| `charge.dispute.created` | строка `adjustment` с причиной `dispute` на сумму спора в грант платежа (§5); авто-пополнение выключается; отметка для оператора |
| `charge.dispute.closed` | `status=won`: обратная строка `adjustment` с `reversal_of_id`; иначе только лог |

### 10.4. Идемпотентность

- Входящие: id события Stripe (`evt_...`) уникален в своей таблице квитанций;
  повтор отвечает 200 без действий. Порядок событий не гарантирован: обработчик
  читает актуальный объект из Stripe.
- **Строка `payments` на каждый оплачиваемый объект Stripe:** Checkout
  `mode=payment` (при создании сессии), попытка авто-пополнения (при создании,
  §6.2), счёт подписки (при первом событии по нему). `mode=subscription` и
  `mode=setup` строки на сессию не пишут. Новые поля `source` (`checkout |
  auto_recharge | subscription`) и `provider_invoice_id`; счёт Checkout
  `invoice_creation` получает метку `source=checkout` и гранта не даёт: грант уже
  дан по сессии. Гранты `top_up` и `subscription_grant` ссылаются на строку через
  `payment_id`.
- Каждое денежное действие идемпотентно по бизнес-ключу: сессия, счёт, платёж,
  возврат Stripe (`re_...`), спор (`dp_...`), строка списания по вызову и гранту,
  итог run, сторно по исходной строке, истечение, удержание по run, бонус по
  GitHub user id, workspace и fingerprint карты. Повтор ничего не пишет. Состав
  ключей и индексов: #371 (журнал), #372 (подписка), #513 (авто-пополнение).
- Исходящие вызовы Stripe идут с `Idempotency-Key` из нашего id (платёж, попытка
  авто-пополнения, отказ), вне транзакции БД (BACKEND_ARCHITECTURE).

### 10.5. Сверка

- Leader-задача раз в сутки читает из Stripe Checkout Sessions, PaymentIntents,
  счета, возвраты и споры (`disputes`) за 72 часа и сравнивает с `payments`,
  грантами, строками `refund` и строками спора. Пропущенное применяется тем же
  идемпотентным обработчиком. Расхождение сумм даёт алерт. Зависшие попытки
  авто-пополнения в `pending` разбирает задача §10.6, а не суточная (§6.2).
- Та же задача сверяет состояние, а не только деньги: Subscriptions workspace
  (статус, тариф, `pending_update`) с тарифом в БД, SetupIntents со
  `metadata.source=link_card` за 72 часа с сохранённой картой и бонусом, карту
  авто-пополнения (существует ли PaymentMethod и привязан ли к Customer). Так
  пропущенные `customer.subscription.deleted`, `setup_intent.succeeded` и
  `payment_method.detached` применяются тем же обработчиком.
- Инвариант баланса: остаток равен сумме `credit_ledger.amount_usd` по workspace;
  отдельного поля баланса нет либо оно проверяется по сумме.

### 10.6. Досписание после сбоя

Строки списания и итог run пишутся разными транзакциями (§3.3). Если процесс упал
между ними, пропуск находит leader-задача, а не повтор воркера. Алгоритм и
критерии пропуска: #371.

- Раз в 5 минут задача сверяет итоги run с §3.4 и применяет недостающее тем же
  идемпотентным обработчиком, что и воркер: списание за вызов, итог, сторно,
  снятие удержания. Берёт только run с удержанием: прогоны, прошедшие при
  выключенном `billing_enforcement`, она не трогает (§16). Run в конечном
  состоянии без воркера (T13 `lease_expired`) входят.
- Та же задача доводит зависшие попытки авто-пополнения (§6.2, шаги в #513) и
  отказа от договора (§9), проверяет авто-пополнение по уровню (§6.2) и в начале
  месяца UTC снова запускает авто-пополнение, остановленное потолком.
- **Истечение грантов** выполняет отдельная leader-задача раз в час обычным use
  case (§3.3): свободный остаток сразу, удержанную часть после снятия удержания
  (§5). Пропуск истечения старше суток даёт алерт.
- Задача смотрит записи старше 2 минут, чтобы не гоняться с живым воркером.
  Найденный пропуск увеличивает метрику и пишется в лог; пропуск старше часа даёт
  алерт.
- Для списания за вызов нужен id события: `SqlAlchemyUsageLedger.record` сейчас
  возвращает `None` (`usage_ledger.py`), в #371 он возвращает id `usage_events`.

### 11.2. Членство поверх GitHub

- Роли хранятся отдельно от `github_user_workspace_access`: строка роли
  `(workspace_id, github_user_id, role, source)`, `source` = `install` (первый
  Owner), `invite` (приглашение или назначение в продукте) или `claim`
  (восстановление Owner). `LinkGitHubInstallations` строки ролей не меняет.
- Роль пользователя определяется по шагам, первое совпадение решает:
  1. **Запись об исключении** (`workspace_member_exclusions`: `workspace_id`,
     `github_user_id`, кто и когда удалил): доступа к workspace в продукте нет, даже
     при доступе GitHub.
  2. **Строка роли:** Owner, Admin, Billing, Member.
  3. **Доступ GitHub без строки роли:** Member.
  4. Иначе доступа нет.
- **Первый Owner это установщик App** (`sender` события `installation.created`):
  на организацию App ставит её владелец или менеджер GitHub App, участник может
  лишь запросить установку; на личный аккаунт его владелец. Право `members: read`
  для этого не нужно. Доставка для ещё не связанной установки ждёт связывания
  (SD §6.9), поэтому Owner пишет проекция после связывания: она сохраняет в
  `provider_metadata` установки `installer_github_user_id` и `account_type` и, если
  у workspace нет ни одного Owner, в той же транзакции пишет строку `owner` с
  `source = install`. Исходы:
  - переустановка на тот же аккаунт (прежний workspace,
    `github_repository_rebinding.py`): если у workspace уже есть Owner, Owner не
    добавляется, роли и баланс не меняются; если Owner нет, установщик новой
    установки становится первым Owner;
  - доставка `installation.created` истекла до связывания (payload живёт 30 дней,
    §1) или не пришла, и установки до #373 (в `provider_metadata` только
    `account_login`): установщика нет, режим без Owner (ниже).
- **Дальше Owner живёт только в нашей БД.** Назначает и снимает Owner только Owner
  в продукте: делает Owner другого участника или приглашает с ролью Owner. Смена
  роли в организации GitHub наши роли не меняет: проверок роли GitHub при входе,
  перед денежными действиями и по вебхукам `organization` и `membership` нет.
- **Принятый риск: роль живёт до снятия в продукте.** Owner, Admin и Billing (любой
  `source`) держат workspace в токене и свои права, пока их роль не снимут в
  продукте, даже если человек ушёл из организации GitHub; его согласие на
  авто-пополнение тоже действует, в пределах месячного потолка (§6.2). Снимают роль
  Owner (любую) и Admin (кроме Owner) удалением участника; если ушли все Owner,
  сначала заявка «Стать Owner». Экран «Команда» показывает у Owner, Admin и Billing
  дату последнего входа через GitHub и, если право `members: read` принято,
  членство в организации. Срока жизни роли нет (§19).
- **Минимум один Owner.** Последнего Owner нельзя понизить или удалить: API
  отвечает отказом, ui прячет действие и советует держать двух Owner.
- **Восстановление Owner** («Стать Owner»). Условие проверяется в момент заявки, а
  не по строкам `github_user_workspace_access`: они живут, пока человек сам не
  войдёт (SD §6.9).
  - Организация: заявку подаёт админ организации в GitHub. Через GitHub API
    (`GET /orgs/{org}/memberships/{username}`) мы проверяем его роль (`admin`,
    `state = active`) и каждого текущего Owner. Заявка проходит, если ни один
    текущий Owner не активный участник организации на момент заявки (ушёл, удалён
    или приглашён без членства) или Owner нет совсем. Нужно право организации
    `members: read` (сейчас прав организации нет, SD §8.2; добавление в #373); пока
    админ организации его не принял, ui пишет «Попросите админа организации
    принять новые права приложения в GitHub» со ссылкой на страницу установки.
  - Личный аккаунт: владелец аккаунта установки (проверка по id аккаунта)
    становится Owner, если он ещё не Owner.
  - Заявка пишет строку `owner` с `source = claim` и строку журнала
    `workspace_owner_claims` (новая, #373): `workspace_id`, `github_user_id`, время,
    id прежних Owner и их статус в организации. Запись об исключении заявка не
    снимает: исключённый до заявки не доходит (шаг 1), вернуть его может только
    новое приглашение от Owner или Admin, как в GitHub и Slack. Прежние Owner сами
    не снимаются; снять их может новый Owner обычным удалением.
  - Кнопка есть и на экране «Команда» вне режима без Owner; при отказе ui
    показывает причину.
- **Режим без Owner.** Owner нет только у workspace, где его ещё не было (выше).
  Последнего Owner снять нельзя, а приглашают только Owner и Admin, поэтому в этом
  режиме нет ни Admin, ни Billing и вернуться в него нельзя.
  - **Назначение при включении флага.** При включении `billing_enforcement` (§16)
    разовый идемпотентный скрипт с журналом (`workspace_owner_claims` с пометкой
    скрипта) назначает Owner (`source = install`) каждому workspace без Owner:
    личный аккаунт: владелец аккаунта установки; организация: первый по времени
    входа админ организации (по `members: read`), у которого уже есть пользователь
    у нас. Повторный запуск ничего не меняет.
  - Если назначить некого (такого админа нет, право `members: read` не принято или
    workspace попал в режим уже после скрипта), workspace остаётся на прежних
    бесплатных лимитах, как при выключенном флаге (§16): ревью бесплатны,
    пополнение, карта, тариф, авто-пополнение и роли закрыты, настройки
    репозиториев открыты всем с доступом GitHub, как на `main`. Баннер «Станьте
    Owner» с кнопкой «Стать Owner» (или текст про `members: read`).
  - Режим заканчивается с первым Owner (заявка или установка): дальше матрица
    §11.1 и оплата с баланса 0 (§16). Ни оператор, ни порядок входа Owner не
    назначают.
- **GitLab и Bitbucket.** Workspace рождается только при входе через GitHub
  (`LinkGitHubInstallations`), а подключение GitLab или Bitbucket требует
  существующего workspace
  (`app/modules/integrations/gitlab/application/manage_connection.py`). Поэтому
  Owner у такого workspace по правилам выше; роли группы GitLab и workspace
  Bitbucket на наши роли не влияют. Подключать и отключать интеграции могут Owner
  и Admin (§11.1). Workspace без GitHub в эпике нет; если он появится, правило
  первого Owner для него решается отдельно.
- **Удалить участника** (Owner или Admin; Admin не удаляет Owner, последнего Owner
  удалить нельзя) значит снять строку роли и записать исключение (шаг 1). Если его
  согласие держит включённое авто-пополнение, оно выключается (§9, п. 3); так же
  при снятии роли, в том числе роли Owner. Повторный вход через GitHub доступ не
  возвращает. Исключение снимается только принятием нового приглашения для этого
  GitHub user id. Доступ GitHub к репозиториям мы не трогаем.
- **Приглашение без email:** ссылка с одноразовым кодом, срок 7 дней, роль задана
  заранее, принять можно только после входа через GitHub. Приглашение Owner, Admin
  или Billing привязано к GitHub login: принимает только этот логин (сверка по
  GitHub user id, найденному по логину при создании), иначе отказ, код не
  тратится. Приглашение Member можно без привязки. Ссылку передают любым каналом.

### 11.3. Роль и JWT

**Членство в workspace** сейчас читается из `github_user_workspace_access` в
нескольких местах (SD §6.5):

| Место | Что читает |
|---|---|
| `app/modules/auth/application/exchange_github_code.py` → `LinkGitHubInstallations.execute` (`link_github_installations.py`, `current_workspace_ids` в `github_installation_links.py`) | список Workspace в токене при OAuth-входе |
| `app/modules/auth/infrastructure/sessions.py` | список Workspace в токене при refresh |
| `app/modules/auth/infrastructure/current_user.py` | `GET /api/auth/me`, список workspace для ui |
| `app/modules/reviews/infrastructure/metrics_summary.py` | список дневных бюджетов (`_workspaces`); итоги и дни идут по доступу GitHub к репозиторию (`_visible`) |
| `app/modules/integrations/bitbucket/infrastructure/connection_store.py` | выбор workspace для подключения Bitbucket |
| `app/modules/workspaces/infrastructure/repository_access.py` | доступ к репозиториям, прогонам и находкам |

С #373 все места выше, кроме `repository_access.py`, читают одно определение
членства: строки `github_user_workspace_access` плюс строки роли любого `source`
(`install`, `invite`, `claim`; Owner, Admin, Billing, Member) минус записи об
исключении (§11.2). Определение живёт в одном запросе модуля `workspaces`, места
выше его вызывают; ранний выход при входе (`current_workspace_ids`) тоже. Вход,
refresh и принятие приглашения сразу выпускают токен по этому определению, так
что новый workspace виден без ожидания refresh. `repository_access.py` остаётся
на доступе GitHub: прогоны, находки и код видны только при доступе GitHub к
репозиторию (§11.1).

**Сводка списаний по workspace** для ролей без доступа GitHub идёт из
`credit_ledger` (#371): сумма списаний за период и по дням по workspace, без
привязки к репозиторию. Итоги прогонов в `metrics_summary.py` остаются по доступу
GitHub. Так Billing без доступа GitHub после принятия приглашения видит workspace
в ui, баланс и сводку списаний и может платить; прогоны и находки ему по-прежнему
не видны.

Роль не кладётся в JWT. На каждом важном действии (оплата, тариф, авто-пополнение,
настройки, команда) роль читается из БД. Запись об исключении (§11.2, шаг 1)
проверяется на каждом запросе к workspace, в том числе на чтении: список Workspace
из JWT сверяется с `workspace_member_exclusions`. Смена роли и удаление действуют
сразу везде, а не через 15 минут жизни access-токена.

## 13. Рассмотренные модели оплаты

| Модель | Плюсы | Минусы |
|---|---|---|
| За место в месяц | привычно, предсказуемо | платят за людей, а не за ревью; маленькие команды переплачивают |
| Расход × наценка | честно к расходу | цена неизвестна до прогона, зависит от провайдера и курса |
| Кредиты Stripe Billing | готовый журнал у Stripe | только при счёте подписки, нет проверки до прогона (§10.2) |
| **Фиксированная цена за ревью + свой баланс** | цена видна заранее, команда бесплатна | свой журнал, сверка и пороги расхода на нас |

Выбрана последняя.

## 14. Последствия

Плюсы:

- клиент знает цену ревью до запуска, команда растёт без доплаты;
- баланс проверяется до прогона, а не после счёта;
- смена модели или провайдера не меняет цену для клиента.

Цена:

- свой журнал, гранты, сроки, сверка со Stripe и идемпотентность вебхуков;
- пороги расхода ограничивают выбор модели (§8.2);
- согласия потребителя частично вне Checkout, на нашей странице;
- роли продукта живут рядом с членством из GitHub.

## 16. Зависимости и порядок внедрения

Решение техлида от 2026-11-07: ADR хранит решения и инварианты журнала (§3.3).
Механику журнала (распределение по грантам, блокировки, ключи, удержания, повторный
claim, досписание, истечение, DDL) описывает и ревьюит #371, шаги счёта
авто-пополнения #513; новые дефекты механики идут в AC этих задач.

- #371 под флагом `billing_enforcement`: журнал и его механика, гранты, удержания,
  пополнение через Checkout, сохранение карты, два гейта прогона, пороги как лимит
  прогона, суточная сверка, бонус за привязку карты под флагом
  `billing_signup_bonus` (§7).
- #372 под флагом `billing_enforcement`: подписки Starter и Pro, гранты подписки по
  `billing_reason`, смена тарифа (§4.4), лимит репозиториев, Graph RAG по тарифу,
  коды отказа.
- [#513](https://github.com/larchanka-training/dmc-268-api-t6/issues/513) под флагом
  `billing_enforcement`: авто-пополнение и шаги его счёта.
- #373: роли, первый Owner от установщика, восстановление Owner, скрипт назначения
  Owner при включении флага, исключения, приглашения.
- #374 и ui#209: расход по репозиториям и списания.
- ui#207, ui#208, ui#210: выбор workspace, «Баланс и тариф», «Команда».
- ui#211: legal-страницы, страница цен с одной брутто-ценой и сноской для бизнеса
  (§9), мок продавца.
- #512: выбор модели в пределах порогов §8.2.

**Порядок внедрения и включение оплаты.** Единственный блокер #371 это ADR, поэтому
он может выйти раньше #373, когда платить ещё некому. Поэтому оплата включается
фича-флагом `billing_enforcement` (по умолчанию выключен):

1. #371 мержится под флагом.
2. #372 под тем же флагом.
3. #373: роли, первый Owner, восстановление Owner, скрипт назначения Owner.
4. #513 после #371 и #373 (выключение при потере роли, §9 п. 3), под тем же флагом.

**При выключенном флаге** ревью бесплатны, как на `main`:

- гейты баланса не проверяются, удержания и строки списаний не пишутся; лимит
  прогона прежний (fast $0.50, deep $3, PIPELINE_SPEC §4.5), порог §8.2 и множитель
  не действуют; `daily_budget_usd` проверяется как на `main`;
- задача §10.6 не досписывает и не проверяет авто-пополнение по уровню;
  проверка по уровню после списаний тоже не идёт, поэтому карта не списывается;
- денежные вебхуки Stripe (§10.3) по-прежнему принимаются и пишутся идемпотентно:
  оплата, пришедшая после выключения, не теряется; пополнение, привязка карты и
  авто-пополнение в ui скрыты, новых платежей не создаём;
- клиенту поля стоимости не отдаются (§3.5): `chargedUsd` `null` и ui показывает
  «Бесплатно», у `WorkspaceDailyBudget` поле `spentTodayUsd` `null` (расход LLM
  клиенту не показываем), `dailyBudgetUsd` остаётся настройкой клиента.

**Переходы флага.**

- Включение: досписание §10.6 берёт только run с удержанием, поэтому прогоны,
  прошедшие без флага, не досписываются. Run, начатый до включения, доходит
  бесплатно.
- Выключение: активные удержания снимаются (`released`) без доплаты, уже
  списанное остаётся, дальше run идут бесплатно; журнал и балансы не меняются и
  снова действуют при следующем включении.

**Условие включения.** Флаг включает команда на стенде только после мержа #371,
#372, #373 и ui-частей, без которых платить нельзя: ui#208 («Баланс и тариф»,
согласия §9), ui#210 («Команда», кнопка «Стать Owner») и ui#211 (legal-тексты и
страница цен). При включении скрипт §11.2 назначает Owner каждому workspace без
Owner; workspace, которому назначить некого, остаётся на прежних бесплатных
лимитах с баннером «Станьте Owner», пока кто-то не станет Owner (§11.2). #513 для
включения не нужен: без него работают ручные пополнения. Остальные существующие
workspace начинают с балансом 0 (строк `credit_ledger` у них нет), новые прогоны
получают `balance_exhausted` до первого пополнения; бонус за привязку карты
доступен, если включён `billing_signup_bonus` (§7).

в issue; строки с пометкой «ждёт правки» появились во втором-пятом раундах ревью
