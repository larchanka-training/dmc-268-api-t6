# ADR 0002 — доступ AI-агента к настройке ревью

| | |
|---|---|
| Статус | Предложено к ревью в рамках [api#249](https://github.com/larchanka-training/dmc-268-api-t6/issues/249) |
| Дата | 2026-11-05 |
| Область | GitHub-репозитории, portal API, лендинг |

## Контекст

Portal API принимает 15-минутный JWT, выдаваемый после браузерного OAuth GitHub App. Агенту нельзя выдавать ключ App, GitHub user access token или refresh-cookie. При этом уже существуют операции для чтения репозиториев, изменения настроек, проверки `.review/rules.md` и чтения результатов. Новая серверная инфраструктура ради повторения этих операций не нужна.

Установка GitHub App и выдача согласия пользователя остаются решениями человека на стороне GitHub. [GitHub требует установку App с выбором репозиториев](https://docs.github.com/en/apps/using-github-apps/about-using-github-apps), а для headless-клиента [предусматривает device flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app). Device flow нужно включить в настройках App до staging-проверки. «Без интерфейса» в этом решении означает отсутствие ручной настройки в *нашем* UI после одной инструкции агенту; согласие на GitHub не автоматизируется.

## Решение

Используем существующий HTTP API, его OpenAPI и одну инструкцию агенту (`GET /api/agent/instructions`). На лендинге копируется строка с URL инструкции и ссылкой на установку конкретного GitHub App. Агент определяет `owner/repo`, получает device code от API, показывает человеку код подтверждения GitHub и опрашивает API. Сервер обменивает код с GitHub, читает user identity и installation listing, связывает подтверждённые гранты и выдаёт **только отдельный opaque agent token**. GitHub OAuth token живёт лишь в памяти запроса и не возвращается агенту или в локальную сессию.

Agent token — случайный секрет с префиксом `acr_`; в PostgreSQL хранится SHA-256, владелец, один Repository/Workspace, срок 30 дней и время отзыва. На каждом запросе выполняется DB lookup и проверка отзыва. Транспорт допускает только GET репозиториев, rules status, PR и run results, а также PATCH настроек Repository. Существующий SQL-предикат дополнительно ограничен сохранённым Repository ID и по-прежнему проверяет текущие пользовательские гранты; удаление App или гранта закрывает доступ без ожидания истечения токена. Владелец отзывает токен по `DELETE /api/agent/tokens/{id}` с браузерным JWT.

`.review/rules.md` меняется обычным Git-коммитом агента с правами, которые пользователь уже дал своему Git-клиенту; reviewer API token не имеет Git write полномочий. Ревью запускает существующая связка PR, лейбла `ai-review` и вебхука. Результат агент читает из существующих `/api/repos/{id}/pulls` и `/api/runs`.

## Альтернативы

| Вариант | Решение |
|---|---|
| Удалённый MCP-сервер | Отложен: повторил бы текущие HTTP-операции и потребовал бы отдельного каталога tools, развёртывания и OAuth discovery/authorization; [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) не снимает задачу грантов и токенов. Позже возможен адаптер поверх этого API. |
| Только skill или текстовая инструкция | Недостаточно: агенту всё равно нужен credential без браузерной JWT-сессии. Выбранная инструкция дополняет API и не хранит секреты. |
| `llms.txt` | Может помочь обнаружению документации, но не даёт авторизацию, порядок действий или права; для одного сценария достаточно публичного Markdown endpoint. |
| Отдельный CLI | Отложен: добавил бы дистрибуцию и обновления бинаря/пакета при том же HTTP-протоколе. Любой агент с HTTP-клиентом уже может выполнить инструкцию. |
| GitHub user token или App private key у агента | Отклонено: избыточные полномочия и нарушение границы секретов. |

## Последствия и проверка

- У API появляется публичный endpoint device flow; хеш device code, интервал опроса и одноразовость хранятся в БД. GitHub-вызовы выполняются вне DB-транзакций.
- Если после успешного обмена device code с GitHub профиль, привязка установки или выдача локального токена завершаются ошибкой, код нельзя безопасно повторно обменять. Инструкция предписывает начать новый device flow; повторная ошибка останавливает сценарий с явным сообщением.
- Оператор должен включить device flow на staging GitHub App. Пользователь подтверждает установку и авторизацию на GitHub; первый review требует настоящего PR с `ai-review`.
- Токен остаётся доступным агенту как bearer secret; компрометация ограничена одним репозиторием, разрешёнными операциями, текущими грантами, сроком и отзывом.
- Перед приёмкой нужен staging-прогон полного сценария на тестовом репозитории и проверка отсутствия GitHub OAuth/App секретов в HTTP-ответах и логах.
