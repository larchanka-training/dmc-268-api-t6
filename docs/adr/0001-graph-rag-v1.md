## 1. Контекст

Детерминированный контекст L0–L4 (#107, #130) показывает изменённые файлы и одну
степень их импортов: L4 разрешает на ревизии PR определения символов, которые
использует diff. Дёшево L4 не даёт двух вещей: **обратных рёбер** — кто
импортирует или использует то, что меняет PR, то есть влияния на неизменённый
вызывающий код, — и **глубины больше одного шага**. Это и есть вклад графа.

До этого ADR канон запрещал такую работу. Р-13 и SD §9 «Граница MVP и будущего
RAG» выводили RAG из MVP (#19); CVS §1 исключал RAG, embeddings и индексацию всего
репозитория, а перечень `source_role` не знал роли retrieval; BACKEND_ARCHITECTURE
утверждал, что RAG не требует новой ORM-модели и миграции; SD §2, §10 и §13
разрешали хранить код клиента не дольше 7 дней в кэше блобов. Индекс v1 вводит
долговременные данные о коде клиента, фоновую работу вне run и источник контекста
с другой ревизией. Поэтому поправка согласует хранение, ревизии, бюджет и guard,
а не одну строку Р-13.

Состояние `main` (`362f758`), на которое опирается ADR:

- `ContextProvider`, `BudgetAllocator` и `ManifestBlock` — целевые контракты, в коде
  их нет. `process_run.py` отбрасывает результат контекстной стадии L1–L4, модель
  получает только L1. Сборку L0–L4 с бюджетом вносит #130, prompt envelope,
  pre-send guard и manifest — #120 (PR #133).
- AST v1 (#130, PR #136): экстрактор `tree_sitter_facts.py` (`facts/v1`), резолвер
  `ast_resolution.py` (`resolver/v1`; исходы resolved/external/ambiguous/dynamic/
  excluded/unsupported/missing), `symbol_id` вида `revision[:12]:path#index`.
- Клиента архива дерева и чтения GitLab нет; сравнение коммитов GitHub есть только
  как `get_merge_base`.
- `usage_events.run_id` — NOT NULL.
- `installation_repositories.removed` и `installation.deleted` только отключают
  доступ; данные репозитория сейчас не удаляются.
- Прецедент fencing — `reserved_generation`/`applied_generation` (миграция 0013,
  `link_github_installations.py`).
- Очереди — RabbitMQ (aio-pika); leader-задачи выполняются в
  `WorkerProcess.leader_tick` под advisory lock.
- Промпты неизменяемы по версии: `review/prompts/<key>.vN.md`, активен
  `review.system.v2`; сид отказывается менять существующую версию.

## 2. Решение — граф символов с указателями

**RAG v1 — граф символов одного репозитория**: определения, ссылки (использование
импортированного имени) и импорты, связанные рёбрами (§3), с указателями — путь,
диапазон строк, `blob_sha` и `indexed_commit_sha` (commit default branch, на
котором опубликован индекс). Embeddings, векторного хранилища и текста кода в
индексе нет. Индексируются только репозитории с включённым тумблером RAG; по
умолчанию тумблер выключен, первая индексация — при включении (D3).

`RagContextProvider` — реализация порта `ContextProvider`: к детерминированному
профилю L0–L4 он добавляет кандидатов графа и возвращает **тот же
`ContextPayload`**. Кандидаты передаются в отдельном списке `retrieved`, который у
детерминированного профиля пуст: `FileContext` требует diff, а у неизменённого
файла его нет. Форму элемента списка закрепляет #144. LLM Gateway, постобработка,
verifier, хранение результата и Publisher от способа retrieval не зависят.

**v2** — векторный поиск (pgvector и embeddings, #147) — открывается только после
положительного гейта #146 (§12). Модель embeddings и хранилище v2 этот ADR не
выбирает.

**Сигнатуры или только указатели: только указатели.** Индекс не хранит
сигнатуры, docstrings и иной текст кода:

1. По правилу ревизий (§8) диапазон и сигнатура кандидата заново извлекаются из
   blob ревизии PR. Сохранённая сигнатура с default branch в prompt не попала бы и
   пользы не дала бы.
2. Сигнатура — фрагмент кода клиента. SD §10 разрешает хранить код клиента не
   дольше 7 дней в кэше блобов, а индекс живёт до 30 дней без использования (§4):
   сигнатуры в индексе нарушили бы этот предел.
3. Это совпадает с D2 и с дизайном куратора: «мы не храним эти файлы».

Текст, который видит модель, читается при ревью из существующего 7-дневного кэша
блобов на ревизии PR; правило 7 дней не меняется.

**Вклад графа сверх L4.** Главный вклад — обратные рёбра. Глубина больше одного
шага — вклад графа в принципе, но v1 ограничивает обход одним обратным шагом сверх
L4 (§3); кейсы глубины 2 в корпусе #146 — ожидаемые промахи v1 и задел для v2.
Примеры контекста, который даёт только граф:

1. PR меняет сигнатуру `parse_config(path)` на `parse_config(path, strict)`; граф
   находит неизменённые файлы, которые импортируют `parse_config` и вызывают её
   по-старому.
2. PR удаляет или переименовывает экспорт `X` модуля `M`, а неизменённый файл всё
   ещё импортирует `M.X` (§8.3).
3. PR делает поле TypeScript interface `User` обязательным; граф находит файлы,
   импортирующие `User`, которые строят объект без этого поля.

## 3. Виды рёбер и идентичность символа

Рёбра v1 (F6) существуют только в пределах однозначного разрешения резолвера #130
(`resolution = resolved`):

| Ребро | Откуда → куда | Гарантия |
|---|---|---|
| `imports` | файл → модуль | явный импорт, разрешённый в путь модуля той же ревизии |
| `defines` | файл → символ | объявление, извлечённое экстрактором #130 |
| `uses_imported` | файл → модуль и экспортируемое имя | имя связано разрешённым явным импортом и использовано в файле |

Не обходятся и остаются `unsupported`, `ambiguous` или `dynamic` по #130: вызовы
через receiver, методы через значения, цепочки barrel re-export, package exports,
aliases, dynamic imports, неявные межфайловые связи Go внутри пакета. «Вызывающие»
v1 — файлы с подтверждённым (§8.2) ребром `imports` или `uses_imported` к
изменённому символу или модулю; это не call graph. Глубина обхода — один обратный
шаг сверх L4: от изменённого символа или модуля к его импортёрам, без рекурсии.
Расширение резолвера — отдельная работа вне v1.

**Идентичность символа (F4).** `symbol_id` из PR #136 (ревизия и порядковый номер)
в индексе не хранится. Логический ключ символа —
`(repository_id, path, qualified_name, kind, disambiguator)`. `disambiguator`
нужен только дубликатам с одинаковыми путём, именем и видом (например, условным
объявлениям): это номер среди них, у единственного объявления он пуст. Ключ не
зависит от commit, а перестановка других объявлений файла его не меняет.

Цель ребра — `(разрешённый путь модуля, экспортируемое имя)`, а не id строки
символа. Поэтому:

- переписанный файл-цель не оставляет входящих рёбер с недействительной целью:
  ребро указывает на имя, а не на строку таблицы;
- удалённая цель делает ребро неразрешённым, а не указывающим на чужой символ;
- изменения, влияющие на разрешение импортов, — добавление, удаление и
  переименование файла, `__init__.py`, `index.ts`/`index.tsx`, `package.json`,
  `go.mod`, пути `tsconfig`, — переизвлекают импортирующие файлы; если вместе с
  изменёнными их больше лимита incremental (§7), выполняется full.

Версии экстрактора (`facts`), резолвера и профиля парсера хранятся на строке
состояния индекса; смена любой из них → full.

## 4. Хранение, очистка и изоляция

Индекс вводит новый класс данных — **производные метаданные кода**: пути,
квалифицированные имена, виды символов, диапазоны строк, `blob_sha` и commit sha,
рёбра. Тела, литералы, комментарии и docstrings не хранятся.

| Аспект | Решение |
|---|---|
| Ключ | `repository_id`; колонка `repository_id NOT NULL` на каждой строке |
| Таблицы | `code_index_states` (одна строка на репозиторий), файлы, символы, рёбра; DDL — #141 |
| Срок жизни | 30 дней с `last_used_at` (чтение при ревью или успешное обновление), настраивается; удаляет leader-задача |
| Немедленное удаление | `installation_repositories.removed`, `installation.deleted`, выключение тумблера |
| Способ удаления | явный DELETE по `repository_id` в транзакции, повышающей поколение (§6.2); FK `ON DELETE CASCADE` — только страховка |
| Не хранится | текст кода, сигнатуры, embeddings; содержимое архива не логируется и не живёт дольше задачи |

После очистки строка состояния получает статус `empty`. Если тумблер включён,
следующее ревью идёт без RAG и ставит обновление в очередь (§6.1).

**Изоляция.** Каждый метод repositories индекса принимает `repository_id`; методов
без него нет. Retriever получает `repository_id` из Run и не видит другие
репозитории, даже того же Workspace.

## 5. Модуль, индексатор и порты

- Новый модуль `app/modules/code_index` владеет таблицами индекса, индексатором и
  реализациями портов.
- Процесс индексатора — отдельный потребитель очереди `index.repo` (exchange
  `code_index`) со своим каналом и prefetch в процессе `worker` (Р-12). Он не
  работает ни в доставке вебхука (`webhook-worker`), ни в потребителе
  `review.run`. Вынос в отдельный сервис того же образа контракт не меняет.
  Топологию с retry и DLQ по образцу SD §7.1 и правку compose вносит #142.
- Порты принадлежат потребителю (`.agents/rules/backend.md` §3, п. 2):
  `GraphRetriever` в `reviews.application` отдаёт кандидатов графа для
  `RagContextProvider`; `CodeIndexPurger` в `repositories.application` немедленно
  удаляет индекс при `removed`, `deleted` и выключении тумблера. Реализации — в
  `code_index.infrastructure`.
- Экстрактор и резолвер #130 переиспользуются, а не дублируются; где живёт общий
  код — решение #142.
- Сверка с HEAD, TTL-очистка и сборка мусора — leader-задачи в
  `WorkerProcess.leader_tick` под advisory lock.

## 6. Жизненный цикл индекса

### 6.1. Триггеры и готовность

| Событие | Действие |
|---|---|
| Включение тумблера | поколение +1, full |
| Мерж PR в default branch | цель — новый HEAD default branch |
| Leader-сверка (интервал настраивается) | для включённых репозиториев сравнить HEAD default branch с `indexed_commit_sha`; покрывает прямые push |
| Ревью при отставшем индексе | поставить обновление в очередь; ревью не ждёт |
| Выключение тумблера | очистка (§6.2); индекс не читается, шага `context.rag` нет |
| `installation_repositories.removed`, `installation.deleted` | очистка (§6.2) |
| TTL (§4) | очистка leader-задачей |

Статусы индекса для #145: `empty`, `building`, `ready`, `failed` с `error_code`;
`stale` — производный (`ready`, но отстаёт от HEAD default branch). `building` —
индекс текущего поколения ещё не опубликован; обновление опубликованного индекса
статус `ready` не снимает: читатели видят прежнюю публикацию (§6.2).

Поведение ревью:

- тумблер выключен — обращений к индексу нет, `context.rag` не пишется;
- тумблер включён, индекс не готов (`empty`, `building`, `failed`) — ревью без RAG,
  trace `rag: not_ready` с причиной (статус и `error_code`);
- готовый индекс, отставший от HEAD (`stale`), используется: кандидаты всё равно
  подтверждаются на ревизии PR (§8), отставание пишется в trace.

### 6.2. Fencing

Контракт F1: очистка, выключение тумблера, удаление App или репозитория
инвалидируют запущенные и стоящие в очереди задачи индексации.

- `code_index_states.generation` — монотонное поколение по прецеденту
  `reserved_generation`/`applied_generation`.
- Очистка (`removed`, `deleted`, TTL) и выключение тумблера в одной транзакции
  повышают поколение и удаляют строки индекса.
- Включение повышает поколение и ставит full с новым значением.
- Задача несёт своё поколение. Каждая пакетная запись проверяет его в своей
  транзакции; при несовпадении задача прекращается без записи и без retry.
- Публикация (`indexed_commit_sha`, статус `ready`) — compare-and-set по
  `(generation, исходный indexed_commit_sha)` в транзакции записи.
- Согласованное чтение: строки несут номера публикаций `valid_from`/`valid_to`,
  читатель фильтрует по опубликованному номеру, вытесненные строки удаляет сборка
  мусора после публикации.
- Сетевые вызовы (архив, сравнение, блобы) выполняются вне транзакций; запись —
  короткими транзакциями.

Так задача, скачавшая архив до выключения тумблера, после очистки ничего не
запишет: её поколение уже устарело.

### 6.3. Incremental

Контракт F2:

- Набор изменений — сравнение VCS `indexed_commit_sha...цель` на default branch, а
  не diff последнего PR.
- Задачи одного репозитория сливаются: цель хранится на строке состояния,
  сообщение очереди только будит `{repository_id, generation}`, задача берёт
  последнюю цель.
- Full выполняется, когда: индекса нет; сравнение неполное или усечено; цель не
  потомок `indexed_commit_sha` (force push); сменилась default branch; изменено
  больше 500 файлов или переизвлечение импортирующих (§3) выводит набор за этот
  лимит; сменилась версия экстрактора, резолвера или профиля; изменился ignore в
  `.review/rules.md`.
- Публикация — только если поколение и исходный `indexed_commit_sha` не
  изменились с начала задачи (§6.2).
- Инвариант: `indexed_commit_sha = C` означает, что всё разрешённое дерево
  проиндексировано на `C`. Порядок задаётся поколением и compare-and-set, а не
  предками commit.

## 7. Лимиты индексации

Контракт F3. Лимиты действуют на репозиторий целиком, настраиваются переменными
окружения `CODE_INDEX_*` (имена — #142); ниже стартовые значения.

| Лимит | Значение | Код превышения |
|---|---|---|
| Скачанные байты архива | 100 MiB | `limit_exceeded:download_bytes` |
| Распакованные байты | 1 GiB | `limit_exceeded:unpacked_bytes` |
| Entries архива | 100 000 | `limit_exceeded:archive_entries` |
| Файл больше 1 MiB | пропускается, это не ошибка | — |
| Разобранные файлы | 20 000 | `limit_exceeded:parsed_files` |
| Символы | 500 000 | `limit_exceeded:symbols` |
| Рёбра | 2 000 000 | `limit_exceeded:edges` |
| Deadline задачи | 15 мин | `limit_exceeded:deadline` |
| Хранение на репозиторий | 512 MiB | `limit_exceeded:repository_storage` |
| Хранение на Workspace | 2 GiB | `limit_exceeded:workspace_storage` |
| Параллелизм | 2 задачи всего, 1 на установку | — (задача ждёт в очереди) |
| Incremental | до 500 изменённых файлов | — (сверх лимита — full) |

Архив tar.gz разбирается потоково в памяти, без записи на диск; текущая сумма
скачанных и распакованных байт сверяется с лимитом по ходу чтения. Entries с
абсолютным путём, `..`, symlink, hardlink, устройства и FIFO отклоняются: они не
читаются и не индексируются.

Превышение лимита — статус `failed` и `error_code = limit_exceeded:<лимит>`. Такая
задача не повторяется, сверка с HEAD и ревью её не перезапускают до повторного
включения тумблера, а ревью идёт без RAG (`rag: not_ready`). Retry — только при
временных ошибках (5xx, 429) с задержками SD §7.1. Коды остальных отказов и их
перезапуск — #142 и #143.

## 8. Использование при ревью

### 8.1. Правило ревизий

- Ревизия индекса (`index_commit_sha` — `indexed_commit_sha` использованной
  публикации) только выбирает кандидатов и никогда не является ревизией блока.
- Текст читается на ревизии PR: `head_sha` для RIGHT, `diff_old_sha` для LEFT
  ([CVS §2.1](../CONTEXT_AND_VERIFICATION_SPEC.md#21-раздельные-ревизии)), из
  существующего кэша блобов.
- Кандидат, отсутствующий на этой ревизии, отбрасывается: omission
  `rag_candidate_missing`.
- Блок manifest с ревизией индекса — нарушение guard: `policy_context_violation`.
- Набор кандидатов не входит в снимок run (Р-6): retry может выбрать других
  кандидатов по новой публикации индекса. Текст при этом всегда читается на
  ревизии PR, а фактически показанное фиксирует manifest каждого вызова.

### 8.2. Подтверждение рёбер

Контракт F5: граф default branch только подсказывает кандидатов. Каждое
использованное ребро заново разрешается резолвером #130 на ревизии стороны PR;
диапазон и сигнатура заново извлекаются из blob этой ревизии; координаты default
branch не переносятся. Неподтверждённое ребро — omission `rag_edge_unconfirmed`.
Чтения блобов и разбор для подтверждения входят в лимиты слота RAG (§9), а не в
лимиты L4.

### 8.3. Удалённый или переименованный экспорт

Импортёр `I` на `head_sha` всё ещё импортирует `M.X`, а резолвер возвращает
`missing`: `X` исчез из `M` либо `M` удалён или перемещён. Это кандидат
`rag_broken_reference`, а не omission. Он даёт два блока, у каждого одна ревизия:

1. импорт и места использования в `I` на `head_sha` (RIGHT, `exact_lines`);
2. определение `X` на `diff_old_sha` (LEFT, `signature`).

Фрагменты разных ревизий не склеиваются (CVS §3.2), каждый блок проходит guard
своей ревизии. Если на `head_sha` `I` уже не импортирует `X`, PR исправил
использование, и кандидата нет.

## 9. Бюджет, manifest, ignore и инъекции

**Слот бюджета.** Порядок `BudgetAllocator`: L1 → L4 → RAG → L2 → L3. Потолок RAG —
4 000 токенов; не больше 20 чтений блобов, 10 файлов-кандидатов и 3 мест на файл за
run. RAG получает остаток после L1 и L4 и вытесняет только L2 и L3; L1 и L4 не
вытесняются, приоритет L1 сохраняется. Приоритет внутри слота: битая ссылка >
вызывающие изменённого экспортируемого символа > импортёры изменённого модуля.
Кандидаты сверх лимитов — omission `rag_limit`.

**Роль и manifest.** Блок RAG: `source_role = retrieved_excerpt`,
`source_kind = source_code` (сопоставление RULES_FORMAT_SPEC §8.1). В
`ManifestBlock` `revision` — ревизия стороны PR; `selection_reason` —
`rag_reverse_edge` или `rag_broken_reference`; `source_ref` несёт
`index_commit_sha` и вид ребра как метаданные выбора.

**Ignore** применяется дважды: при индексации — встроенные исключения и
`review-ignore` из `.review/rules.md` на HEAD default branch; при ревью —
закреплённый ignore run к каждому кандидату до чтения блоба (RULES_FORMAT_SPEC
§5, §8.4). Исключённый кандидат не читается и учитывается только счётчиком, без
пути.

**Инъекции.** Блок RAG — типизированная недоверенная секция prompt envelope #120:
код — данные, не инструкции. Новый блок контекста — новая версия промпта
`review.system.v3` (Р-6); eval-baseline пересобирается без смешения прогонов (#82).

## 10. Трейс и коды

- Действие `context.rag` пишется только при включённом тумблере. Request: статус
  индекса, `indexed_commit_sha`, HEAD default branch, признак `stale`. Response:
  `used` или `not_ready` с причиной; кандидаты найдены, подтверждены и отброшены по
  причинам; токены.
- Состояние индекса и отбор кандидатов RAG не задают `runs.error_code`: отказ,
  `not_ready` и превышение лимитов индекса дают ревью без RAG. Исключение — общий
  pre-send guard: блок с ревизией индекса вместо ревизии PR даёт
  `failed/policy_context_violation`, как для любого источника (§8.1).
- `rag_candidate_missing`, `rag_edge_unconfirmed` и `rag_limit` — причины
  coverage, как `ast_*`. Отсутствие RAG и эти причины сами по себе не делают
  coverage partial; правило `insufficient_context` не меняется.
- `limit_exceeded:<лимит>` — код строки состояния индекса, не Run.

## 11. Учёт расхода

Индексация v1 не вызывает LLM и embeddings: строк `usage_events` нет, подставного
`run_id` нет (`usage_events.run_id` — NOT NULL). Операционные счётчики — байты,
файлы, символы, рёбра, длительность, запросы к GitHub — хранятся на строке
состояния индекса. Токены RAG в prompt ревью входят в `usage_events` этого run и
подчиняются `daily_budget_usd` (D3). Как учитывать расход без run, когда появятся
embeddings, решает #147.

## 12. Замер вклада и гейт v2

Метрика и порог объявлены до замера #146.

- Корпус — не меньше 24 кейсов, у каждого снимок репозитория на ревизии кейса:
  10 дефектов, видимых только через обратное ребро (3 из них — удалённые или
  переименованные экспорты); 6 контрольных (достаточно L4); 4 глубины 2 (ожидаемые
  промахи v1, задел для v2); 2 с инъекцией внутри извлечённого кода; 2 без
  дефектов.
- A/B: одна версия промпта и модель; плечо A без RAG, плечо B с RAG; offline
  replay с замороженным снимком индекса; 3 прогона на плечо.
- Метрика вклада — ΔRecall на подмножестве обратных рёбер.
- Гейт открытия #147 (все условия): ΔRecall ≥ +15 п. п.; на всём корпусе Precision
  падает не больше чем на 5 п. п., Critical Recall не ниже, Hallucination Rate
  растёт не больше чем на 2 п. п., медиана токенов на run — не больше +30 %;
  ноль исполненных инъекций.
- Это решение о гейте, а не обязательная проверка CI. Гейт не пройден — #147
  закрывается как not planned.

## 13. Последствия

Плюсы:

- ревью видит неизменённый вызывающий код и битые ссылки, подтверждённые на
  ревизии PR;
- нет затрат и рисков embeddings и vector DB; текст кода сверх 7-дневного кэша не
  хранится;
- LLM Gateway, verifier и публикация не меняются.

Цена:

- новый класс долговременных данных, модуль, таблицы и миграции (#141);
- фоновая работа вне run: очередь, leader-задачи, fencing;
- дополнительные запросы к GitHub (архив, сравнение, блобы) и квоты хранения;
- новая версия промпта и пересъёмка baseline;
- v1 только для GitHub и не видит вызовов через receiver, re-export, aliases и
  глубины больше одного обратного шага.
