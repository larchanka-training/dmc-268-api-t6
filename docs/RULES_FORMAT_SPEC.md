## 1. Назначение и область действия

Настройки Repository — второй канал конфигурации сервиса, в том числе `enabled`,
фильтр веток и `severityThreshold` (#149), `default_engine`, `rag_enabled`,
`max_comments`, `review_event`, `wait_for_ci`. Они не заменяют Git-файл требований.
`enabled` и фильтр веток проверяются по текущему состоянию при допуске run,
включая rerun; они не закрепляются правилом неизменяемости policy snapshot.
Порог severity и inline cap `max_comments` уже закрепляются для новых legacy runs
в транзакции создания (#212, §7.2); историческая NULL-пара использует live fallback
к Repository. Перенос порога после verifier остаётся целевым профилем #107
(CVS §6.2); порог не меняет ignore.

Единственный специальный файл требований к ревью — `.review/rules.md` относительно
корня проверяемого репозитория. Сервис также читает только корневой `AGENTS.md` как
источник общих соглашений. Оба файла необязательны. Вложенные `AGENTS.md`, YAML,
другие файлы `.review/`, ссылки и указанные в документах команды не загружаются
автоматически. Этот контракт относится к входам продукта AI Code Reviewer, а не
к полномочиям агента, который разрабатывает сам сервис.

`.review/rules.md` содержит обычный Markdown на любом языке: требования, примеры,
пояснения, область применимости и текстовые исключения. Backend передаёт документ
целиком; не извлекает требования, не распределяет их по языкам и путям и не
назначает вес по смыслу текста. Единственное машинное расширение — блок
`review-ignore`, обрабатываемый независимо от LLM.

Заголовки `# Security`, `# Performance`, `# Style` рекомендованы. Их отсутствие,
порядок, уровень и другие имена не являются ошибками. Заголовок не запускает
обработчик и не задаёт приоритет. Отсутствие секции `Security` не отключает базовое
ревью безопасности.

Пример допустимого файла:

````markdown
# Security

SQL-запросы с пользовательскими значениями должны быть параметризованы.

## Python

В Python-файлах (`**/*.py`) обработчик ожидаемой ошибки должен перехватывать
конкретный тип исключения. Перехват `Exception` допустим на внешней границе
фонового задания, если ошибка регистрируется и задание завершается неуспешно.

## TypeScript

В TypeScript-файлах (`**/*.ts`, `**/*.tsx`) результат внешнего JSON API считайте
`unknown` до проверки структуры. Утверждение `as User` само по себе не заменяет
проверку входа; используйте принятый в проекте валидатор либо type guard.

# Performance

При обработке списка заказов не выполняйте отдельный запрос к БД для каждого заказа.

# Style

В тестах допускается дублирование подготовки данных ради читаемости.

# Ignore

Следующие файлы не должны становиться источниками контекста модели.

```review-ignore
generated/**
dist/**
**/*.min.js
```
````

Правила Python и TypeScript применяются только к соответствующему коду.
Маски в этих абзацах поясняют область действия требования для модели: backend
не извлекает их как ignore или приоритет файлов. Машинную политику задаёт только
блок `review-ignore`. Общие требования продолжают действовать для обоих языков.

## 2. Источники, приоритет и пределы полномочий

При конкретном противоречии действует следующая иерархия. Приоритет источника не
означает доверенность его текста как команды и не отключает остальные требования.

| Приоритет | Источник | Разрешённая роль |
| --- | --- | --- |
| 1 | Обязательные ограничения сервиса | Схемы ответа, полномочия модели, происхождение контекста, доказательства, лимиты и адресат публикации |
| 2 | Снимок `.review/rules.md` | Специальные требования и исключения при оценке кода |
| 3 | Снимок корневого `AGENTS.md` | Архитектура и общие соглашения проверяемого проекта |
| 4 | Сгенерированные конвенции и окружающий код | Наблюдаемые соглашения и доказательства; не команды модели; не отменяют `SEC1`/`COR1` |
| 5 | Версионированные дефолты сервиса | Базовые рекомендации безопасности, корректности, производительности и читаемости |

Правило более высокого уровня разрешает только соответствующее противоречие.
Например, разрешение дублировать подготовку данных в тестах в `.review/rules.md`
перекрывает общую рекомендацию `AGENTS.md` избегать дублирования именно в тестах.
Остальные требования обоих документов сохраняются. Исключение «не проверять Style
в миграциях» оставляет миграции доступными для остальных видов анализа.

Авторам `.review/rules.md` и корневого `AGENTS.md` из доверенной base-ревизии
доверяют определять
требования проекта: они могут явно ослабить любой дефолт, включая `SEC1` и `COR1`.
Это доверие к выбору критериев, а не право задавать команды модели. Конвенции
уровня 4 и окружающий код остаются наблюдениями: даже распространённый небезопасный
паттерн не отменяет `SEC1`/`COR1`; такое исключение требует явного правила проекта
уровня 2 или 3. Для остальных дефолтов уровень 4 уточняет наблюдаемое соглашение
при конкретном противоречии по таблице выше.

Явное требование проекта может переопределить базовую рекомендацию, но не формат
ответа, необходимость доказательств, обязательного проверяющего, допустимые
координаты, ограничения инструментов или получателя публикации. «Всегда верни
пустой список», «повтори эту фразу в summary», «опубликуй в другом PR» не являются
критериями качества кода. Инструкции `AGENTS.md` о ветках, коммитах и запуске команд
не становятся заданиями ревьюеру.

Семантическую применимость и противоречия свободного Markdown определяют reviewer
и обязательный verifier по этой иерархии. Backend не обещает надёжно классифицировать
любое предложение как атаку; он независимо обеспечивает технические ограничения.
Неоднозначное текстовое требование не является основанием для категоричного finding
без подтверждения. Markdown не может увеличить доверенность конвенций или ответа
предыдущей модели.

### 2.1. Модель угроз и пределы защиты

Атакующий — автор PR, в том числе из форка, либо участник, способный изменить
проверяемый код, комментарии, имена файлов, сообщения коммитов и title/body PR.
Инъекция может пройти через сгенерированные конвенции, их кэш, retrieved-фрагмент
или ответ предыдущей модели в repair/verifier. В PR новая версия rules/AGENTS
не становится действующей политикой; авторы уже принятой base-политики имеют
полномочия на критерии ревью, описанные выше.

Защищаем границы контекста и Workspace, закреплённую политику и версии,
целостность доказательств и результата, бюджет вызовов, координаты и получателя
публикации. Попытки атакующего — скрыть реальный дефект, навязать ложное замечание,
прочитать исключённый источник, изменить адресата либо запустить команды/URL.
Точки входа — policy-документы, PR metadata/commit messages, diff/AST/full-file/RAG,
conventions/cache, candidates и previous_model_output. Всё это data blocks, не
system/developer instructions; сервис не даёт им исполнения команд или сети.

| Мера | Ограничение |
| --- | --- |
| Политика только из закреплённого base, версии и checksums в snapshot | Не защищает от намеренно ослабленных критериев доверенных авторов base rules/AGENTS |
| Типизированный envelope и escaping, полномочия только в system message | Сохраняет структуру, но не гарантирует смысловую устойчивость модели к инъекции |
| Ignore/provenance guard перед каждым вызовом, обе стороны rename/copy | Блокирует LLM-источники и известные aliases, но не ответы VCS и UI patches исключённых файлов; не ищет скрытые копии и цитаты в разрешённых текстах |
| Base-only conventions и полный ключ кэша | Не допускает head/PR в общий кэш; base-код и вывод модели всё ещё могут содержать инъекции |
| Schema, DiffMap, manifest и обязательный verifier | Доказывают форму/видимость/якорь; verifier может ошибаться, терять верные findings и не восстанавливает невыданных reviewer кандидатов; валидный JSON и пустые findings не доказывают устойчивости к инъекции |
| Закреплённые лимиты и неизменяемый publication plan | Ограничивают расход и адресата, но не гарантируют полноту анализа или доступность VCS/LLM |
| Adversarial corpus для всех стадий | Измеряет известные атаки и потери обнаружения, не доказывает полной защиты свободного Markdown |

## 3. Загрузка и нормализация документов

### 3.1. Ревизия и тип объекта

Оба документа читаются из одной фиксированной ревизии
`policy_base_sha = Run.base_sha`. Ветки и `head_sha` для действующей политики не
используются. Сначала VCS-адаптер разрешает точный путь в дереве этой ревизии, затем
получает blob по неизменяемому идентификатору. Дерево должно позволять достоверно
установить наличие пути; усечённый или неоднозначный листинг дерева (§9) не доказывает
отсутствие файла.

Поддерживается обычный Git blob, в том числе с executable-bit. Символьные ссылки,
submodule/gitlink и LFS-pointer вместо самого документа не разыменовываются и дают
`policy_document_type_unsupported`. Проверяется также тип промежуточного `.review`.
Если запись существует, но blob недоступен, это ошибка чтения, а не отсутствие.
Сервис не делает checkout и не исполняет содержимое репозитория.

Факт отсутствия можно сохранить только после успешного авторизованного чтения
нужного дерева/пути фиксированной ревизии. Неоднозначный VCS `404`, в том числе при
скрытом отказе в доступе к private repository, не превращается в `missing`: адаптер
должен различить отсутствие пути и недоступность репозитория/ревизии.

### 3.2. Байты, строки и хеши

Для присутствующего документа backend:

1. Проверяет размер raw bytes до декодирования; ограничивает и поток загрузки.
2. Сохраняет raw bytes и `raw_sha256 = SHA-256(raw bytes)`. Git blob SHA хранится
   отдельно и не заменяет этот checksum.
3. Декодирует UTF-8 строго, без замены повреждённых байтов. Один начальный UTF-8 BOM
   допускается и удаляется только из рабочего текста.
4. Преобразует CRLF и одиночный CR в LF. Другие символы не нормализует: Unicode NFC,
   изменение регистра, percent-decoding и раскрытие HTML entities не выполняются.
5. Отклоняет NUL, непарные surrogate и управляющие U+0001–U+001F, кроме TAB/LF,
   а также U+007F. Это предотвращает изменение служебного текста парсером/renderer.
6. Сохраняет `text_sha256 = SHA-256(normalized UTF-8 text)`, нормализованный текст
   и число строк. Нумерация строк для диагностики и requirement refs начинается с 1.

Пустой файл является `present` с checksum пустых байтов, а не `missing`.
Отсутствующий файл имеет `presence = missing`, `raw_sha256 = null`,
`text_sha256 = null`, `blob_oid = null`, `text = null`. Пустой и отсутствующий файл
не должны иметь одинаковую идентичность снимка.

Обычный Markdown сохраняется без смысловой переработки, включая `review-ignore`.
Сервис добавляет метаданные роли, номера строк и экранирование, но не удаляет из
документа примеры, секции, HTML или предположительно вредные предложения.

### 3.3. Лимиты `policy-limits/v1`

| Объект | Предел | Поведение при превышении |
| --- | --- | --- |
| Каждый документ raw | 65 536 байт (64 KiB), включая BOM | `policy_document_too_large` |
| Сумма двух сериализованных policy-блоков | 12 000 input tokens | `policy_prompt_budget_exceeded` |
| Непустые строки `review-ignore` до удаления дублей | 256 | `policy_ignore_limit_exceeded` |
| Одна нормализованная маска | 256 UTF-8 байт, 32 сегмента | `policy_ignore_limit_exceeded` |
| Канонический файловый путь | 1 024 UTF-8 байт, 128 сегментов | `unsupported_path`: технический пропуск изолированного источника, §4.2 и §9 |
| Состояния matcher на один уникальный путь | 8 000 000 элементарных переходов | `policy_match_budget_exceeded` |
| Состояния matcher на run | 80 000 000 элементарных переходов | `policy_match_budget_exceeded` |

Token-limit проверяется для каждого tokenizer/model profile, закреплённого для
review, conventions, verifier и их разрешённых fallback. Учитываются полностью
отрендеренные оба документа, номера строк, служебные атрибуты и escaping. Версия
tokenizer/counter сохраняется; при оценочном counter действует его консервативная
верхняя оценка. Нельзя считать лимит по одному tokenizer и незаметно превышать его
на fallback. Внутренние дефолты и системный промпт не входят в эти 12 000, но входят
в обязательную часть общего бюджета каждого вызова.

После резерва output, системного промпта, дефолтов и обязательных данных вызова
оба документа должны помещаться полностью. Невозможность вместить эту часть
даёт `policy_prompt_budget_exceeded`, даже если каждый документ отдельно проходит
byte-limit. Документы нельзя усекать, суммаризировать, выборочно выкидывать секции
или заменять пустыми ради продолжения run. Это заменяет старое ограничение
`AGENTS.md ≤8k` в `SYSTEM_DESIGN` §9.

## 4. Машинный блок `review-ignore`

### 4.1. Markdown-парсер и зарезервированный синтаксис

Предлагается `markdown-it-py`, preset `commonmark`, без расширений и без вызова
HTML-renderer. Парсер нужен для определения fenced-block и его положения в дереве,
а не для извлечения требований. API возвращает token stream с уровнями вложенности
и диапазонами строк ([официальная документация](https://markdown-it-py.readthedocs.io/en/latest/using.html)).
Профиль `rules-markdown/v1` фиксирует exact package version в lockfile и в снимке;
обновление пакета/настроек без проверки совместимости требует новой версии профиля.

Базовая форма fenced-block следует
[CommonMark 0.31.2, §4.5](https://spec.commonmark.org/0.31.2/#fenced-code-blocks).
Дальнейшие ограничения — контракт сервиса:

- Распознаётся `fence` с info-string, который после удаления краевых ASCII SPACE/TAB
  в точности равен `review-ignore`; регистр значим.
- Допускаются backticks или tildes, минимум три одинаковых символа. Закрытие — того
  же вида и не короче открытия, без текста после него, кроме SPACE/TAB.
- Блок должен быть непосредственным ребёнком документа. Допустимы 0–3 начальных
  пробела как часть CommonMark fence; code block с отступом в четыре пробела не
  является директивой.
- Закрывающий fence обязателен. В отличие от обычного Markdown, EOF не считается
  корректным закрытием специального блока.
- Допускается не более одного специального блока, в том числе пустого. Два блока
  не объединяются и дают ошибку.
- Настоящий fenced-block с точной меткой внутри list/blockquote даёт
  `policy_ignore_block_nested`: это явная ошибка, а не незаметно недействующая маска.
- Info-string, начинающийся с `review-ignore` и пробела/табуляции с дополнительным
  параметром, даёт `policy_ignore_info_invalid`. Аргументов у директивы нет.
- `Review-ignore`, `review-ignore-example` и другие метки — обычный Markdown.
  Строки внутри внешнего fenced примера, inline code или HTML-блока не сканируются
  второй раз; маски из примеров не становятся политикой.

Уровень вложенности и закрытие определяются по токену и его исходному диапазону;
нельзя искать блоки одной regex по всему документу. Только для найденного
специального токена проверяется наличие реального closing fence. В `AGENTS.md`
даже точная метка является обычным текстом: разбор ignore выполняется только для
`.review/rules.md`.

### 4.2. Грамматика масок `review-ignore/v1`

Тело блока разделяется по LF. У каждой строки удаляются краевые ASCII SPACE/TAB;
пустые строки пропускаются. Порядок непустых строк сохраняется для диагностики.
Одна такая строка задаёт ровно одну маску. Повтор одинаковой маски допустим:
он не меняет результат; для эффективной политики дубли удаляются, все исходные
номера строк остаются в диагностике.

```text
pattern  = segment ("/" segment)*
segment  = "**" | component
component = one_or_more(literal | "*")
```

В `component` не допускаются два соседних `*`; `**` разрешён только как целый
сегмент. `literal` — Unicode scalar, кроме `/`, `\`, `!`, `?`, `[`, `]`, `{`, `}`,
управляющих символов и Unicode whitespace, отличного от обычного SPACE. SPACE
внутри сегмента допустим. Сегменты `.`/`..`, пустые сегменты и первый сегмент
формы ASCII-letter + `:` запрещены. Таким образом, `/foo`, `foo/`, `a//b`,
`C:/foo`, `./foo`, `a/../b` недопустимы. `!` зарезервирован и не может использоваться
даже как буквальный символ имени в маске v1.

| Конструкция | Семантика |
| --- | --- |
| Буквальный символ | Точное совпадение с Unicode scalar; регистр значим |
| `*` | Ноль или больше символов внутри одного непустого сегмента пути; `/` не пересекается |
| `**` | Ноль или больше полных сегментов пути |
| Маска целиком | Сопоставляется весь путь от корня, не подстрока |
| `#` | Обычный символ; комментариев в блоке нет |
| `.` в имени | Обычный символ; dotfiles не скрываются от wildcard |

Отрицания, `?`, классы символов, brace expansion и backslash-escaping не
поддерживаются. Это не `.gitignore`, не shell glob и не существующий matcher
структурированных `include/exclude`. Для каталога используется `generated/**`,
а не `generated/`. Маска `generated/**` также совпадает с файлом буквально
`generated`, поскольку `**` допускает ноль сегментов; для существующего каталога
она охватывает все его файлы. Маска `**` исключает все файловые источники контекста,
кроме действующих policy-документов в их специальной роли (§5.3).

Путь VCS декодируется адаптером из quoting провайдера ровно один раз. Он должен
быть относительным, использовать `/` как разделитель, не иметь пустых сегментов,
`.`/`..`, абсолютного префикса, backslash, NUL или управляющих символов. Путь
корневого файла не содержит разделителя и допустим. Для путей допустимы буквальные
`!`, `?`, `[]`, `{}`: запрет
на эти символы относится к синтаксису масок, а не к именам в Git. Путь с нарушением
контракта получает локальный технический пропуск `unsupported_path`, а не
«исправляется» свёрткой `..` (при невозможности изоляции — failed). Unicode-normalization,
case-folding и URL-decoding не выполняются ни для пути, ни для маски.

Валидация представимости, структуры и лимитов пути выполняется до ignore-matching.
Недопустимый или непредставимый путь VCS даёт локальный технический пропуск
`unsupported_path`, если источник можно надёжно изолировать. Это не совпадение
с ignore-маской и не основание считать файл проигнорированным; остальные файлы
продолжают обработку с неполным покрытием. Содержимое и автоматически добавленное
имя такого источника не допускаются ни в один вход LLM. Невозможность изоляции или ошибка целостности
snapshot останавливает run; полная семантика определена в
[CONTEXT_AND_VERIFICATION_SPEC §9.1](CONTEXT_AND_VERIFICATION_SPEC.md#91-идентичность-снимка-и-файлов).

Matcher должен использовать ограниченный автомат/динамическое программирование,
а не regex с неограниченным backtracking. Состояние segment matching — пара
индексов маски и пути; для wildcard внутри сегмента — пара индексов символов.
Переход из ранее невычисленного состояния считается одной операцией бюджета.
Результаты для `(ignore_digest, canonical_path)` мемоизируются в пределах run;
повторное использование не тратит бюджет заново. Превышение лимита останавливает
run; нельзя трактовать непроверенные пути как разрешённые или проигнорированные.

### 4.3. Нормативные примеры разбора

| Вход | Результат |
| --- | --- |

| `  generated/**  ` | Одна маска `generated/**` |

| `generated/**` и `generated/a.py` / `src/generated/a.py` | Совпадает / не совпадает |

## 5. Применение политики ко всем входам LLM

### 5.1. Порядок и фильтры

Pipeline должен соблюдать порядок: закрепить версии и документы → валидировать
политику → получить согласованный inventory → валидировать пути и изолировать
`unsupported_path`/`identity_unresolved` → для достоверной идентичности применить
`review-ignore` (обе стороны rename/copy) и built-in generated → доказанные binary/empty_file
исключения → классифицировать остальные пропуски → сохранить VCS-only DiffMap
и отдельную run-классификацию (также для skipped) → оба триггера summary-only
(unknown inventory/relevant counters или >3 000 counted allowed строк) → остальные
исходы по [CVS §2.2](CONTEXT_AND_VERIFICATION_SPEC.md#22-порядок-операций)
→ только при анализируемом тексте выбрать контекст/конвенции → pre-send guard.

Маска или generated побеждает binary/too_large, если путь и обе стороны rename/copy
достоверны; `unsupported_path`/`identity_unresolved` не превращаются в ignored
через совпадение доступного alias. Binary — доказанное встроенное исключение,
не неполнота: сервис анализирует текстовый scope, а не содержимое картинок/шрифтов/PDF.
Само отсутствие patch или расширение файла не доказывает binary. Нужен достоверный
факт адаптера, NUL в patch либо bounded blob evidence (NUL в первых 8 KiB или
magic PNG/JPEG/GIF/PDF/ZIP/ELF). Oversized blob без независимого доказательства
получает too_large до blob-based binary-проверки; GitHub-удаление картинки без
нового blob и независимого evidence — missing_patch/incomplete. Критерии и единое поле сохранённой
классификации — CVS §9.2. Built-in generated matcher сохраняет собственную версию
и семантику, его версия входит в `ignore_digest`.

Технические пропуски `unsupported_path`, `identity_unresolved`, `too_large`,
`unsupported_change` не являются ignored; в целевом профиле #107 вместе с
анализируемыми файлами дают partial (либо summary-only по оставшемуся scope),
а без них — none по строгому условию CVS §2.2. `unsupported_change` охватывает
submodule/gitlink и доказанный чистый rename/mode-only без поддерживаемого анализа.
Raw patch_state=metadata_only при changes=0 не доказывает ни T, ни E.
Для пустого added #213 вводит E=`empty_file` только по полному proof
[CVS §9.2](CONTEXT_AND_VERIFICATION_SPEC.md#92-hunks-и-проход-по-строкам):
поддерживаемый канонический точный путь, added без предыдущего пути (`previous_filename is None`,
логический `old_path=null`), исходный patch=None/пустая строка (при reload также
точная сохранённая пустая обёртка `diff --git` / `---` / `+++` того же пути без
иных строк), все три counters=0,
точный empty Git blob SHA, непротиворечивый size и независимые type=blob /
mode=100644|100755. Не более одного optional recursive tree-запроса на pinned
head при кандидатах, полный unique exact path+SHA match, cap **1 500 000 байт**
(identity encoding, streamed read); без кандидатов запроса нет, дополнительных
blob-байт для доказанных кандидатов нет. Missing/failed/capped/truncated/duplicate
metadata, несовпадение SHA/пути/типа/mode, symlink/gitlink или конфликт остаются
missing_patch/incomplete; один SHA не proof. Cancellation/deadline не подавляются.
Validated marker сохраняется в omission_reason через CHECK-миграцию `20261026_0043`,
reload проверяет durable поля и `previous_filename is None`; legacy missing_patch
по SHA не повышается.

Решения #213 по остальным случаям сохраняют блокировку clean рядом с кодом:
доказанный pure rename/mode-only — unsupported_change/T; без no-text proof —
missing_patch/incomplete, raw status и нулевые counters не доказывают тип.
Удалённый binary без независимого proof остаётся missing_patch/incomplete;
base/old blob не читается, расширение не доказательство. Blob >1 048 576 байт
без предварительного независимого binary proof становится too_large до чтения:
это известный проектный компромисс подтверждения binary при blob cap 1 MiB,
а не универсальная публичная причина всех too_large. Prefix/range read и новый
size-origin столбец не вводятся. Для этих четырёх случаев дополнительных
tree/blob/compare-запросов нет; независимо доказанный binary остаётся E.
При пустых/info findings mixed run имеет partial/null; фактические supported
critical/high либо medium/low сохраняют blocking/attention при partial.

Канонические тексты причин #213 для summary/body/check-run (без завершающей
точки; оформление сводки может добавить счётчик, разделитель и точку):

| Случай | Полный текст причины |
| --- | --- |
| Доказанный pure rename, unsupported_change | Семантика переноса файла (включая импорты) не анализируется |
| Rename без no-text proof, missing_patch | Отсутствующий patch не подтверждает неизменность содержимого переноса |
| Доказанный mode-only, unsupported_change | Изменения прав доступа/типа файла не анализируются |

| Удаление без независимого binary proof | Удалённое содержимое недоступно для подтверждения binary |

| patch_malformed | patch повреждён |

Метки оформления сводки и списка причин (не коды причин):

| Условие | Точная метка |
| --- | --- |
| coverage=partial | Проверка неполная |
| coverage=none | Текстовые изменения не проверены |

| Строчная метка verdict при partial без supported риска | проверка неполная |
| summary.done_well; reviewed_files — проверенные текстовые файлы, excluded_files — сумма exclusions | Проанализировано файлов с текстовыми изменениями: {reviewed_files}; исключено файлов: {excluded_files}. |
| Число проверенных текстовых файлов в partial/none overview | **Проверено файлов с текстовыми изменениями:** {reviewed_files} |

| Строка coverage в partial/none overview; summary_problem включает точку | **Coverage:** {status} — {summary_problem} |

Текст «Нет подтверждения обычного пустого файла» выбирается только по
доверенным backend-фактам квалифицированного кандидата: поддерживаемый
канонический путь, status=added, `previous_filename is None` (логический
`old_path=null`), additions=deletions=changes=0, точный Git empty-blob SHA и
size=None/0. Исходный patch равен None или пустой строке; при reload допустима
также точная сохранённая пустая обёртка `diff --git` / `---` / `+++` того же пути
без иных строк. При этом принятого ordinary-file proof нет. Один added, пустые
counters либо raw metadata_only недостаточны. Предыдущий путь, неподдерживаемый
путь, неизвестные/ненулевые counters, неверный/неизвестный SHA, конфликт размера
или иной patch не получают empty-текст: действует соответствующая общая причина,
для обычного added без patch — «Отсутствует подтверждённый patch».
У GitLab в этом потоке нет независимого tree-доказательства обычного файла:
пустое добавление остаётся `missing_patch`/partial, даже при empty SHA и size=0.
Квалификация переносится из durable фактов, не из model JSON. Новые сохранённые
coverage с более чем 20 причинами могут содержать внутренний optional
`reason_variant_counts`: не более шести фиксированных семантических ключей и
числа, без путей. Это сохраняет канонический текст за окном первых 20
диагностических путей без раскрытия новых имён. Restore проверяет суммы по
reason_counts и доверенную snapshot capacity; legacy без агрегата не получает
выдуманной квалификации за окном. Поле не добавляется в публичный DTO/LLM schema.
Отсутствие proof не утверждает, что файл действительно обычный и пустой.
Для исключения E=empty_file нужен независимый полный nontruncated tree на
закреплённом head: уникальное точное совпадение path+SHA, type=blob,
mode=100644/100755 и size=None/0; предел ответа — 1 500 000 сырых байт.
Для too_large снимок не хранит источник лимита (blob bytes, patch bytes или
строки), поэтому публичный текст нейтрален и не приписывает всем случаям binary/1 MiB.



Доказанные исключения и технические пропуски не расходуют LLM-бюджет и не входят
в пороговый счётчик 3 000 строк; исходные счётчики VCS сохраняются в диагностике,
неизвестные — `null`, не 0. 4 000 таких строк и 50 анализируемых дают обычное
ревью 50 строк, с partial при техническом пропуске. Это целевой контракт #107:
legacy main ещё учитывает `too_large` в пороге. `patch` сохраняется для UI,
`review_patch` содержит только допустимый вход модели. Поздний фильтр после
сохранения summary-only недостаточен.

Маски применяются до выбора и загрузки исходников конвенций, окружающего кода,
полных файлов, импортов, AST-определений и кандидатов графа RAG v1. Повторный
вызов, repair и fallback не разрешают обойти запрет.

Кандидаты графа RAG v1 ([ADR 0001](adr/0001-graph-rag-v1.md#9-бюджет-manifest-ignore-и-инъекции))
проходят ignore дважды. При индексации действуют встроенные исключения и
`review-ignore` из `.review/rules.md` на HEAD default branch; исключённый файл не
попадает в индекс. Отсутствие файла доказывают только полные Git tree листинги
того же закреплённого commit. Архив сам по себе этого не доказывает: `export-ignore`
может скрыть `.review/rules.md` или весь родительский каталог. Поэтому индексатор
всегда читает оригинальный rules blob через tree/blob на commit исходного архива;
архивная копия, включая изменённую `export-subst`, не задаёт политику (#207).
Достоверное отсутствие даёт пустые пользовательские маски; built-ins сохраняются.
Ошибка чтения (включая 404, усечённый или неоднозначный tree), типа, UTF-8, лимита или разбора
завершает попытку RELEASED с `last_error_code=policy_*` без новой публикации;
fallback к пустой политике запрещён. Последняя публикация сохраняется, её нельзя
объявить индексом нового HEAD. Контракт строк и стоимость чтения —
[SD §7.4](SYSTEM_DESIGN.md#index-row-contract); применение ignore —
[ADR 0001 §9](adr/0001-graph-rag-v1.md#9-бюджет-manifest-ignore-и-инъекции).
При ревью закреплённый ignore run заново применяется к каждому
кандидату до чтения его blob: индекс, построенный по другой маске, разрешения на
отправку не даёт. Исключённый кандидат не читается и учитывается только счётчиком,
без пути. Перед отправкой проверяются структурированные source
records окончательного payload; regex по готовому prompt не является этой проверкой.
Каждый вызов получает собственный окончательный manifest по связанной спецификации.

Для `unsupported_path` изоляция охватывает автоматически добавленное имя и
содержимое во всех источниках: diff, AST, импортированном и окружающем коде,
полных файлах, conventions и их кэше,
repair, fallback и автоматически собранных метаданных. Нельзя восстановить доступ
через другую роль или безопасно выглядящий alias. Утечка такого источника в
окончательный payload даёт `policy_context_violation` до отправки.
Проверка опирается на provenance источника; она не требует искать и удалять
совпавшие строки имени внутри кода других разрешённых файлов.

### 5.2. Переименования и копирование

Для modified/added используется новый путь, для removed — старый. Для rename/copy
проверяются оба пути: совпадение любого исключает весь diff-блок и файловый контекст
по новому пути в этом run. Запрет сохраняется в provenance как alias/taint от
исходного пути, в том числе для повторной загрузки через импорт разрешённого файла.

Если любой из путей rename/copy имеет `unsupported_path`, технически пропускается
всё изменение, включая контекст и alias нового пути. Ignore-matching допустимой
стороны не превращает такой пропуск в доказанное исключение по политике.

Пример: `generated/client.py → src/client.py` при `generated/**` исключает patch,
новый полный файл и определения `src/client.py`, запрошенные через импорт. Смена
роли блока с diff на AST не снимает запрет. Источник rename/copy должен поступать
из проверяемых VCS-метаданных, не из текста модели. При недостоверных путях источник
получает `identity_unresolved` и пропускается в этом run без ожидания и без
отправки модели (CONTEXT_AND_VERIFICATION_SPEC §9.1). Гарантия относится к установленным
rename/copy связям; сервис не объявляет поиск произвольных скрытых копий кода.

### 5.3. Исключение для действующей политики

Снимки `.review/rules.md` и корневого `AGENTS.md` передаются независимо от масок
только как `source_kind = repository_rules` / `project_conventions_document`
и `source_role = policy_document`, с
`revision = policy_base_sha`, checksum и `policy_document = true`.
Это исключение нельзя назначать произвольному файлу или новому содержимому этих
путей на `head_sha`.

При `**/*.md` действующие два документа из base остаются policy-блоками. Их
изменения в diff, версии из head, AST/full-file запросы по ним и остальные Markdown
файлы исключаются. Если PR впервые добавляет `.review/rules.md`, его новый текст
не является политикой; если он разрешён масками, его можно анализировать как
обычное проверяемое содержимое. После merge новый run прочитает новый base.

Автоматические `repo_tree`, `changed_files`, `omitted_files` скрывают и имена
исключённых файлов, заменяя их общим счётчиком. В UI/диагностике остаются пути,
совпавшие маски, исходные пути rename/copy и причины. Эти файлы не считаются
проверенными. Маски/пути внутри текста самих документов не вычищаются.

Гарантия — запрет использования исключённых файлов как источников контекста LLM.
Она не обещает, что общий VCS-ответ не содержал их patches или что backend не
сохранил их для UI; не ищет все возможные цитаты их кода в PR description или
правилах. Сообщения коммитов PR (#82) — такой же авторский текст, как PR
description: имена исключённых файлов в них не фильтруются (решение техлида, #168).
Кэш blob также не является разрешением показать blob модели.

### 5.4. Приоритет файлов сохраняется отдельно

Для допустимого файла сохраняется формула:

```text
priority = type_weight × ln(additions + deletions + 1) × rules_multiplier
```

`type_weight`: тесты 0.6, распознанные конфиги 0.4, остальные 1.0. Множитель 1.5
применяется один раз, если путь совпадает хотя бы с одним `include` и ни с одним
`exclude` внутри хотя бы одной структурированной priority-группы; иначе 1.0.
Совпадения нескольких групп не перемножаются. При равенстве — сортировка по пути.
Если всё помещается, отбор по весу не нужен.

Существующие 12 priority-групп JSON-дефолтов сохраняются с их масками без перевода
на `review-ignore/v1`, включая brace expansion текущего matcher. Их формат и
matcher версионируются отдельно. Markdown не преобразуется в priority-группы.
Отсутствие бонуса не отменяет базовые проверки; file priority не изменяет иерархию
требований. Старые `include/exclude` конкретного требования нельзя автоматически
переносить в ignore: область применимости проверки не равна запрету передачи файла.

## 6. Дефолты сервиса и перенос текущего набора

### 6.1. Целевая модель

Каждый новый run получает один полный набор `service-defaults/v2`, независимо от
преобладающего стека. Он содержит универсальные проверки и условные Python/backend,
TypeScript/React/frontend рекомендации. Применимость последних определяется по
показанному коду и явным соглашениям проекта, а не по обязательному наличию `app/`
или `src/`. В mixed repository обе части доступны одновременно.

Универсальное ядро переносится из `review.system.v2` в отдельный блок дефолтов:
security — инъекции, секреты/логи, небезопасная десериализация, SSRF, traversal,
отсутствие авторизации; correctness — границы значений, гонки, утечки ресурсов,
ошибки/краевые случаи, off-by-one и межфайловые инварианты; performance — N+1,
лишние копии/аллокации, неограниченная работа и сетевые вызовы внутри транзакций;
readability — согласованность имён, архитектурные границы, устаревший комментарий
и необоснованный мёртвый код. Stable IDs ядра: `SEC1`, `COR1`, `PERF1`, `READ1`.

Обязательные правила об обоснованности, валидной схеме, полномочиях, запрете
выдумывать недоступный контекст и детерминированном удалении замечаний линтера
остаются в system message, не в переопределяемых дефолтах. Порог длины функции и
другие эвристики не превращаются в безусловный дефект: finding должен объяснять
конкретное ухудшение и пройти verifier. Отсутствие теста/символа в неполном контексте
не доказывает его отсутствие в репозитории.

Специфичные `Zod`, FSD, Clean Architecture, UnitOfWork, пути модулей и тестов
применимы только при подтверждённом использовании соответствующего подхода.
Эквивалентная валидация внешнего ввода не становится нарушением только из-за
другого инструмента. Условия применимости сохраняют смысл исходных требований,
но не навязывают стек любому репозиторию.

Отступление как построено (решение техлида 26.10.2026, #130 F2; Q1 в
`docs/plans/130-snapshot-switch-plan.md`):
`review.system.v4` оставляет порядок анализа v3 (security → correctness →
performance → readability) в system message, и finding по этим стандартным
критериям получает `rule_name: null`. `<service_defaults>` рендерит наборы правил
v1 (`default-backend.v1`, `default-frontend.v1`; check ID — §6.2); наборов `SEC1`,
`COR1`, `PERF1`, `READ1` нет. `service-defaults/v2` — отдельное изменение: новая
версия дефолтов и prompt v5 или новее.

## 7. Неизменяемый снимок run и хранение

### 7.1. Контракт snapshot

Предлагается отдельная таблица `run_policy_snapshots` с PK/FK `run_id`, уникальным
`snapshot_id` UUID и неизменяемой записью после успешной сборки. Содержимое
snapshot описывается `schema_version = 1`.

**Инженер 3 (createunix)** владеет схемой и всеми миграциями этой таблицы,
включая хранение `prompt_bindings` и `execution_profile`. Он также отвечает за
связанные изменения хранения привязок версий run и staging `run_policy_documents`
из §7.2. Отдельные миграции инженера 4 (#120) для этих таблиц и полей не создаются.

Состав snapshot:

| Поле | Значение |
| --- | --- |
| `run_id`, `snapshot_id`, `repository_id` | Владелец и идентичность снимка; repository должен совпадать с run |
| `policy_base_sha` | Ровно сохранённый `Run.base_sha`; не обозначает автоматически LEFT diff |
| `documents` | Ровно две записи для `.review/rules.md` и `AGENTS.md`: presence, blob_oid, raw/text SHA-256, raw bytes, text, byte/line counts |
| `ignore_patterns` | Уникальные валидные маски в лексикографическом порядке. Исходные строки масок для диагностики — не отдельное поле: они в staged `rules.text` снимка. Их восстанавливают повторным разбором этого текста стадия политики (`review_context_stage.py`) и pre-send guard; чтение снимка из хранилища текст не разбирает. Результат сверяется с `ignore_patterns` и с `ignore_digest`, пересчитанным по версиям снимка. Если текст больше не разбирается, даёт другие маски или другой `ignore_digest` (дрейф парсера, лимитов или грамматики после деплоя), действуют сохранённые маски без номеров строк и в лог пишется предупреждение: строки — диагностика и run не останавливают. Отказ pre-send guard по маске называет эту маску и, когда строка известна, первую строку с ней в `.review/rules.md` |
| `parser_profile`, `matcher_version`, `limits_version` | `rules-markdown/v1`, `review-ignore/v1`, `policy-limits/v1`; exact parser version также закреплена |
| `builtin_exclusions_version`, `priority_matcher_version` | Версии встроенных исключений и отдельного matcher веса |
| `ignore_digest` | Checksum всех данных, определяющих допуск файлов |
| `service_defaults_rule_version_id`, `defaults_checksum` | Первый равен `Run.rule_version_id`, checksum проверяется при чтении |
| `prompt_bindings` | Immutable ID/checksum для `review.system`, `review.conventions`, `review.verifier`; review ID совпадает с `Run.prompt_version_id` |
| `severity_threshold` | `all`, `warning` или `critical` из Repository; сохраняется в Run при создании и копируется в snapshot (#212), неизменяемый вход публикации; у исторических Run NULL |
| `max_comments` | Inline cap 1–10 из Repository, сохраняется в Run и snapshot вместе с порогом (#212); у исторических Run NULL |
| `execution_profile` | Закреплённые primary/fallback model IDs, provider routes, tokenizer/counter versions, temperature, response-schema, recovery/budget profile из связанной спецификации |
| `policy_digest` | Checksum документов, допусков, дефолтов, prompt bindings, interpreter/execution versions |
| `created_at` | Время фиксации; не влияет на policy_digest |

Все digest — lowercase SHA-256 hex. Для объектов используется canonical JSON:
ключи сортированы, UTF-8, без незначащих пробелов, `ensure_ascii = true`, числа
целочисленные либо конфигурационные decimal-строки; массивы сохраняют определённый
порядок. Алгоритм сериализации версионирован как `policy-json/v1`.

```text
ignore_digest = SHA256(canonical_json({
  version, matcher_version, builtin_exclusions_version,
  sorted_unique_patterns, rename_copy_propagation: "both-paths/v1",
  policy_document_exemption: "base-policy-role-only/v1", limits_version
}))

policy_digest = SHA256(canonical_json({
  schema_version, policy_base_sha,
  documents: [{path, presence, raw_sha256, text_sha256}],
  ignore_digest, parser_profile, exact_parser_version, limits_version,
  defaults_checksum, prompt_bindings, execution_profile, priority_matcher_version
}))
```

Закрепление threshold/cap реализовано в #212: оба значения читаются из Repository
в транзакции создания Run, сохраняются в его полях, `RunPolicyPins` и policy snapshot.
Текущий legacy postprocess использует поля Run независимо от наличия snapshot.
Retry сохраняет пару; новый Run и rerun закрепляют текущие настройки Repository.
Для исторических Run оба поля остаются NULL без backfill; postprocess и retry
читают текущую пару Repository. Создание или чтение snapshot такого Run сохраняет
NULL, не превращая fallback в закрепление.

`severity_threshold` и `max_comments` — закреплённые настройки публикации,
они не входят в `policy_digest` и ключ conventions cache: не меняют правила,
источники или вход модели conventions. В целевом профиле #107/#130 они входят в `FinalReviewResult` и его
`result_digest`, а через него — в идентичность публикации (CVS §8.1/§10).
Формула `policy_digest` и `schema_version=1` здесь не меняются.

В `policy_digest` не входят `run_id`, случайные UUID снимка или время: одинаковая
политика имеет одинаковый content digest. Идентичность публикации включает run и
снимок отдельно. Изменение только prose правил меняет policy_digest, даже если
ignore-маски остались теми же. Отсутствие документа кодируется явно, а не checksum
пустой строки.

Raw bytes сохраняются в ограниченном bytea-поле либо неизменяемом объекте по
checksum; первый вариант достаточен для двух файлов по 64 KiB. Эти данные доступны
только в рамках авторизованного repository/workspace и не копируются целиком в
общие логи. Retention соответствует run/trace; ссылки на версии не удаляются,
пока ими пользуется сохранённый run.

### 7.2. Закрепление и повторные попытки

Для новых Run уже реализовано (#212): короткая транзакция создания сохраняет
`severity_threshold` и `max_comments` из текущей строки Repository в Run.
Обе настройки переносятся через `RunPolicyPins` в готовый policy snapshot;
legacy postprocess и вход Reflection Pass читают порог Run, а не живую настройку
Repository. Retry сохраняет пару; новый run и rerun закрепляют текущие значения.
Исторические Run с обоими полями NULL не backfill-ятся: обе настройки читаются
из Repository при каждой обработке и retry, готовый snapshot сохраняет NULL.

Merged #130 D уже закрепляет все три prompt ID при создании Run: review prompt
(`prompt_version_id`), conventions (`conventions_prompt_version_id`) и verifier
(`verifier_prompt_version_id`, миграция `20261024_0039`). Repository override действует
только для review prompt; для двух остальных выбираются активные версии своих keys.
При отсутствии активной версии pin остаётся NULL без подстановки на retry;
исторические NULL также не backfill-ятся. `RunPolicyPins` читает ID/checksum/version
из закреплённых строк, а готовый snapshot не переписывается после активации новых
prompts. Rerun выбирает новые текущие bindings.

Execution profile пока фиксируется первым сохранённым snapshot, а не транзакцией
создания Run: это принятое отклонение от полного целевого профиля #107.
Подключение snapshot/полного профиля к боевому пути #130 F этим изменением не выполняется.
После commit worker читает VCS вне DB-транзакции по сохранённому base SHA.

До полной сборки snapshot допустимы отдельные immutable `run_policy_documents`
с уникальным `(run_id, path)`: это staging загруженных документов/фактов отсутствия.
Повторная попытка переиспользует их, дополняет только отсутствующие записи и не
перезаписывает успешную загрузку. Ошибку сети нельзя записать как missing.
Документы читаются по очереди: сначала `.review/rules.md`, затем `AGENTS.md`. Каждый
прочитанный документ или доказанное отсутствие записывается в staging своей короткой
транзакцией до чтения следующего, поэтому ошибка одного документа не теряет staging
другого. После ошибки следующий документ в этой попытке не читается; после
retryable-ошибки его читает retry.
После разбора короткая транзакция атомарно создаёт `run_policy_snapshots` из обеих
записей и фиксированных привязок. Привязки версий входят в snapshot при его
создании: последующее дополнение готовой записи через `UPDATE` не допускается.
Конкурирующий worker использует уже сохранённый снимок; несовпадающий checksum
при том же immutable source означает
`policy_snapshot_integrity_error`, а не last-write-wins.

Ни один LLM-вызов не разрешён до готового snapshot. При ошибке конфигурации
сохраняются имеющиеся документы и диагностика, run завершается `failed`; полного
валидного snapshot может не быть. Retry одного run использует те же версии,
источники, семантику, effective policy и подготовленные diff snapshots. Новый
rerun — новый run с новой привязкой версий и ревизий, даже при прежнем head.

Если закреплённый artifact/prompt/tokenizer недоступен или checksum не совпадает,
нельзя использовать активную версию вместо него: `policy_snapshot_integrity_error`.
Для оценочного подсчёта токенов консервативная оценка в 3 символа на токен (`(len(text) + 2) // 3`)
определяется версией `counter_version = "counter/v2"`. Подсчёт разрешается через фабрику
`token_counter_for(counter_version)`: неизвестная версия счётчика прерывает выполнение
с ошибкой `policy_snapshot_integrity_error`. Прежняя оценка в 4 символа на токен закреплена
за версией `"counter/v1"`. Контекстная стадия до фиксации snapshot (#168) использует
локальный счётчик в 4 символа на токен; синхронизация контекстной стадии на `"counter/v2"`
передана в #168. Модель verifier `verifier_model` закрепляется значением первичной модели
рецензирования (`review_model`, по умолчанию `"mistral-small-4"`). Версии вспомогательных профилей
фиксируются и разрешаются через `validate_execution_profile_versions(profile)` и `send_budget_for(profile)`
(неизвестная версия любого из полей прерывает выполнение с `policy_snapshot_integrity_error`):
- `tokenizer_version = "tokenizer/v1"` — символьно-эвристическая схема токенизации UTF-8 без внешнего BPE-словаря, работающая в паре с закреплённым `counter_version`;
- `recovery_profile_version = "recovery/v1"` — профиль восстановления gateway (однократный JSON-repair с блоком `previous-output` при ошибке схемы и переключение на `fallback_model` при отказе primary, с обязательным pre-send guard и manifest на каждом вызове);
- `budget_profile_version = "budget/v1"` — профиль бюджетирования отправки (`send_budget_for`: расчёт бюджета отправки из окна конкретной модели и профиля исполнения за вычетом резерва на максимум выхода модели `min(context_window, max_input_tokens) - max_output_tokens` с учётом переопределений окружения и модели; conventions рассчитывается через `gateway.max_prompt_tokens`, без отдельных квот документов).
Все repository writes выполняются через use case/UoW; repository вызывает flush,
commit выполняет use case. VCS/LLM вызовы происходят вне транзакций.

### 7.3. Совместимость `rule_versions` и миграция

`rule_versions` остаётся repository-local, версионированным и неизменяемым.
Для новых данных предлагаются `format_version = 2`, `origin = service_defaults`,
`artifact_key = service-defaults/v2`, `priority_profiles` JSONB. `rules` v2 содержит
массив `{id, text, applies_when, severity_hint}` с уникальными stable IDs §6.
`priority_profiles` сохраняет 12 исходных include/exclude групп с именами,
квалифицированными стеком, и версией matcher.

Для v2 `checksum` вычисляется по canonical JSON всего manifest: format_version,
artifact_key, rules, priority_profiles и версии интерпретации; для v1 сохраняется
старый checksum только массива rules. Выбор функции checksum определяется
format_version, не догадкой по структуре. Новый combined default artifact
создаётся при реализации; существующие `default-*.v1.json` не редактируются.

`Run.rule_version_id` продолжает указывать на immutable row. Markdown не записывается
в `rules` и не получает вторую активную DB-копию пользовательской политики. Новые
версионные default rows для репозиториев создаются явно; преобладающий стек больше
не выбирает единственную доступную половину проверок.

Миграция должна быть добавочной: существующим rows присваиваются `format_version=1`,
`origin=legacy`. Старые значения не переименовываются в достоверные custom/default
источники без provenance. Старые завершённые runs читаются прежним renderer/schema
и не получают выдуманные snapshots. Существующий legacy pending run либо дорабатывает
закреплённым legacy pipeline, либо явно отменяется с предложением нового rerun;
нельзя наполовину переключить его на новую политику. Период rollout фиксируется
через `pipeline_contract_version` run; legacy режим не объявляется соответствующим
новым спецификациям. После переключения создаются только новые versioned runs.

### 7.4. Граница загрузчика и LLM-пайплайна

**Инженер 3 (createunix)** отвечает за чтение VCS и загрузчик политики: получает
`.review/rules.md` и корневой `AGENTS.md` из закреплённого `policy_base_sha`,
проверяет тип/размер/UTF-8, нормализует текст по §3.2, разбирает только машинный
блок `review-ignore` и сохраняет policy snapshot по §§7.1–7.2. Отсутствие документа
и ошибка чтения остаются разными исходами. Заголовки, требования и исключения
не извлекаются в отдельный список правил.

Граница передачи — полный неизменяемый snapshot, а не отдельная строка
`rules_text`: `snapshot_id`, `run_id`, `repository_id`, `policy_base_sha`,
`policy_digest`, документы с path/source kind, presence, blob/checksums, полным
нормализованным текстом и нумерацией строк, разобранная ignore-политика и
закреплённые версии/профили §7.1. Raw bytes сохраняются для воспроизводимости;
в prompt передаётся нормализованный документ целиком, включая `review-ignore`.

**Инженер 4 (#219)** предоставляет контракт и значения `prompt_bindings` и
`execution_profile` для закрепления при создании run по §7.2: immutable
ID/checksum промптов, версии моделей и профилей. Их хранение и миграции реализует
инженер 3 по §7.1; инженер 4 не дописывает версии в готовый snapshot.
Как построено: prompt bindings закрепляются при создании run — `runs.prompt_version_id`
и, с #130 D (миграция 0039), `runs.conventions_prompt_version_id` и
`runs.verifier_prompt_version_id`; execution profile фиксирует первый сохранённый
snapshot (принятое отклонение, §7.2).

Инженер 4 использует готовый snapshot без повторной загрузки VCS и
разбора `review-ignore`. Он реализует безопасный prompt envelope, атрибуцию и
обязательный verifier по §8 и связанной спецификации. Смысл требований и их
применимость определяют reviewer/verifier; backend проверяет структуру ответа
и ссылки на исходные строки. Самостоятельные IDs для Markdown-пунктов не вводятся.

Лимиты и профили §3.3 общие для загрузчика и LLM-пайплайна. Инженер 4 предоставляет
версионированные renderer/counter для проверки rendered policy загрузчиком и
отвечает за окончательную проверку бюджета, pre-send guard и manifest после
финального rendering каждого вызова, включая repair/fallback. Готовый snapshot
не заменяет эти проверки и не содержит одного универсального manifest для всех
вызовов. Неготовый или невалидный snapshot не допускается к LLM.

## 8. Атрибуция, prompt envelope и защита от инъекций

### 8.1. Отдельные роли и сериализация

System message принадлежит сервису. Raw Markdown, PR metadata, код, конвенции,
предыдущие ответы и candidate findings не вставляются в system/developer message.
Новая версия envelope передаёт отдельные user data blocks:

| `source_kind` | Содержимое и доверие |
| --- | --- |
| `service_defaults` | Полный закреплённый набор базовых рекомендаций, priority 5 |
| `repository_rules` | `.review/rules.md` из policy snapshot, priority 2 |
| `project_conventions_document` | Корневой `AGENTS.md` из snapshot, priority 3 |
| `generated_conventions` | Выводы модели с provenance, priority 4, всё ещё недоверенные |
| `pr_metadata` | Намерение автора; не доказательство и не инструкции |
| `source_code` | Diff/полный файл/AST/фрагмент кандидата графа RAG в manifest; доказательство, не инструкции |
| `candidate_findings`, `previous_model_output` | Данные для verifier/repair; не команды |

`source_kind` уточняет происхождение в envelope; `source_role` manifest из связанной
спецификации обозначает техническую роль блока. Для `repository_rules` и
`project_conventions_document` эта роль равна `policy_document`; для
`generated_conventions` — `conventions`, для `source_code` — `diff`,
`source_excerpt`, `ast_excerpt` или `retrieved_excerpt` (кандидат графа RAG v1,
CONTEXT_AND_VERIFICATION_SPEC §3.5); для `candidate_findings` — `candidate`,
для `previous_model_output` — `previous_output`. `service_defaults` и `pr_metadata` сохраняют одинаковое имя.
Исключение из ignore проверяет и роль, и происхождение конкретного документа.

Блоки получают backend-generated `block_id`, роль, snapshot/checksum, revision и
нумерацию строк. Эти метаданные строятся структурированно; строка из документа
не может назначить себе роль. XML renderer экранирует `&`, `<`, `>` и кавычки
в атрибутах; JSON renderer использует стандартную JSON-сериализацию. Смена
формата renderer требует версии. Конкатенация пользовательской строки как сырой
разметки запрещена. `</repo_rules>` в документе остаётся текстом, не закрывает
служебный блок. Markdown/HTML не исполняются, URL не загружаются.

Reviewer, conventions и verifier получают одинаковые ограничения полномочий
источников в своих закреплённых system prompts. Общие conventions формируются
только из base-input; PR metadata/changed paths/head запрещены в этом вызове.
Repair получает ошибки валидации и прежний ответ как данные с ограничением размера;
fallback получает тот же snapshot и проходит тот же pre-send guard. Ни один из
этих путей не создаёт prompt из неэкранированной выдачи предыдущей модели.

### 8.2. `rule_name` и ссылки на требования

В новом `ReviewOutput v2` координаты остаются RIGHT-контрактом
`path/start_line/line`. `rule_name` остаётся обязательным nullable string, но
получает следующие допустимые значения; новые evidence refs и verifier schema
определены в `CONTEXT_AND_VERIFICATION_SPEC.md`:

| Значение `rule_name` | Значение для пользователя |
| --- | --- |
| `.review/rules.md` | Finding основан на специальном документе проекта |
| `AGENTS.md` | Finding основан на общих соглашениях проекта |
| `service-defaults:<ID>` | Finding основан на конкретном stable check из закреплённого набора |
| `null` | Основание — видимый код/конвенции либо нет отдельной документальной атрибуции |

Произвольные имена секций не становятся IDs; backend не извлекает Markdown rules.
Название `Security` само по себе не является доказательством требования.
Старый обязательный body-prefix `According to custom instructions ...` снимается
только в новой версии схемы, prompts и validator. Backend формирует подпись по
проверенному source metadata; raw model body не управляет provenance.

Verifier возвращает `requirement_refs`:
`{block_id, start_line, end_line, check_id}`. `check_id` nullable, используется
только для `service_defaults`; SHA, source kind и revision backend восстанавливает
по manifest конкретного verifier-вызова. Для Markdown диапазон должен относиться
к соответствующему полному policy-блоку. Для defaults check должен существовать
в закреплённой версии и совпадать с `rule_name`. Для `supported`/`contradicted`
при ненулевом `rule_name` нужна валидная ссылка на требование. Если недостаточно
оснований — `insufficient_context`; нельзя заменить источник выдуманным именем.

Ссылка доказывает существование и видимость текста, а не правильность его
толкования: применимость подтверждается смысловым verifier. Evidence refs к коду
не заменяются ссылкой на правила. Если действуют несколько источников, `rule_name`
обозначает непосредственное основание высшего применимого приоритета, а остальные
сохраняются как requirement refs. Неверная атрибуция не должна молча превращаться
в подтверждённый generic finding без повторной смысловой оценки.

`.review/rules.md` и `AGENTS.md` допустимы как `rule_name`, только если
review-вызов показал этот документ с содержимым. Атрибуция к отсутствующему,
пустому или состоящему только из пробельных символов документу — отказ
`evidence_source_disallowed` в проходе 3 (CVS §6.2): кандидат отбрасывается
до verifier, а не продолжает путь с очищенным `rule_name`.

### 8.3. Технические ограничения

Все модели работают без shell, browser, сетевых инструментов и самостоятельной
VCS-публикации. Сервисные ключи/токены не входят в контекст. Backend, независимо от
ответа модели, проверяет схему, enum, длины, coordinates, видимость доказательств,
ignore, source hashes и целевой repository/PR/revision. Publication payload
формируется по сохранённому run, а не по URL/SHA/инструкциям модели.

Невалидный ответ приводит к ограниченному восстановлению или `failed`, не к
пустому успешному ревью. Валидный JSON и пустой findings сами по себе не доказывают
устойчивость к инъекции. Обязательный verifier не может гарантировать обнаружение
кандидата, который reviewer вообще не создал; оценка атак должна измерять и
подавление настоящих дефектов.

### 8.4. Кэш и перенесённые инструкции

Запись в БД, кэш-hit или наличие документа в base не повышают доверенность.
Общие conventions не могут зависеть ни от одного входа текущего PR: description,
title, changed paths, commit messages или head-content. Если такие данные
участвовали в вызове, весь результат считается run-local, даже если поля называются
`key_patterns`/`recommendations`.

Новый cache key включает repository/tenant, policy_base_sha, полный показанный
base-tree, исходные blobs и показанные диапазоны, policy docs/policy_digest,
ignore semantics, prompt/schema/model profile, defaults checksum, версии
selection/truncation/renderer/tokenizer. Manifest сохраняется после окончательного
усечения. Точная структура ключа и storage — в связанной спецификации; одного
`AGENTS.md SHA + prompt ID` или SHA выбранных файлов недостаточно.

Записи старого `repo_conventions` без доказуемого полного provenance не подходят
для нового cache lookup; они сохраняются для legacy runs и не получают фиктивный
ключ новой схемы. Изменение ignore требует пересчёта, поскольку старый результат
мог использовать теперь исключённый файл. Кэш AST/контекста подчиняется тому же
pre-send guard; доступность blob в кэше не разрешает обойти новую политику.

Индекс графа RAG v1 — тоже запись в БД и доверенности не повышает. Изменение
ignore в `.review/rules.md` на default branch или версии встроенных исключений
требует полной переиндексации
([ADR 0001 §6.3](adr/0001-graph-rag-v1.md#63-incremental)), а до её публикации кандидаты старого индекса всё равно проходят
закреплённый ignore run (§5.1). Код кандидата — недоверенные данные
`source_code`, не инструкции; новый блок контекста вводится только новой версией
промпта.

## 9. Ошибки и наблюдаемость

Диагностика содержит `code`, `source_path`, `policy_base_sha`, безопасное `message`,
nullable `line`, `column`, `pattern_index`, `limit`, `actual`, флаг
`actual_is_lower_bound` (`true`, когда `actual` — лишь нижняя граница) и `retryable`.
Строка/столбец — 1-based, столбец считается в Unicode scalars, не UTF-8 байтах.
Для ошибки маски указывается её строка в документе и первый недопустимый символ;
для duplicate block — второе открытие. Ошибка не выводит весь документ или секреты
в общие логи. Полные входы доступны только в защищённом trace.

Диагностика пишется в trace действия того шага, где возникла ошибка, —
`response.error.diagnostic` ([PIPELINE_SPEC §2](PIPELINE_SPEC.md#2-фазы-внутри-running-и-трейс-run_actions)):
ошибка загрузки или разбора документов, проверки профиля исполнения и бюджета
документов политики (`policy_prompt_budget_exceeded` с `limit`/`actual`, на пути
снимка с закреплённым v4 после #130 F2) — в `policy.load`,
ошибка сопоставления масок — в шаге, где сработал сопоставитель (`vcs.fetch_diff`,
`context.build`). `message` диагностики — без указания места. Run хранит только
`error_code` и безопасное сообщение с местом в `error_message`; отдельных колонок
для полей диагностики нет.

`policy_base_sha` есть у каждой записанной ошибки политики run: ошибка, место
которой базы не знает (например, проверка профиля исполнения или сохранённых
документов), получает закреплённую базу в `policy.load`; ошибки любого
сопоставителя на пути run (стадия политики и pre-send guard) несут её сами.
`source_path` называет документ, когда ошибка относится к нему: размер, кодировка,
управляющий символ, тип, блок и маски, чтение blob документа, проверка при чтении
сохранённых документов и снимка, бюджет сопоставления и отказ pre-send guard по
маске (`.review/rules.md` с масками). `source_path` — `null`, когда ошибка не
относится к одному документу:
чтение дерева (корня или `.review`), HTTP-отказ при чтении ветки или репозитория,
`policy_snapshot_integrity_error` профиля или снимка в целом, бюджет документов
политики (`policy_prompt_budget_exceeded`) и `policy_path_invalid` — ошибка о пути
репозитория, а не о документе.

У `policy_match_budget_exceeded` `actual` — значение счётчика, превысившего `limit`,
в момент остановки: нижняя граница реальной стоимости, а не точное значение.
Поэтому сообщение говорит «фактически более {limit}, допустимо {limit} переходов».

У `policy_document_too_large` `actual` точен, когда размер известен без чтения всего
blob: размер записи дерева, у GitHub также `Content-Length` несжатого ответа, у
GitLab — длина blob, который run уже прочитал. Иначе это нижняя граница с
`actual_is_lower_bound=true`: у GitHub — байты, полученные к остановке потока, у
GitLab — 65 537 (его чтение останавливается за пределом, не сообщая, сколько
прочитано). Сообщение тогда говорит «фактически более 65536, допустимо 65536», без
выдуманного точного значения.

Источники политики GitHub (run и статус правил, §10) читают blob документа сами, не
через VCS-провайдер run, поэтому его `BlobTooLargeError` на путь политики не
попадает: too_large дают размер записи дерева или сам поток. Поток
`application/vnd.github.raw+json` с `Accept-Encoding: identity` останавливается, как
только получено больше 65 536 байт (ровно 65 536 проходят); несжатый ответ с
`Content-Length` больше 65 536 не читается вовсе. Ответ с `Content-Encoding`, отличным от
identity, тоже не читается: это retryable `policy_fetch_transient`, ведь httpx
распаковал бы каждый фрагмент целиком раньше, чем предел его остановит.
Raw-ответ не повторяет SHA,
поэтому Git blob id полученных байтов пересчитывается (SHA-1, для id из 64 hex —
SHA-256) и сверяется с запрошенным; расхождение — retryable
`policy_fetch_transient`. Индексатор читает `.review/rules.md` тем же потоком с тем
же пределом, но id не сверяет
([PIPELINE_SPEC §5.2](PIPELINE_SPEC.md#52-сбои-github)).

Диагностику в trace не пишут фазы вне шагов трассировки, у них остаются только
`error_code` и сообщение Run: `apply_ignore` стадии политики
(`review_context_stage.py`) и проверки перед отправкой модели: pre-send guard
(`policy_context_violation`) в conventions, ревью, reflection и шлюзе LLM;
обязательный бюджет verifier (`policy_prompt_budget_exceeded`, один раз перед
вызовом ревью); повторная проверка бюджета подогнанного промпта ревью
(`policy_prompt_budget_exceeded`, только для ревью) и
`policy_snapshot_integrity_error` из `execute_review.py` (нет reflection pass,
снимок не готов к вызову LLM).

Ошибка действующего `AGENTS.md`, как и `.review/rules.md`, останавливает ревью;
необязательность документа означает допустимость его отсутствия, а не пропуска
непрочитанных соглашений. Check-run и приложение показывают путь, понятную причину,
допустимый предел и фактическое значение, когда оно известно, а также действие
для исправления. Например: «Размер AGENTS.md — 85 КиБ, допустимо 64 КиБ. Ревью не
выполнено; уменьшите документ». При остановке загрузки до получения полного размера
указывается подтверждённое превышение, без выдуманного точного значения. Для UTF-8
сообщение предлагает исправить кодировку. Если документы проходят собственные
лимиты, сначала сокращаются необязательные расширения контекста по CONTEXT §4.1;
сами документы сохраняются целиком. Предупреждение не заменяет ошибку политики.

Обозначения `nested`/`unclosed` в объединённой строке таблицы сокращают только
отображение: фактические коды — `policy_ignore_block_nested` и
`policy_ignore_block_unclosed`.

Временные ошибки используют общий bounded retry pipeline: не более трёх попыток
run, без скрытого бесконечного цикла загрузки. VCS-call retries, backoff, общий
deadline и rate-limit ожидание входят в существующий бюджет попытки; исчерпание
не разрешает пустую политику. Ошибка доступа отличается от rate limit по
подтверждённым headers/body провайдера, а не только HTTP-коду. Изменение credentials
или правил после терминальной ошибки требует нового rerun.

`unsupported_path` не смягчает ошибки общих документов `.review/rules.md` и
`AGENTS.md`: ошибки их чтения, разбора или целостности остаются `failed`.
Недопустимый путь отображается только в backend-диагностике/UI в ограниченном
по размеру, безопасно экранированном виде, не становится входом LLM и не
используется как угаданное или «исправленное» имя для загрузки/публикации.
Неизолируемый источник и нарушение целостности snapshot также дают `failed`.

Исходы run определяет каноническая таблица
[CVS §2.2](CONTEXT_AND_VERIFICATION_SPEC.md#22-порядок-операций).
`all_changes_ignored` требует доказанного исключения каждого изменения масками,
generated, binary или доказанным empty_file **без технических пропусков/incomplete**; результат — skipped, 0 LLM,
verdict=null. Неподдерживаемый путь, identity_unresolved, too_large и
unsupported_change не являются исключениями. При полном inventory, хотя бы одном
техническом пропуске и отсутствии любых иных неизученных/анализируемых записей
получается backend none, publishing → succeeded/neutral, не summary-only.
При наличии анализируемых файлов — partial либо summary-only по CVS §2.3.
Неизвестный inventory или обычный файл с missing patch не разрешают ветку none.
Без анализируемого текста при наличии incomplete и возможных E/T, полном inventory,
известных relevant counters ≤3 000 — backend partial, summaryOnly=false, findings=[],
verdict=null, 0 LLM, publishing → succeeded/neutral. Сохраняются pins,
below_severity_threshold_count=0 и reviewed_changed_lines=0; неизвестная исходная
статистика остаётся null. Анализируемый текст — разрешённые hunks вне E/T, включая сохранившиеся
hunks truncated в L1: обычное review/partial, blocking возможен; без hunks —
no-text ветка. Relevant counters — additions/deletions вне E/T, включая
incomplete; raw counters E/T — диагностика (пустой counted scope=0).
Оба триггера CVS §2.3 проверяются раньше этой ветки:
unknown inventory/counters либо >3 000 counted allowed дают summary-only/partial,
summaryOnly=true (включая known missing-patch-only 4 000 строк). Все backend-ветки
обходят conventions/context/reviewer/verifier; skipped — ещё и публикацию.
Доказанный binary-only/empty-only — skipped; binary/empty_file + проверенный код могут дать complete/clean. Причины всех
пропусков и исключений сохраняются отдельно по CVS §9.2.

## 10. Совместимость будущего Rules API и UI

Git-файл остаётся единственным источником пользовательских требований к коду.
Отдельные настройки Repository (в том числе `enabled`, фильтр веток и порог
severity из #149) управляют допуском run, включая rerun, и публикацией (§1).
Текущие enabled/фильтр читаются при допуске, порог и inline cap закреплены по §7.2.
Это второй канал конфигурации, а не набор custom rules. Будущий
UI отображает активный base snapshot и редактор `.review/rules.md`, а не активирует
параллельный DB-набор custom rules. Изменение вступает в силу только после попадания
файла в base нового run. Нельзя включать «несохранённый preview» для обычного run.

Запланированные операции `createRuleVersion`/`previewRuleVersion` из indicative
`contracts/openapi.yaml` требуют явной замены до реализации:

| Операция | Целевой контракт |
| --- | --- |
| Просмотр rules | Текст `.review/rules.md`, policy_base_sha, presence/checksum, диагностические лимиты и read-only effective snapshot |
| `previewRuleVersion` | Чистый preview UTF-8 Markdown: parse/ignore diagnostics, digest проекта политики и оценка токенов выбранного профиля; не запускает LLM, не меняет active policy |
| `createRuleVersion` | В v2 не активирует пользовательский DB row; заменяется отдельной Git draft/change операцией, если продукт её реализует |
| Просмотр исторической rule version | Чтение legacy rules для соответствующих старых runs; явно помечено как legacy |
| Управление service defaults | Служебное версионирование/rollout с отдельными полномочиями; не пользовательский редактор правил |

Публикация изменения правил в Git требует отдельного продукта/контракта операции:
авторизация repository, ветка/commit, optimistic concurrency по исходному blob SHA,
и явное действие пользователя. Этот документ не проектирует скрытую запись в
default branch и не смешивает редактор правил с VCS write-back результатов ревью.
Текущие indicative operation IDs нельзя тихо сохранить с несовместимым JSON body:
нужны versioned endpoints или объявленное изменение ещё не выпущенного контракта.

### 10.1. Статус правил репозитория (#150)

Механизм согласован техлидом [техлид, 18.10.2026, #150].

Просмотр rules из таблицы выше реализован как `GET /api/repos/{repo_id}/rules-status`
(`getRulesStatus` в `contracts/openapi.yaml`). Planned-операции `listRuleVersions`,
`createRuleVersion` и `previewRuleVersion` с прежним телом не реализуются: в контракте
у них остаётся `x-status: planned`, а `x-note` называет их заменёнными по этому разделу.

Read-only effective snapshot из строки «Просмотр rules» этот эндпоинт не отдаёт: он
показывает только сам файл (текст, sha, checksum, маски, диагностику). Effective
snapshot (§5, итог дефолтов и файла для прогона) вне объёма #150.

**Кто читает файл.** Процесс `api` ключа GitHub App не получает
([SECRETS.md](SECRETS.md)), поэтому VCS он не читает. `.review/rules.md` читает
`webhook-worker` и сохраняет результат в таблицу `repository_rules_status`: одна
строка на репозиторий (статус, ветка, sha, текст, checksum, маски `review-ignore`,
диагностика, версия дефолтов, время чтения и маркер запроса перечитывания). `api`
только отдаёт эту строку и ставит запрос.

**Как читается.** Ветка — текущая default branch из GitHub, затем полный SHA её
головы, затем дерево и blob по SHA; дальше те же `LoadPolicyDocuments`,
`normalize_document` и `parse_review_ignore`, что и для run (§3, §4). Адаптер
привязан к репозиторию и SHA, а не к PR и run, и классифицирует ошибки так же, как
адаптер run (§9). Неоднозначный `404`, `409`/`422`, усечённое или неоднозначное дерево дают
`unavailable`, а не `missing` (§3.1). Пустой файл — `present` с checksum пустых байтов
(§3.2). Достоверное отсутствие сохраняется строкой `missing` с версией дефолтов
(номер активной `rule_versions.version`, например `v1`): отсутствие — такой же
сохранённый результат, как и файл. Если у репозитория нет активной версии правил
(онбординг всегда её создаёт), `defaultsVersion` = `unknown`, и воркер пишет об этом
предупреждение в лог. `sha` — 40 hex в нижнем регистре; другой ответ GitHub о SHA
головы — временная ошибка `policy_fetch_transient`.

**Когда перечитывается.** Запрос — маркер в строке таблицы, его пишут в той же
транзакции, что и `NOTIFY webhook_work_available`, поэтому потерянное уведомление
только откладывает чтение до следующего прохода воркера (раз в 30 с и сразу после
старта), а не теряет его. Запрос ставят:

- подключение репозитория (`installation.created`, `installation_repositories.added`):
  в транзакции синхронизации, вместе с самим репозиторием;
- событие `push` в default branch. Файл меняют в самом репозитории (коммит или merge PR),
  а не в портале, поэтому без этого события сервис узнал бы об изменении только при
  следующем перечитывании. `push` в другие ветки и теги отбрасывается. Для этого App
  должна быть подписана на событие Push: это обязательный ручной шаг в настройках
  каждой App (staging, dev, sandbox), см. SYSTEM_DESIGN §8.2. Без подписки триггер
  молча не срабатывает, и изменение видно только по GET после порога в 10 минут. Новых
  прав не нужно, `contents: read` уже есть;
- `GET` статуса, если строки ещё нет, если результат старше 10 минут
  (`RULES_STATUS_STALE_AFTER`) или если последняя ошибка временная (`retryable`) и
  с её чтения прошло не меньше 30 секунд (`RULES_STATUS_RETRY_AFTER`), а при rate
  limit не меньше `Retry-After` GitHub, если он длиннее 30 секунд. Порог в 10 минут
  проверяется раньше, поэтому дольше 10 минут `Retry-After` чтение не откладывает;
  сохраняется он не больше чем на сутки (`RULES_STATUS_MAX_RETRY_AFTER`). GET отвечает
  сохранённой строкой, а не ждёт чтения; без строки он отвечает `pending`.

Запрос, пришедший во время чтения, не теряется: для захваченной строки он пишет новое
время, а `save` снимает только то время, которое было захвачено, поэтому следующий
проход читает файл ещё раз. `save` записывает результат, только если захват ещё свой:
чтение, чья аренда истекла и строку захватил другой воркер, не затирает более новый
результат. Неожиданное исключение при чтении сохраняется как `unavailable` с
`policy_fetch_transient` (`retryable: true`), поэтому GET через 30 секунд запросит
чтение снова.

Репозиторий, к которому App потеряла доступ (`installationAvailable: false` в
`GET /api/repos/{repo_id}`), воркер не читает. Для него GET сразу отвечает
`unavailable` с `policy_access_denied` (`retryable: false`, `sha` = null, `checkedAt` =
время ответа) и запрос чтения не ставит, поэтому `pending` не зависает.

Итог для контракта: после `push` изменение обычно видно через несколько секунд. Если
событие `push` потеряно или подписки нет, порог в 10 минут отсчитывается от последнего
чтения, а не от `push`: GET после порога ставит чтение, и новый результат показывает
уже следующий GET. Отдельной POST-ручки и кнопки «Обновить» нет.

**Состояния ответа.** Вариант различается полем `status`, а не текстом сообщения:
`present` (текст, маски, checksum, диагностика), `missing` (`defaultsVersion`),
`invalid` (ошибка формата или лимита; `text` = null, если файл не стал текстом),
`unavailable` (ошибка доступа, ревизии или временная; `sha` = null, если ветку не
удалось разрешить в коммит) и `pending` (чтения ещё не было). Общие поля — `branch`,
`path`, `sha`, `checkedAt`. Диагностика — поля §9 в camelCase: `code`, `message`,
`line`, `column`, `retryable` и, когда известны, `limit`, `actual`, `patternIndex`;
`actualIsLowerBound` приходит только как `true`, когда `actual` — лишь нижняя граница
(§9: например, байты, полученные к остановке потока blob за пределом 65536), а при
точном `actual` поля нет; диагностика, сохранённая до появления флага, читается как
точная. `message` — тот же понятный текст, что в check-run, с местом ошибки. Схема
ответа в `UI_ZOD_COMPONENTS` не входит.

Вне объёма: редактирование файла из портала, `previewRuleVersion` и подробности
ошибки политики в `RunSession` (#204).

Детерминированные проверки должны доказывать отсутствие запрещённых отправок,
изменения получателя, обхода версии и invalid publication. Отдельный versioned
adversarial corpus для review/conventions/verifier/repair/cache измеряет изменение
ответов модели: навязанные находки, подавленные реальные дефекты, игнорирование
допустимых исключений. Валидный JSON не считается прохождением смыслового сценария.
Критерии независимой оценки verifier и потерь верных findings определены в
связанной спецификации; корпус добавляется в `TEST_PLAN`, а не заявляется уже
пройденным. Полную защиту свободного Markdown от Prompt Injection спецификация
не обещает.

## 12. Замещаемые положения и зависимости внедрения

В #213 ограниченная внутренняя coverage хранится в существующих snapshots и JSON
`context.build`/`review.postprocess`, с привязкой к head, raw DiffMap digest и
snapshot digest; списки ограничены 20 безопасными элементами при точных counts.
Точный fully reviewed count опирается на полный доверенный набор changed patches,
а не на первые 20 элементов диагностики: повторный пропуск уже непроверенного
файла не уменьшает count снова. Этот внутренний набор не сериализуется;
диагностические списки остаются bounded, ignored имена не раскрываются.

Внутренний `checked_paths` #170 — пути с сохранённым review_patch != null
(пустая строка тоже входит). Этот набор обозначает доступные текстовые входы,
а не доказывает fully reviewed coverage #213: её точный счётчик берётся из
доверенного покрытия после fit. При partial путь доступного входа может быть
перечислен, хотя fully reviewed count равен 0; coverage остаётся partial, а
при пустых/info findings verdict=null. Supported blocking/attention сохраняются.
Для списка путей overview сначала проверяется канонический поддерживаемый путь.
При classification_unavailable либо наличии ignored exclusions все имена
консервативно скрываются; иначе packer #170 выводит целые пути в бюджете 4 000
Unicode-символов и строку «… и ещё N файл/файла/файлов». Это отдельный бюджет:
ограничение 20 элементов относится к coverage diagnostics, а не к body path list.
Перепаковка через run_url/overflow footer сохраняет backend summary, coverage и
severity threshold; она не возвращает raw model summary и не делает partial clean.

Закреплённый policy_base_sha (= Run.base_sha) не заменяется живым base; фактический diff_old_sha
хранится отдельно и не подменяется policy_base_sha. Контекст и restore используют
одну достоверную durable identity; восстановление — application-решение над
реальными сохранёнными входами, без фиктивных provider locator/meta.
Выбирается новейшая context.build с явной coverage classification; последующие
prompt-only записи (их писали только попытки до #168 ч.6) её не заслоняют, невалидная
новая classification не
возвращает старый clean. Referenced response body принадлежит тому же run.

Итог учитывает точный контекст после ignore и единственного fit_review_context
в GatewayReviewModel перед отправкой провайдеру. Omitted или prefix-truncated
разрешённый changed patch даёт
review_input_incomplete/partial; такой файл исключается из fully reviewed count.
Потеря только вспомогательного контекста не означает пропуск changed patch.
Потеря changed patch на внутренней границе модели учитывается, даже если
внешний контекст не изменился. Эти доверенные факты сохраняются через обе
ветки возврата reflection до финализации и публикации без расширения
LLM ReviewOutput. Технический drop unknown_path
также понижает coverage до partial; lint/duplicate/severity drops сами по себе
этого не делают. Остальные reflection coordinate drops, evidence_not_shown и
verifier insufficient_context остаются за lifecycle #107/#130; их общее влияние
на coverage не объявляется реализованным в #213.

После #130 F1 worker собирает Reflection Pass, а после F2 seed активирует
`review.system:v4` для новых runs. Snapshot-путь выбирается только по
закреплённому v4; runs с v3 или ниже, созданные до F2 seed либо с pins до 0039,
сохраняют legacy-путь без verifier. Адаптер ревью
выполняет fit/guard/manifest один раз: snapshot-ответ `ReviewReply` несёт
фактический fitted context и manifest принятого вызова, legacy — mapping.
В обоих ответах факт потери changed patch передаётся доверенным внутренним
carrier, сохраняется после unwrap и обеих веток Reflection Pass; JSON/schema
ответа модели не расширяются. Остальные технические drops из целевого lifecycle
#107/#130 не объявляются реализованными этим стыком.
Coverage понижается до summary/effort/verdict/body и сохранения
postprocess outcome. Supported blocking/attention сохраняются при partial;
пустые/info findings дают null. Complete допускается только без причин неполноты;
оба читателя сохранённого результата/coverage проверяют этот инвариант.

Старый action без достоверной classification использует unavailable/partial
fallback: counts-only, без имён потенциально ignored файлов. Валидные ignored
классификации также раскрывают только counts. Inline legacy без coverage
получает unavailable/partial, не complete/clean. Прямой legacy-вызов
FindingsPostProcessor.process с coverage=None также получает
classification_unavailable/partial до summary/body, без clean по отсутствию данных.
Повреждённый сохранённый JSON даёт warning с run_id без raw JSON, путей или
секретов; ожидаемое отсутствие записи само по себе не предупреждение. Оба
читателя используют общий валидатор status/count invariants; restore считает
snapshot digest один раз. StoreReviewOutput явно отклоняет отсутствующий backend
summary до записи/commit/очереди, независимо от Python -O.
Для none тело review и check-run
одинаково сообщают «нет доступных для анализа изменений».

В публичных detail/latest-run для всех состояний кроме SUCCEEDED summary=None и
saved_result=None; fallback не синтезируется заранее, latest-run batch читает
результаты только succeeded. Это gate публичного caller, не общего loader:
внутренний PUBLISHING recovery может читать доверенный finalized result для
сохранения исходных event/body/verdict. Существующие nullable поля API не меняются.
Для исторического succeeded без достоверного результата API может показать
fallback/null, тогда как ранее опубликованное GitHub-тело остаётся прежним;
историческая перепубликация не выполняется.

Нового публичного coverage DTO, LLM-полей, result_id или таблиц результата нет.
Полный #107, общий run-owned file_omissions #130/#168 и zero-LLM lifecycle
summary-only/none/no-text partial остаются целевыми, а не активированными #213.
Текущий summary-only может вызывать модель, но все его findings отбрасываются
как insufficient_context: нет inline, blocking/attention или дефектов из них;
coverage partial, verdict null. Обещание zero-LLM относится к будущему lifecycle.
