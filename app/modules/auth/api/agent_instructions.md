# Connect AI Code Reviewer from an agent

Work in the target Git repository. Use the HTTPS origin of this document as `API_ORIGIN` and read its `/openapi.json` for exact request and response fields. Determine the GitHub `owner/repo` from this repository's `origin` remote and confirm it with the user. Never put the App private key, a GitHub OAuth token, or the device code in a commit or chat reply.

1. **GitHub consent.** If the GitHub App is not installed on this repository, ask an owner to approve the installation using the App install link in the original instruction. The owner chooses this repository. The user must also authorize the App at `https://github.com/login/device` in step 3. These are GitHub permission grants, not actions in the AI Code Reviewer UI.
2. **Start authorization.** `POST /api/agent/device/start` with JSON `{"repository":"owner/repo"}`. Save `deviceCode` temporarily. Show `verificationUri` and `userCode` to the user and ask them to approve the App on GitHub. The agent must never request or receive the user's GitHub OAuth token.
3. **Poll.** After `interval` seconds, `POST /api/agent/device/poll` with JSON `{"deviceCode":"..."}`. Repeat on `status=pending` at `retryAfter` seconds, or honor the `Retry-After` header on HTTP 429. Stop on `denied`. On `expired`, ask whether the user wants to restart from step 2. On `authorized`, save the returned `token` in a local secret store or a file outside Git with mode 0600; save `tokenId` for owner revocation. Remove the device code. If HTTP 404 says the repository is unavailable, have the owner confirm the App installation and repository selection, then restart from step 2. On HTTP 502 or another server error after approval, wait briefly and restart from step 2; a new code may require GitHub confirmation again. If the error repeats, report it and stop. Do not log the token.
4. **Find and configure.** Send `Authorization: Bearer <agent token>` on subsequent calls. `GET /api/repos` and find the exact `fullName`; use its `id` as `repo_id`. `GET /api/repos/{repo_id}` first. Then `PATCH /api/repos/{repo_id}` with the settings the user wants: `enabled`, `branchFilter` (target branches; `[]` means all), `severityThreshold` (`all`, `warning`, `critical`), `reviewEvent` (`COMMENT`, `REQUEST_CHANGES`), `ragEnabled` (boolean), and optionally `waitForCi` (`auto`, `always`, `never`), `defaultEngine` (`fast`), `maxComments` (1–10). If no preferences were supplied, enable review while preserving all other current settings. Verify the PATCH response. An unavailable installation cannot be enabled by this PATCH.
5. **Rules.** Edit `.review/rules.md` in the Git repository, not through the portal API. It is plain UTF-8 Markdown (up to 64 KiB); headings such as `# Security`, `# Performance`, `# Style` are optional. Do not overwrite existing rules without asking. Commit and push the change using the user's normal Git workflow. The service reads rules from the target branch's base commit, so a new rules file affects later PRs after it reaches that branch. After pushing to the default branch, poll `GET /api/repos/{repo_id}/rules-status` until `status=present` and `sha` equals the commit the chosen PR uses as its base. Stop and report `missing`, `invalid`, or `unavailable` instead of triggering a review with the wrong rules.
6. **First review.** Select a real open PR targeting that default-branch commit with the user, or use a test PR in a test repository. After enabling reviews and verifying the rules status in step 5, add the `ai-review` label to an unlabeled PR using the user's normal GitHub permissions; the new `labeled` webhook triggers the review. If the label is already present, ask the user before you remove and reapply the label to create a new event. Merely enabling the repository or selecting an already-labeled PR does not start a run. `GET /api/repos/{repo_id}/pulls` shows synchronized PRs and recent runs. `GET /api/runs?repo=owner/repo` lists runs. If no run appears after the normal scheduling delay, report that and stop instead of polling forever. Poll `GET /api/runs/{run_id}` until a terminal status, then read its verdict and findings; `GET /api/runs/{run_id}/comments` and `/actions` provide published results. Report the review URL and result to the user. Do not fabricate a production change just to trigger review.
7. **Revoke.** With a browser access JWT, the owner can find active token IDs using `GET /api/agent/tokens`, then revoke one immediately with `DELETE /api/agent/tokens/{tokenId}`. The listing contains repository names and dates, never token secrets. A revoked or expired agent token receives 401. A token can access only its repository's settings, rules status, pull requests and review reads; it cannot access App keys, OAuth credentials, other repositories, metrics or administrative operations.
